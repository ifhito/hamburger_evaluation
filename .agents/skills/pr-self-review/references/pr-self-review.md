# PR Self Review リファレンス

## スコープ

このスキルはワーキングツリーだけをレビューする。PR をマージ・クローズ・
書き換えるかどうかは判断しない。

## 手順

1. `git status --short --branch --untracked-files=all` を確認する。
2. `git diff --check` を確認する。
3. `git diff --stat` を確認する。
4. ステージ済みの変更があれば `git diff --cached --stat` を確認する。
5. ファイルを次に分類する:
   - 意図した実装、
   - その実装を支えるテスト/チェック/ドキュメント、
   - 無関係または既存のローカルファイル。
6. 変更エリアに基づいて不足している検証を報告する:
   - backend: gofmt、go vet、go build、go test、
   - frontend: type-check、lint、test、
   - build/API 境界: frontend build。
7. 境界の規約を確認する(差分に該当する場合):
   - frontend にドメインのルールの判断(検証・権限の条件・定数・導出)が入っていないか。判断は
     backend の `domain` だけが持ち、frontend は backend が返した値とサーバーのエラーを表示する。
   - usecase が repository を宣言・保持・呼び出していないか(`.repo.` の呼び出し、`*Repository` の
     型・フィールド、`domain.*Repository` の参照)。読み取りは `*Query`、書き込みは domain の
     書き込みオブジェクトを通す。
   - 追加・変更したテスト名・コメントが、story を知らない人に伝わるか(story・受け入れ条件・issue の番号、
     意味の伝わりにくい英語が混ざっていないか。「状況 → 結果」が名前だけで分かるか)。

## `/code-review`(PR を ready にする前・人間にレビューを頼む前。必須)

このスキル自体は読み取りだけ(`git status` / `git diff`)なので、次は、呼び出し元
(オーケストレーター、メインセッション、または実装を直接任された側)が行う。

1. `/code-review` を実行する(Skill の `code-review`。対象は `origin/main` との差分)。
   **`args` に、対象のディレクトリの絶対パスと差分のコマンド(`git fetch origin` のあと
   `git -C <パス> diff $(git -C <パス> merge-base origin/main HEAD)`)を明示し、他のディレクトリの
   変更は対象外と書く**(`code-review` は、呼んだセッションの作業ディレクトリを見る。`git worktree`
   で作業していると、明示しない限り、主ディレクトリの未コミットの変更を黙ってレビューする。
   実測済み)。`ultra` は使わない。返ってきた結果の対象が自分の worktree であり、差分が空でない
   ことを確かめる。**別の木をレビューした結果(または差分が空)は、未実行として扱い、証拠として
   PR に残さない**。バックグラウンドの fork として実行され、10〜25 分かかる。結果が届くまで、
   短いコマンド(`date && sleep 25`。`sleep` で始まる長いコマンドは拒否される)で待つ。
2. 結果は「未検証(コードを読んだ結果。確度にはばらつきがある)」と明記される。指摘ごとに、
   **失敗するテストで再現を確かめる**(または、起きない根拠を書く)。再現した指摘は直す。
3. **結果の要約を PR のコメントに残す**(`gh pr comment`。指摘の番号・再現した/しない・
   直した内容・コミット)。
4. `/code-review` が使えない・失敗したとき(別の木・差分が空を含む)は、黙って飛ばさず、
   **未実行の理由**を PR のコメントに残し、利用者に手動での実行を頼む。理由だけのコメントは、
   ready にしてよい証拠ではない(PR は draft のまま、利用者の判断を待つ)。
