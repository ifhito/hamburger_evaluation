# PR Template

## ルール

1. **PR タイトルと本文は日本語で書く**(コード識別子・コマンド・パスは原文のまま)。
2. **概要は「やさしい説明」で書く**: 専門用語や内部用語を使わず、このプロジェクトを知らない人が読んでも「何ができるようになるのか / 何が変わるのか」が分かる言葉で 2〜4 行。技術的な詳細・実装の言葉は変更内容欄に書く。
   - ❌「ShopStatus VO を導入し可視性を VisibilityScope に集約」
   - ✅「お店は登録するとまず『承認待ち』になり、運営者が承認すると みんなに表示されるようになります。その仕組みを追加しました」
3. セクション構成は下のテンプレートに従う。空になるセクションは見出しごと削除してよい(空欄のまま残さない)。
4. **テスト欄には実際に実行したコマンドと結果だけを書く**。実行していない検証を書かない。スキップしたものは理由付きで明記する。
5. ストーリー issue から作る PR は必ず `Closes #<issue>` を関連 Issue 欄に入れる。
6. 規模ゲートで「大」判定の PR は、レビュー観点欄に**推奨レビュー順**(どのファイルからどの順で読むか)を書く。
7. 末尾の attribution(Generated with Claude Code / セッションリンク)はハーネスの規約どおり付与する。

## テンプレート

```markdown
## 概要

<!-- やさしい説明: 専門用語を使わず、何ができるようになるか/何が変わるかを2〜4行で。
     プロジェクトを知らない人が読んでも分かる言葉で。技術詳細は変更内容へ -->

## 関連 Issue

Closes #<番号>

## 変更内容

- <!-- 意図ごとに箇条書き。ファイル列挙ではなく変更の意味を書く -->

## テスト

<!-- 実行したコマンド + 結果(pass/fail)。実測のみ。 -->
- `go-checks.sh` → exit 0
- `docker compose up` スモーク: /up → 200

## レビュー観点

<!-- レビュアーに最初に見てほしい箇所、設計判断、リスク。大きい PR は推奨レビュー順 -->

## 備考

<!-- マイグレーション有無、先送り事項(P3等)、フォローアップ、既知の制約 -->
```

## 既存 PR を更新するとき

- 追加コミットで内容が変わったら本文も追従させる(テスト欄に最新の実測を追記)。
- レビュー往復で決まったこと(採用した修正方針・棄却理由)は備考に残す。
