# ADR-0004: 写真の保存先

- ステータス: 提案中(Proposed)
- 日付: 2026-09-21(2026-09-20 初版「静的ファイルとアップロード画像」を全面改訂・改題)
- 対象: レビューに添付する写真の保存先と配信経路
- 方針: **無料で始める**
- 関連: [ADR-0001](0001-frontend-deploy-target.md)、[ADR-0002](0002-backend-deploy-target.md)

## 背景

**初版は「写真機能は未実装。実装するときまで着手しない」と書いたが、これは誤りだった。**
実装は完成しており、しかも初版が推奨した設計とは**正反対**である。

### 実装されている経路

```text
ブラウザ                    Go API                      保存先
  |                           |                           |
  |-- multipart/form-data --->|                           |
  |   (POST /reviews の        |-- デコード                 |
  |    photo パート)           |-- 向き補正(EXIF)          |
  |                           |-- 長辺 1600px へ縮小        |
  |                           |-- 再エンコード              |
  |                           |------- 保存 -------------->| disk or S3
```

- `internal/photo/` が画像処理、`internal/adapter/storage/{disk,s3}.go` が保存を担う。
- **署名付き URL による直接アップロードではない。** 写真は必ず API を経由する。
- フロントも送信前に縮小する(`frontend/src/lib/photoResize.ts`。基準値は `GET /meta` から取得)。
  ただし判定と再処理は backend が行う。

初版の「署名付き URL でブラウザから直接アップロードし、API は本体を中継しない」という決定は**撤回する**。

### 制約(CLAUDE.md より)

| 項目 | 値 |
|---|---|
| 受け付ける形式 | JPEG / PNG / WebP のみ(中身で判別)。HEIC / HEIF は 422 |
| 保存形式 | JPEG→JPEG、PNG→PNG、WebP→JPEG |
| 保存サイズ | 長辺 1600px 以下に縮小(拡大はしない) |
| ファイル上限 | 5 MiB |
| 寸法上限 | 1 辺 10,000px かつ 2,400 万画素 |
| リクエスト上限 | multipart は 6 MiB |

### 保存先の切り替え

`PHOTO_STORAGE` が `disk`(既定)か `s3` かで、**配信経路まで変わる**。

- `disk`: API の `GET /photos/*` が配信する。フロント側に `/photos/*` のリライトが要る。
- `s3`: `GET /photos/*` は登録されない。写真の URL は `PHOTO_PUBLIC_BASE_URL`(バケットの公開ドメイン)を指す。

本番は `s3` を使う。API を画像配信から外せるうえ、フロントのリライトも 1 本減る。

### 設計が変わったことで消えた論点・増えた論点

| 論点 | 初版 | 実装を読んだあと |
|---|---|---|
| バケットのアップロード用 CORS | 必須 | **不要**(ブラウザはバケットに直接触らない) |
| 署名付き URL の発行コード | 各社で比較 | **不要** |
| API のメモリ | 論点なし | **最重要**。デコードが API のメモリを食う |
| API の帯域 | 論点なし | アップロードが API を通る |
| 外部の画像変換サービス | 折衷案として検討 | **不要**。保存時に 1600px へ縮小済み |
| 転送量(配信) | 最重要 | **最重要のまま** |

## 評価軸

1. **転送量(egress)の無料枠**。写真は 1 回書いて何度も読むため、ここが最初に尽きる
2. 保存容量の無料枠
3. **S3 互換 API**(`adapter/storage/s3.go` がそのまま使えるか。エンドポイントを差し替えるだけで済むか)
4. 公開配信のしやすさ(カスタムドメイン、CDN)
5. 東京または近傍リージョン

## 無料で始められる候補

条件は 2026-09 時点の目安。

| 候補 | 保存 | 転送量 | S3 互換 | 公開配信 | 立地 |
|---|---|---|---|---|---|
| Cloudflare R2 | 10GB | ◎ **無料・無制限** | ◎ | ◎ カスタムドメイン | ○ 自動配置 |
| Supabase Storage | 1GB | △ 5GB/月 | ◎ | ○ | ◎ 東京 |
| Tigris | 5GB | ○ Fly 内は無料、外部は従量 | ◎ | ○ | ○ グローバル |
| Backblaze B2 | 10GB | ○ 保存量の 3 倍/月まで無料 | ◎ | ○ Cloudflare 併用で無制限 | ✕ 米・欧 |

### 所感

- **Cloudflare R2**: 転送量が無料・無制限という条件は唯一。`PHOTO_S3_ENDPOINT` に R2 の
  エンドポイントを入れるだけで `adapter/storage/s3.go` がそのまま動く。カード登録は要るが無料枠内なら請求は出ない。
- **Supabase Storage**: DB も Supabase にするなら一体化できる。転送量 5GB/月は写真用途では小さい。
- **Tigris**: API を Fly に置く場合のみ R2 と並ぶ。今回 Fly は候補外([ADR-0002](0002-backend-deploy-target.md))。
- **B2**: R2 登場前の定番。Cloudflare を挟むなら R2 を直接使うほうが単純。

## それ以外(有料のみ、または不要になったもの)

| 候補 | 理由 |
|---|---|
| ImageKit / Cloudinary / Cloudflare Images | 保存時に 1600px へ縮小済みなので、動的変換の必要が薄い |
| Wasabi / Hetzner / DO Spaces | 無料枠がない |
| AWS S3 | 無料枠が 12 か月で終わる |
| Render Disk | 直接配信も CDN も無い。`PHOTO_STORAGE=disk` 用の緊急手段 |
| MinIO(セルフホスト) | 開発環境では有用。本番は VPS 構成のときのみ |

## 実測(2026-09-21、Phase 2)

4 社を、`adapter/storage/s3.go` と同じ組み立ての client で計測した(300KiB を 50 回ずつ)。

| 候補 | PUT p50 | **GET p50** | DELETE p50 | GET の標準偏差 |
|---|---|---|---|---|
| **Tigris** | **89.2ms** | **26.0ms** | **22.3ms** | 19.3ms |
| Supabase Storage | 433.2ms | 38.5ms | 199.8ms | 106.1ms |
| Cloudflare R2 | 160.2ms | 80.9ms | 77.8ms | 36.8ms |
| Backblaze B2 | 233.2ms | 280.7ms | 185.6ms | 8.5ms |

### 予想が外れた点: Region のハードコードは問題にならなかった

実装は `Region: "auto"` を固定している。AWS の署名 v4 は署名鍵にリージョンを含むため、
実リージョンを要求する事業者では弾かれると見ていたが、**4 社ともそのまま通った**。
エンドポイントにリージョン名を持つ B2 でも問題なかった。

**本 ADR の「コード変更は不要」という前提は支持された。**

### 決定を揺るがす点: Tigris が全項目で最速

GET 26.0ms は R2 の 3 分の 1 である。本 ADR は Tigris を「Fly.io を使う場合のみ」と
位置づけていたが、**単体で R2 を上回っている**。

ただし R2 は開発用の `r2.dev` URL で測っており不利がある。カスタムドメインでの再計測が要る。

**速さでは Tigris、費用では R2(転送量が無料・無制限)。** 配信量の見込みで決まる。

詳細は `docs/benchmarks/phase2-summary.md` にある。

## 決定(案)

- **Cloudflare R2** を使う。本番は `PHOTO_STORAGE=s3`。
- 配信は R2 のパブリックバケットにカスタムドメインを付け、`PHOTO_PUBLIC_BASE_URL` に設定する。
  API は配信に関与しない。
- 動的な画像変換サービスは使わない。保存時の縮小で足りる。
- 開発環境は `PHOTO_STORAGE=disk` のまま。S3 互換の検証が要るときは MinIO を立てる。

## 結果・影響

- 設定するもの: `PHOTO_STORAGE=s3`、`PHOTO_S3_ENDPOINT`、`PHOTO_S3_BUCKET`、
  `PHOTO_S3_ACCESS_KEY_ID`、`PHOTO_S3_SECRET_ACCESS_KEY`、`PHOTO_PUBLIC_BASE_URL`。コード変更は不要。
- アクセスキーは環境変数で渡す。リポジトリに書かない。
- **API のメモリが本 ADR の裏テーマになった。** 保存先を R2 にしても、デコードは API で起きる。
  無料枠の 512MB で 2,400 万画素の写真が処理できるかは [ADR-0002](0002-backend-deploy-target.md) の
  計測項目であり、結果によっては「写真つき投稿だけ有料プラン」という結論もありうる。
- 有料化するとき: R2 は保存量だけ従量($0.015/GB/月)。転送量は無料のままなので、
  写真が増えても配信コストは増えない。
- バケットには**アップロード用の CORS 設定が不要**。誤って公開書き込みを許可しないよう、
  書き込みはアクセスキーを持つ API だけに限ること。
