# ADR-0005: 非同期処理の実行基盤

- ステータス: 一部承認。1(現行の統計再計算の維持)は 2026-09-24 に本番で採用。2(定期実行)は未実装
- 日付: 2026-09-21(2026-09-20 初版を、実装の確認を受けて決定ごと差し替え)
- 対象: `backend-go/` のバックグラウンド処理
- 方針: **無料で始める**
- 関連: [ADR-0002](0002-backend-deploy-target.md)、[ADR-0003](0003-database-hosting.md)

## 背景

**初版は「キューを持たず、同期実行 + 外部 cron で足りる」と結論したが、これは実装を読まずに書いた誤りだった。**
実際には DB を使った待ち行列とワーカーが既に実装されており、その設計は妥当である。本 ADR は決定を差し替える。

### 実装されている仕組み

```text
レビューの投稿/編集/削除・退会
        |
        |  同一トランザクション
        v
burger_stats_recalc_requests に 1 行 upsert(バーガーごとに 1 行)
        |
        v
StatsWorkerLoop(goroutine、既定 1 秒間隔、1 サイクル 20 件まで)
        |
        v
統計を再計算して burger_stats を更新 → 依頼の行を削除
```

要点は次のとおり。

- **登録は書き込みと同一トランザクション。** 統計そのものはリクエスト内で計算しない。
- **バーガーごとに 1 行。** 同じバーガーへの連続した書き込みは、再計算 1 回にまとまる。
- **`version` は sequence から取る。** ワーカーは取り出したときの `version` と一致する行だけ削除するので、
  処理中に入った新しい依頼を消してしまうことがない。
- **再試行がある。** `attempts`、`next_attempt_at`、`last_error` を持ち、上限は `STATS_WORKER_MAX_ATTEMPTS`(既定 8)。
- **起動直後に 1 サイクル回す。** 前回の停止までに溜まった依頼を、再起動やスリープ復帰のたびに回収する。

### スリープする無料枠との相性

初版では「プロセス内タイマーは寝ているホストで発火しない」ことを問題視した。
実装を読むと、**この設計では実害が出にくい**。

- 依頼が増えるのは書き込みリクエストが来たときだけで、そのときホストは必ず起きている。
- ワーカーの間隔は既定 1 秒。Render のスリープまで 15 分あるので、通常は寝る前に処理が終わる。
- 取りこぼしても、起動直後の 1 サイクルが次のアクセス時に回収する。

**「スリープ中にキューが溜まり続ける」という初版の懸念は成立しない。**

### それでも残る課題

| # | 課題 | 影響 |
|---|---|---|
| 1 | Cloud Run はリクエスト処理中以外の CPU を絞る | 常駐ワーカーが動かない可能性。再試行が次のリクエストまで止まる |
| 2 | 時間減衰のための定期全件再計算が存在しない | スコアは 180 日半減期で減衰するが、依頼はレビューの書き込み時にしか入らない。放置されたバーガーの統計が古いままになる |
| 3 | 期限切れ行の削除がない | `oauth_token_sessions`(アクセス 15 分・更新 30 日)と `mail_deliveries` が溜まる。無料枠の 0.5GB に効く |

課題 1 はデプロイ先の選定に直結する([ADR-0002](0002-backend-deploy-target.md))。
課題 2 と 3 は**定期実行の仕組みが要る**という同じ形をしている。

## 評価軸(定期実行の担い手)

課題 2 と 3 を動かす方法を選ぶ。

1. **無料枠の条件**
2. 寝ているホストを起こせるか
3. 追加インフラの有無
4. 実装量(エンドポイントの追加、シークレット管理)
5. 発火の遅延と再試行

## 候補

| # | 候補 | 起こす主体 | 無料枠 | 遅延 | 再試行 | 所感 |
|---|---|---|---|---|---|---|
| 1 | cron-job.org | 外部 cron が HTTP で叩く | 実質無制限 | 小 | 簡易 | 最も手軽。URL と時刻を登録するだけ |
| 2 | GitHub Actions(`schedule`) | CI が HTTP で叩く | 公開リポジトリは無制限 | **数分〜十数分ずれる** | ジョブ単位 | 設定がリポジトリに残りレビューできる |
| 3 | Upstash QStash | 外部キューがプッシュ | 500 メッセージ/日 | 小 | ◎ DLQ・署名検証 | ホストを問わない。実装がやや増える |
| 4 | Google Cloud Scheduler | GCP が HTTP で叩く | 3 ジョブまで | 小 | ○ | API が Cloud Run のときのみ自然 |
| 5 | ワーカー内の定期処理 | プロセス内 | — | — | — | **採用しない**。寝ているホストで発火しない(課題 1 と同根) |

日次〜時間単位の処理なので、2 の遅延は実害にならない。

## 決定

### 1. 現行の統計再計算はそのまま維持する(採用)

DB キューと `StatsWorkerLoop` を変更しない。River などの外部ライブラリも導入しない。
初版の「同期実行にすべき」という推奨は撤回する。

- 同期にすると、レビュー投稿のレスポンスに再計算が乗る。
- 現行は同一トランザクションで依頼だけ積むので、書き込みの整合性は保ちつつ応答は速い。

### 2. 定期実行が必要な 2 つを、内部エンドポイント + 外部 cron で回す(未実装)

| エンドポイント | 周期 | 課題 |
|---|---|---|
| `POST /internal/jobs/recalculate-all` | 日次 | 時間減衰の反映 |
| `POST /internal/jobs/cleanup-expired` | 日次 | トークン・メール履歴の削除 |

API が Cloud Run に決まったので、叩く側は **Cloud Scheduler** を第一候補とする。全件再計算は、統計を直接書くのではなく `burger_stats_recalc_requests` に全バーガー分の依頼を積む。

### 3. Cloud Run での常駐ワーカー(実測の結果)

Cloud Run は要求がない間インスタンスを 0 にするので、**誰も見ていない間はワーカーも止まる**。依頼は DB に残り、次の起動直後の 1 サイクルでまとめて処理される。実害は「しばらく誰も来ないと、統計の反映が遅れる」ことに限られるので、いまは何もしない。

確実に動かす必要が出たら、最小インスタンスを 1 にする(常時課金)か、2 の cron で起こす。

## 結果・影響

- **2 は未実装。** 内部エンドポイント 2 本と、その認証(公開 API の JWT とは別系統)が要る。
- 削除ジョブの対象と基準を決める。`oauth_token_sessions` は期限切れ、`mail_deliveries` は送信から一定期間を経たもの。
- 外部 cron を置いたら、**どこで何を叩いているかを本 ADR か [インフラ構成](../infrastructure.md) に必ず記録する。**
- `STATS_WORKER_INTERVAL` は既定 1 秒。Neon の無料枠のコンピュート時間が気になったら 5〜10 秒へ緩める。
