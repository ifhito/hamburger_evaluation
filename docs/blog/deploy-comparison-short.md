## はじめに

生成 AI やフレームワーク、クラウドサービスが充実して、個人でもサイトや Web アプリを形にしやすくなりました。仕事や趣味で「ちょっと作って公開したい」と思う場面もあるのではないでしょうか。

作るところまでは早くても、いざ公開しようとすると、無料で始められるサービスがたくさん出てきます。どれを選び、どう組み合わせればよいのかは、料金表を眺めるだけではなかなか決められません。

個人開発のハンバーガーレビューアプリ(Go + React)を、できるだけ無料で動かしたい。そう思って調べ始めたら候補が多すぎたので、**DB・写真ストレージ・メール・API・フロントの 5 層で 4 つずつ、計 20 サービスに実際にデプロイして比べました**。

先に結果だけ確認したい方は、末尾の[選んだ構成](#選んだ構成)から読めます。

## 何をどう比べたか

**本物のアプリをそのまま置いて測りました。** ミニマムなサンプルだと、写真処理で使うメモリや SMTP のポートのような、実際に効いてくる制約が見えないからです。

アプリは Go 1.27(標準 `net/http` + sqlc + pgx)と React 19 の SPA です。DB は PostgreSQL で主キーは UUID、レビューの写真はサーバー側で長辺 1600px に縮小し、サインアップの確認メールを SMTP で送ります。

候補の条件は「無料で始められて、個人が一人で登録から運用までたどり着けること」にしました。営業への問い合わせが要るもの、自前でサーバーを運用するもの、IAM の設計が要るものは外しています。

計測は日本の自宅回線からで、数字は p50(中央値)です。順序は DB → 写真 → メール → API → フロントで、後ろの層は前の層で選んだものに向けて測りました。

候補は延べ 80 ほど見て、層ごとに 4 つに絞りました。絞り方は**「同じ軸を代表するものを 2 つ入れない」**です。各章では今回比べた4つと実測結果を先に紹介し、そのあとに「ほかの選択肢」として選ばなかった候補をまとめます。前提が違えば、そちらのほうが合うこともあると思います。

## 今回の比較条件と限界

これは、すべての個人アプリにそのまま当てはまるランキングではありません。今回作ったアプリを、できるだけ変更せず無料で動かす場合の比較です。

- 既存の Go API、PostgreSQL、S3 互換ストレージ、SMTP という構成を維持しています。別の言語やデータベースへ乗り換える選択肢は同じ条件で測っていません
- フロントエンドは `/api/*` を同一オリジンで呼ぶ作りです。そのため、外部の API へ `/api/*` を転送できることを今回の条件にしました。CORS を許可して API を直接呼ぶ構成なら、候補は増えます
- DB → 写真 → メール → API → フロントの順に選び、後ろの層は前の層で選んだ構成に向けて測っています。各層を完全に独立して比較したものではありません
- 速度は日本の自宅回線から測った中央値です。利用地域や時間帯が変われば結果も変わると思います
- 無料枠と料金は 2026 年 9 月時点のものです。無料プラン、試用期間、登録条件は変更される可能性があります

## 1. データベース

### 今回比べた 4 つ

このアプリは pgx + sqlc で、UUID 主キー・外部キー 6 本・`FOR UPDATE SKIP LOCKED` を使っています。なので「Postgres のワイヤプロトコルで、これらがそのまま動くこと」が最低条件になります。ここで MySQL 系と SQLite 系と NoSQL が落ちました。

残った Postgres 勢から、**違う軸を代表する 4 つ**を選んでいます。

- **Neon** は「休む DB」の代表です。使った時間で課金する方式が、個人アプリで本当に無料で収まるのかを見たかった
- **Supabase** は 4 社で唯一、東京リージョンがあります。「1 週間触らないと止まる」という変わった挙動も測っておきたかった
- **Render Postgres** は「API と同じ事業者に置く」構成を試すために入れました。API の当初の第一候補が Render だったからです
- **Xata** はニッチ枠です。日本語の情報がほぼなく、測ること自体に価値があると思いました

### 4 社の顔ぶれ

**Neon**(Databricks 傘下・米)は、サーバーレスの Postgres です。無料で使えるのは保存 0.5GB、コンピュート 100 CU 時間/月までで、カードは要りません。超えると従量課金で $0.106/CU 時間、保存 $0.35/GB 月になり、月額の最低額はありません。5 分触らないと自動で休止し(無料枠では無効化できません)、DB を Git のようにブランチできるのが特徴です。

**Supabase**(シンガポール)は、Postgres を中心に認証やストレージまで 1 つのプロジェクトで提供する「Firebase 代替」です。無料枠は DB 500MB、プロジェクト 2 つまでで、カードは要りません。ただし **1 週間触らないと一時停止します**。超えると Pro $25/月(DB 8GB 込み)です。東京リージョンがあります。

**Render Postgres**(米)は、アプリ基盤 Render のマネージド Postgres です。無料枠は 1GB、256MB RAM ですが、**作成から 30 日で失効します**。有料は $6/月(256MB)からです。同じ Render の Web サービスと私設ネットワークでつながるので、常用するなら有料前提の選択肢になりそうです。

**Xata**(米)は、ブランチ機能を中核にした Postgres です。料金ページを見る限り、常設の無料枠ではなく、14 日間の無料トライアルという位置づけだと思います。今回の検証も、この無料トライアルの期間内に行いました。有料はコンピュート $0.012/時から、保存 $0.28/GB 月です。差分だけ課金される Copy-on-Write のブランチと、ゼロダウンタイムのスキーマ変更を特徴としています。

### 実測

日本から pgx で直接叩いて、各 200 回測りました。

| 候補 | リージョン | 往復(SELECT 1) | 書き込みトランザクション |
|---|---|---|---|
| **Neon** | シンガポール | **86ms** | **348ms** |
| Supabase | ムンバイ | 131ms | 527ms |
| Render | オレゴン | 146ms | 588ms |
| Xata | 米国東部 | 177ms | 714ms |

**差は距離だけでした。** 4 社ともマイグレーション 12 本が無改変で通り、互換性では差がつきません。

意外だったのは、主キーでの 1 件取得も、3 テーブルを結合した 20 件も、`SELECT 1` と区別がつかなかったことです。この規模だと DB の処理時間はネットワークの往復に完全に埋もれてしまいます。

書き込みだけが 4 倍遅いのは、BEGIN から COMMIT まで 4 往復しているからです。4 社とも倍率がぴったり 4.02〜4.04 で揃いました。時間を決めているのは DB の性能ではなく往復回数なので、CTE で 1 文にまとめれば 1 往復にできます。

### 実際に組み込んで気づいた癖

ここで少し分かりにくかったのが pooler です。アプリと PostgreSQL の間に入り、DB 接続を使い回してくれる仕組みで、接続数を抑えられます。ただ、今回試した範囲では、用途に応じて URL を使い分ける必要がありました。

Supabase の Direct connection は、今回確認した範囲では IPv6 前提だと思います。IPv4 しか使えない実行環境から接続する場合は、Session pooler を経由する形になりそうです。

Neon は普段の API であれば pooler 用 URL で動きました。ただ、マイグレーションでは prepared statement と相性が悪かったため、そのときだけ直結 URL に切り替えました。

このことから、アプリ用とマイグレーション用で、あらかじめ接続先を分けておくと扱いやすいと思います。


### ほかの選択肢

以下は今回の条件では比較対象に入れなかったものです。構成や重視する点が違えば、こちらのほうが候補になる場合もあると思います。

| 区分 | サービス |
|---|---|
| 技術的に使えない | Aurora DSQL(外部キー非対応)、Cloudflare D1(Workers 内専用)、MongoDB Atlas / DynamoDB(リレーショナルでない) |
| 別の道具に乗り換えることになる | PlanetScale、TiDB Serverless(MySQL)、Turso、SQLite + Litestream |
| 要件に対して過剰 | CockroachDB、YugabyteDB(分散 SQL) |
| 今回の比較軸を増やさない | Aiven、Prisma Postgres、Nile |
| 無料で始められない | Fly Postgres |
| 個人には運用が重い | Oracle Cloud の VM に自前構築 |
| 登録できなかった | Koyeb Postgres |

選ばなかったものの概要です。料金と運営は 2026 年 9 月に公式ページで確かめました。

**技術的に使えなかった**

今回は既存の Go + PostgreSQL の実装を変えずに動かすことを条件にしました。外部キーが使えないもの、Workers 専用のもの、リレーショナル DB ではないものは、料金を比較する前に対象から外しています。

**[Amazon Aurora DSQL](https://aws.amazon.com/rds/aurora/dsql/)**(AWS・米)は、PostgreSQL 互換のサーバーレス分散 SQL です。毎月 10 万 DPU と 1GB が無料で、超えると 100 万 DPU あたり $8 です。外部キーとシーケンスに対応していないので外しましたが、リージョンをまたいで止まらない構成を最初から考える場合は候補になりそうです。

**[Cloudflare D1](https://developers.cloudflare.com/d1/)**(Cloudflare・米)は、SQLite の SQL を持つ Workers 向けのサーバーレス DB です。無料で読み 500 万行/日、書き 10 万行/日、5GB まで使えます。Workers の中からしか使えないので Go の API には合いませんでしたが、アプリ本体も Workers に置く構成とは相性がよさそうです。

**[MongoDB Atlas](https://www.mongodb.com/atlas)**(MongoDB, Inc.)は、マネージドのドキュメント DB です。M0 は 512MB で永久無料、有料は Flex が $0.011/時からです。JSON 中心のスキーマで、リレーションや外部キーを必要としない人であれば、候補の一つになりそうです。

**[Amazon DynamoDB](https://aws.amazon.com/dynamodb/)**(AWS・米)は、サーバーレスのキーバリュー DB です。常時無料枠が 25GB、25 WCU・25 RCU と大きめです。アクセスパターンが決まっていて、キー指定の読み書きが中心の AWS 利用者とは相性がよさそうです。

**別の道具に乗り換えることになる**

MySQL や SQLite へ移ると、pgx、sqlc のクエリ、PostgreSQL 用のマイグレーションを見直す必要があります。サービス自体の条件は良くても、今回はデプロイ先の比較より先にアプリの作り替えが発生するため選びませんでした。

**[PlanetScale](https://planetscale.com/)**(米)は、MySQL(Vitess / Neki)と PostgreSQL のマネージド DB です。無料枠はなく、最安は Postgres の単一ノード PS-10 で $10/月です。月 $10 を払えて、将来シャーディングまで見据える人とは相性がよさそうです。

**[TiDB Cloud Starter](https://www.pingcap.com/tidb-cloud-serverless/)**(PingCAP・米)は、MySQL 互換のサーバーレス分散 SQL です。無料枠は 1 インスタンスあたり 5GiB + 5GiB、5,000 万 RU/月と大きく、東京も選べます。MySQL 互換でよく、無料枠の大きい分散 DB を試したい人であれば、候補の一つになりそうです。

**[Turso](https://turso.tech/)**(米)は、SQLite / libSQL 系のマネージド DB です。無料で 5GB、DB 100 個、読み 5 億行/月まで使え、カードも要りません。SQLite の手軽さのまま、DB を多数作ったりエッジ寄りに置きたい人とは相性がよさそうです。

**[Litestream](https://litestream.io/)**(Ben Johnson 氏の OSS。Fly.io が支援)は、SQLite の変更を S3 などへ継続的に複製するツールで、DB サービスではありません。ソフトは無料で、費用は複製先のストレージ代だけです。単一 VM + SQLite で運用し、バックアップだけ欲しい人であれば、候補の一つになりそうです。

**要件に対して過剰**

どちらも分散構成に強みがありますが、今回のアプリは小規模で、複数リージョンへの分散や水平スケールを必要としていません。固有の強みを使わないまま複雑さだけが増えると考えて外しました。

**[CockroachDB Cloud](https://www.cockroachlabs.com/product/cockroachdb-cloud/)**(Cockroach Labs・米)は、PostgreSQL ワイヤ互換の分散 SQL です。Basic は毎月 $15 相当(5,000 万 RU + 10GiB)が無料ですが、カード登録が前提です。Postgres 互換のまま、地理分散と水平スケールが要件の人とは相性がよさそうです。

**[YugabyteDB Aeon](https://www.yugabyte.com/cloud/)**(Yugabyte・米)は、PostgreSQL 互換の分散 SQL です。Sandbox は 2 vCPU・4GB・10GB が永久無料でカード不要ですが、単一ノード・バックアップなし・10 日無操作で停止と、公式が本番には不向きと明記しています。分散 Postgres を学習・検証したい人であれば、候補の一つになりそうです。

**今回の比較軸を増やさない**

この3つは使えないわけではありません。4社という枠の中で異なる特徴を比べたかったため、今回の構成で固有機能を活かせないものを外しました。Aiven は癖の少ない比較基準として入れる余地がありましたが、素の PostgreSQL という点で Render と役割が重なります。Prisma Postgres は Go から使うため Prisma 向けの利点が薄く、Nile のマルチテナント機能も単一テナントの今回のアプリでは使いません。

**[Aiven for PostgreSQL](https://aiven.io/postgresql)**(Aiven・フィンランド)は、素の PostgreSQL のマネージドサービスです。無料枠は 1 CPU・1GB RAM・1GB で期限がなく、有料は $5/月からです。EU 企業が運営する素の Postgres を使いたい場合や、1GB で足りる小規模な用途であれば候補になりそうです。

**[Prisma Postgres](https://www.prisma.io/postgres)**(Prisma Data, Inc.)は、操作数で課金するマネージド PostgreSQL です。無料で 500MB、20 万操作/月まで使え、カード不要です。Prisma ORM を使う TypeScript アプリで、DB とホスティングを 1 か所にまとめたい人とは相性がよさそうです。

**[Nile](https://www.thenile.dev/)**(Nile Platform・米)は、マルチテナントの B2B アプリ向けサーバーレス PostgreSQL です。無料で 1GB、5,000 万クエリトークン/月まで使えます。テナント分離を DB 側で担保したい SaaS 開発者なら検討しやすいと思います。

**無料で始められない・運用が重い・登録できなかった**

このグループは技術要件ではなく、無料で検証を始められることと、一人で運用できることに合わず外しました。Koyeb は条件上は候補でしたが、検証時に登録できなかったため比較できませんでした。

**[Fly.io Managed Postgres](https://fly.io/docs/mpg/)**(Fly.io・米)は、Fly.io 上のマネージド PostgreSQL です。無料枠はなく、最安は Basic $38/月です。アプリを Fly.io に置いていて、同じ基盤で DB も運用したい人であれば、候補の一つになりそうです。

**[Oracle Cloud Always Free](https://www.oracle.com/cloud/free/)**(Oracle)は、Autonomous Database 2 個と Arm の VM(合計 2 OCPU・12GB)などを期限なしで無料提供する枠です。DB は Oracle DB で Postgres 互換ではなく、VM に自分で Postgres を入れることになります。7 日間の使用率が 20% 未満の VM は回収されます。OS の更新やバックアップを自分で持ってよい人とは相性がよさそうです。

**[Koyeb Postgres](https://www.koyeb.com/docs/databases)**(Koyeb)は、Koyeb のマネージド PostgreSQL で、5 分無操作でスリープします。free インスタンスは 1GB・コンピュート 5 時間/月までです。検証時は利用登録ができませんでした。Koyeb にアプリを置いていて、常時稼働しない検証用 DB でよい人であれば、候補の一つになりそうです。

## 2. 写真ストレージ

### 今回比べた 4 つ

アプリのアダプタが使うのは S3 互換の `PutObject` と `DeleteObject` だけで、公開 URL からそのまま配信します。なので「S3 互換で、公開配信できること」が条件です。このアプリは保存時に縮小まで済ませているので、変換特化のサービスには出番がありませんでした。

写真は 1 回書いて何度も読まれるので、**転送量の課金を一番重く見ています**。

- **R2** は費用の面で第一候補でした。転送量が無料という一点が大きい
- **Supabase Storage** は、DB を Supabase にするなら一体で使えるかを見るために入れました
- **Tigris** は、アクセス元に寄せる分散型が速さにどう出るかを見たくて入れました
- **B2** は R2 登場前の定番で、4 社で唯一カードが不要です

### 4 社の顔ぶれ

**Cloudflare R2**(米・上場)は、S3 互換のオブジェクトストレージです。無料枠は保存 10GB、書き 100 万回/月、読み 1,000 万回/月で、カード登録は要ります。超えると保存 $0.015/GB 月ですが、**転送はいくら読まれても $0** です。これだけで選ぶ理由になります。

**Tigris**(米)は、全世界に分散する S3 互換ストレージです。無料枠は保存 5GB、書き 1 万回/月、読み 10 万回/月で、転送は無料です。超えると保存 $0.02/GB 月になります。データがアクセス元に追従して分散し、リージョン別の課金がありません。

**Supabase Storage**(シンガポール)は、Supabase プロジェクトに付属するファイル保存です。無料枠は 1GB、転送 5GB/月で、DB と同じく 1 週間触らないと休止します。超えると Pro $25/月(100GB 込み)、転送 $0.09/GB です。DB・認証と同じ権限(RLS)で扱えるのが強みですが、単価は R2 や Tigris より高めです。

**Backblaze B2**(米・上場)は、S3 互換の老舗ストレージです。最初の 10GB が常時無料で、転送は保存量の 3 倍/月まで無料、**カードも要りません**。超えると保存 $6.95/TB 月(約 $0.007/GB)と最安級で、最短保存期間などの縛りもありません。

### 実測

300KB の JPEG を各 50 回測りました。

| 候補 | PUT | GET | GET のばらつき |
|---|---|---|---|
| Tigris | **89ms** | **26ms** | 小 |
| Supabase Storage | 433ms | 39ms | **大**(最大 780ms) |
| **Cloudflare R2** | 160ms | 81ms | 中 |
| Backblaze B2 | 233ms | 281ms | **最小**(8.5ms) |

**速さでは Tigris が全項目で最速でした。** GET 26ms は R2 の 3 分の 1 です。それでも R2 を選んだのは、転送量の課金が長期的に効いてくるからです。

Supabase は中央値こそ速いのに、2 割ほどの閲覧で目に見えて待たされます。B2 は遅いけれど最も安定していました。**平均だけ見ると判断を誤ります。**

Region を `auto` に固定しているコードも、4 社ともそのまま通りました。エンドポイントと鍵を差し替えるだけで動きます。

### 実際に組み込んで気づいた癖

どちらも S3 互換なので、コード側はほとんど変えずに使えました。ただ、管理画面に出てくる名前と、アプリに設定する値が少し分かりにくいです。

B2 では普段のアカウント情報ではなく、App Key を使う形になると思います。keyID を S3 の Access Key ID、applicationKey を Secret Access Key として設定することで接続できました。

R2 はアップロードに使う S3 API のエンドポイントと、画像を表示するための公開 URL を分けて考える必要があると思います。`*.r2.dev` は開発用とのことなので、本番で使う場合は独自ドメインを用意する形になりそうです。

どちらもコードを変えるというより、管理画面に書かれている値をどこへ設定するかを確認することが重要だと思います。


### ほかの選択肢

以下は今回の条件では比較対象に入れなかったものです。構成や重視する点が違えば、こちらのほうが候補になる場合もあると思います。

| 区分 | サービス |
|---|---|
| S3 互換でない(コードを書き足す) | Vercel Blob、Cloudflare Images、Bunny Storage |
| 用途が違う(画像変換に特化) | ImageKit、Cloudinary、Uploadcare / Uploadthing |
| 無料枠がない、または期限付き | AWS S3、Google Cloud Storage、Azure Blob、Wasabi、DigitalOcean Spaces、Hetzner |
| 運用が重い、条件が読めない | MinIO(セルフホスト)、Storj、Render Disk |

選ばなかったものの概要です。

**S3 互換でない(コードを書き足す)**

今回は既存の S3 アダプタをそのまま使えることを条件にしました。専用 SDK や独自 API が必要なサービスは、同じコードで比較できなくなるため選びませんでした。

**[Vercel Blob](https://vercel.com/docs/storage/vercel-blob)**(Vercel・米)は、Vercel のプロジェクト向けオブジェクトストレージです。独自 SDK(`@vercel/blob`)で使い、S3 互換 API はありません。Hobby は保存 1GB、転送 10GB/月まで無料で、超えると課金ではなく 30 日間使えなくなります。フロントも Vercel に置いて Next.js から SDK だけで完結させたい人とは相性がよさそうです。

**[Cloudflare Images](https://www.cloudflare.com/developer-platform/products/cloudflare-images/)**(Cloudflare・米)は、画像の保存・変換・配信に特化したサービスです。変換は月 5,000 ユニークまで無料で、保存は $5/10 万枚月、配信は $1/10 万枚です。リサイズや形式変換をサーバーで持ちたくない人、画像枚数で料金を読みたい人であれば、候補の一つになりそうです。

**[Bunny Storage](https://bunny.net/storage/)**(BunnyWay・欧州)は、CDN 直結のファイルストレージです。API は独自の HTTP REST で S3 互換ではありません。無料枠はなく 14 日の試用で、以降は $0.01/GB 月、月額最低 $1 です。Bunny CDN への転送は無料なので、月 $1 台から CDN 込みで安く済ませたい人とは相性がよさそうです。

**用途が違う(画像変換に特化)**

このアプリは保存前に画像を縮小しており、配信時の変換機能を必要としていません。便利な機能ではありますが、今回の構成では追加料金や設定に見合う使い道がないため外しました。

**[ImageKit](https://imagekit.io/)**(ImageKit Private Limited・インド)は、画像・動画の変換と CDN 配信の層です。S3 や Wasabi など外部ストレージの前段に置けます。無料枠は帯域 20GB/月・保存 3GB で期限がなく、有料は $9/月からです。既存の S3 互換バケットを残したまま、URL パラメータで変換を足したい人であれば、候補の一つになりそうです。

**[Cloudinary](https://cloudinary.com/)**(米)は、画像・動画の管理・AI 変換・配信の SaaS です。無料は 25 クレジット/月(変換 1,000 回か保存 1GB か帯域 1GB が 1 クレジット)でカード不要ですが、有料は $89/月からと段差が大きいです。画像の加工が主機能の人とは相性がよさそうです。

**[Uploadcare](https://uploadcare.com/)**(米)は、アップロード UI・保存・画像処理・CDN をまとめたプラットフォームです。無料は操作 1,000 回/月・保存 1GB・転送 5GB で個人利用のみ、有料は $66/月からです。アップロードのウィジェットまで用意してほしい人であれば、候補の一つになりそうです。

**[UploadThing](https://uploadthing.com/)**(Ping Labs)は、TypeScript アプリ向けのアップロード SaaS です。無料で保存 2GB、有料は $10/月(100GB)です。フロントもバックも TypeScript で、認可付きのアップロードを数行で済ませたい人とは相性がよさそうです。

**無料枠がない、または期限付き**

長期間ほぼ無料で動かすことを重視したため、試用後に必ず課金されるものや転送量の単価が高いものは4社に入れませんでした。既に同じクラウドを使っている場合は、運用をまとめられる利点があると思います。

**[Amazon S3](https://aws.amazon.com/s3/)**(AWS・米)は、S3 API の本家です。2025 年 7 月以降の新規は「6 か月・最大 $200 のクレジット」方式で、以降は保存 $0.0265/GB 月、インターネットへの転送 $0.09/GB です。実績と周辺エコシステムを最優先する人であれば、候補の一つになりそうですが、転送の単価が重いです。

**[Google Cloud Storage](https://cloud.google.com/storage)**(Google)は、XML API が S3 互換ツールと相互運用できます。Always Free は米国リージョン限定で保存 5GB、北米からの転送 100GB/月です。日本向けの配信では無料転送の条件から外れるため、転送量を最も重く見た今回の4社には入れませんでした。

**[Azure Blob Storage](https://azure.microsoft.com/products/storage/blobs)**(Microsoft)は、Azure のオブジェクトストレージで、独自 REST API です。無料アカウントは $200 クレジット(30 日)+ 12 か月の無料枠で、カードが必須です。すでに Azure に寄せていて、Azure SDK で書くことに抵抗がない人とは相性がよさそうです。

**[Wasabi](https://wasabi.com/cloud-object-storage)**(米)は、egress と API 呼び出しが無料の S3 互換ストレージです。無料枠はなく、$7.99/TB 月で最低課金が 1TB 分です。数 TB 以上を置く人であれば、候補の一つになりそうですが、数 GB の個人アプリだと $7.99/月が固定で乗ります。

**[DigitalOcean Spaces](https://www.digitalocean.com/products/spaces)**(米)は、CDN 内蔵の S3 互換ストレージです。無料枠はなく、$5/月で保存 250GiB・転送 1TiB が込みです。月 $5 固定で CDN 込みの転送枠を確保したい人とは相性がよさそうです。

**[Hetzner Object Storage](https://www.hetzner.com/storage/object-storage/)**(Hetzner・ドイツ)は、欧州 3 拠点の S3 互換ストレージです。無料枠はなく、基本料金に保存 1TB と egress 1TB が含まれます(金額はページから取得できず)。EU にデータを置きたい人、TB 級の egress が要る人であれば、候補の一つになりそうです。

**運用が重い、条件が読めない**

MinIO はサーバー自体の運用が増え、Render Disks は無料の Web サービスと組み合わせられません。Storj も試用後は最低料金が発生します。今回は「保存先を管理しなくてよい無料サービス」と同じ条件で比べにくいため外しました。

**[MinIO](https://www.min.io/)**(MinIO, Inc.・米)は、自前で動かす S3 互換ストレージのソフトウェアです。旧 AGPLv3 の OSS 版はメンテナンス終了と明記され、現在は AIStor Free(単一ノード)が無料です。開発環境で S3 API を再現したい人とは相性がよさそうです(本検証でもツールの動作確認に使いました)。

**[Storj](https://www.storj.io/)**(米)は、分散型の S3 互換ストレージです。30 日の試用のあとは保存 $7/TB 月、egress $7/TB で、最低課金 $5/月です。TB 級で安く、地理分散を重視する人であれば、候補の一つになりそうです。

**[Render Disks](https://render.com/docs/disks)**(Render)は、サービス 1 インスタンスにマウントするブロックストレージです。$0.25/GB 月で、無料の Web サービスには付けられず、付けると水平スケールとゼロダウンタイムデプロイができなくなります。ローカルディスク前提のコードをそのまま動かしたい人とは相性がよさそうです。

## 3. メール送信

### 今回比べた 4 つ

実装は SMTP だけで、送るのは 1 日数通です。なので「SMTP で送れて、個人が登録できること」が条件で、**無料枠の通数はどこでも余るので見ませんでした**。

- **Mailjet** は制約の少なさで当初の第一候補でした。ドメインなしで任意の宛先に送れます
- **Resend** は、API キー 1 つで送れる最短経路がどこまで短いかを見るために入れました
- **MailerSend** は配信事業者の出自です。Resend と同じ「ドメイン前提」の方式が、別の会社でどう違うかを見たかった
- **Brevo** は繰り上げです。一度は外したのですが、代わりに入れた SMTP2GO がフリーメールで登録できず、戻しました

### 4 社の顔ぶれ

**Resend**(米)は、開発者向けのトランザクションメール API です。無料枠は 3,000 通/月、100 通/日、ドメイン 3 つで、送信にはドメインの検証が必須です。超えると Pro $20/月(5 万通)になります。無料でも独自ドメインを複数登録できます。

**Mailjet**(Sinch 傘下・スウェーデン)は、マーケティングとトランザクション両方をこなす配信基盤です。無料枠は 6,000 通/月、200 通/日と 4 社で最大ですが、Mailjet のロゴが付きます。超えると Starter $9/月(8,000 通)です。送信元の検証が 4 社で最も緩いのが特徴です。

**Brevo**(旧 Sendinblue・仏)は、マーケティング中心の配信基盤に SMTP リレーが付いたものです。無料枠は 300 通/日でした(検証時の記録で、公式ページは今回取得できませんでした)。超過後の料金は未確認です。送信元 IP の登録と、登録時に企業名が要ります。

**MailerSend**(米・MailerLite と同じチーム)は、トランザクションメールの API と SMTP です。無料枠は 500 通/月、ドメイン 1 つと小さめですが、有料は Hobby $5.60/月(5,000 通)と最安です。

### 実測

計測は 2 段階になりました。**独自ドメインを持たない状態と、取得して認証したあと**です。

| 候補 | ドメインなし | ドメイン認証後 | 解決に要った作業 |
|---|---|---|---|
| Mailjet | **送れた** | 送れた(4 秒) | なし |
| **Resend** | 自分宛てにしか送れない | 送れた(4 秒) | DKIM の登録 |
| MailerSend | `450 domain must be verified` | 送れた(6 秒) | SPF と DKIM の登録 |
| Brevo | `525 Unauthorized IP` | 送れた(2 秒) | **送信元 IP の登録**(ドメインでは解決しない) |

ドメインなしで送れたのは Mailjet だけでした。ドメインを認証したら 4 社とも送れて、迷惑メールにも入りませんでした。

最初は関門のない Mailjet を選びました。でも **Mailjet は認証していないドメインのアドレスからでも送れてしまいます**。これは利点ではなく弱点だと考え直して、Resend に変えました。鍵が漏れたら任意の差出人で送られてしまいますし、他社なら弾かれる設定ミスに気づけないからです。

### 実際に組み込んで気づいた癖

メールは、単に SMTP の設定を入れれば終わり、とはなりませんでした。サービスごとに「どこまで確認できたら送信を許すか」がかなり違います。

Brevo では、ドメイン認証とは別に送信元 IP の登録も求められました。そのため、Cloud Run のように送信元 IP が固定されない環境とは、そのままでは組み合わせにくいと思います。

MailerSend は、ドメイン設定に不備がある場合も 450 という一時的なエラーを返しました。アプリが再試行を続ける可能性があるため、再試行回数には上限を設けたほうがよさそうです。

Resend の共有ドメインは送信先が限られていました。開発中の動作確認には使えますが、本番で送る場合は認証済みの独自ドメインが必要になりそうです。

メールサービスを選ぶときは送信数だけではなく、実行環境やドメインの有無も一緒に考える必要があると思います。


### ほかの選択肢

以下は今回の条件では比較対象に入れなかったものです。構成や重視する点が違えば、こちらのほうが候補になる場合もあると思います。

| 区分 | サービス |
|---|---|
| 登録の障壁で失格 | SMTP2GO(フリーメール不可)、SendGrid(審査で止まる報告が多い)、Amazon SES(サンドボックス解除の申請が要る) |
| 規約上、本番で使えない | Gmail SMTP、Outlook SMTP |
| 無料枠が小さい、または試用のみ | Mailgun(100 通/日)、Postmark(100 通/月)、ZeptoMail(初回 1 万通のみ) |
| 立地や条件が合わない | Scaleway(EU のみ)、Elastic Email、Loops / Plunk |

選ばなかったものの概要です。Mailgun と Elastic Email にも無料枠はありますが、選んだ4社と比べて無料で送れる通数が少ないか、今回の比較に新しい特徴を加えにくかったため外しました。

**登録の障壁で失格**

今回の条件には、個人が既存のメールアドレスで登録し、すぐ検証を始められることも含めました。独自ドメインのメールや審査、サンドボックス解除が先に必要なサービスは、送信性能を比べる段階まで進めないため外しました。

**[SMTP2GO](https://www.smtp2go.com/)**(ニュージーランド)は、SMTP リレーと API の両方を提供する配信サービスです。無料枠は 1,000 通/月でカード不要ですが、登録には独自ドメインのメールアドレスが必須です。独自ドメインのアドレスを持っていて、少量を無料で送りたい人であれば、候補の一つになりそうです。

**[Twilio SendGrid](https://sendgrid.com/)**(Twilio・米)は、SMTP と Web API の両方を提供する大手です。無料は「100 通/日を 60 日間」の試用のみで、有料は $19.95/月からです。将来月数万通へ伸ばす予定があり、有料前提で実績のある大手を使いたい人とは相性がよさそうです。

**[Amazon SES](https://aws.amazon.com/ses/)**(AWS・米)は、API と SMTP の両方を持つ従量課金の配信サービスです。通数の恒久無料枠はなく、新規アカウントのクレジットを使い、以降は $0.10/1,000 通です。サンドボックス解除の申請が要ります。すでに AWS を使っていて、通数単価を最安にしたい人であれば、候補の一つになりそうです。

**規約上、本番で使いにくい**

どちらも少量の通知には使えますが、アプリ専用の配信基盤ではありません。送信停止や認証方式の変更がアプリのメール機能へ直接影響するため、本番候補には入れませんでした。

**[Gmail の SMTP](https://support.google.com/a/answer/176600)**(Google・米)は、メールサービス付属の SMTP です。個人 Gmail は 500 通/日、Workspace は 2,000 通/日で、アプリからは 2 段階認証とアプリパスワードで送ります。ポリシーはアプリからの送信を明示的に禁じてはいませんが、上限に達すると最大 24 時間送信停止になり、差出人が個人のアドレスに固定されます。自分宛ての通知などごく少量の用途で使いやすそうです。

**[Microsoft 365 / Outlook.com の SMTP](https://learn.microsoft.com/exchange/mail-flow-best-practices/how-to-set-up-a-multifunction-device-or-application-to-send-email-using-microsoft-365-or-office-365)**(Microsoft・米)は、メールボックス付属の SMTP です。Microsoft 365 は有料ライセンスが必要で 1 万宛先/日、公式は「一括送信には適さない」として外部向けは別サービスを推奨しています。基本認証の SMTP AUTH は廃止予定です。すでに Microsoft 365 を契約している組織の社内通知で使いやすそうです。

**無料枠が小さい、または試用のみ**

今回のアプリが送るのは1日数通なので、Mailgunの100通/日やPostmarkの100通/月でも足ります。ただ、選んだ4社より無料枠が小さく、少ない通数のサービスをあえて比較に加える理由もなかったため外しました。ZeptoMailは最初の1万通を使い切ると有料になるため、長期間無料という条件に合いませんでした。

**[Mailgun](https://www.mailgun.com/)**(Sinch 傘下・米)は、REST API と SMTP リレーの両方を提供します。無料枠は 100 通/日で送信ドメイン 1 つ、有料は $15/月(1 万通)からです。検証時には「試用のみ」と把握していましたが、現在の料金ページには恒久の無料枠があります。1 日 100 通以内で API 中心に使いたい人とは相性がよさそうです。

**[Postmark](https://postmarkapp.com/)**(AC PM, LLC・米)は、トランザクションメール重視の配信サービスで、REST API と SMTP の両方があります。無料は 100 通/月でカード不要ですが独自ドメインは含まれず、有料は $15/月(1 万通)からです。到達性と分析を重視し、有料前提で使いたい人であれば、候補の一つになりそうです。

**[ZeptoMail](https://www.zoho.com/zeptomail/)**(Zoho・インド / 米)は、トランザクション専用の配信サービスで、SMTP と API の両方があります。最初の 1 クレジット(1 万通)は無料ですが、ドメインの DNS 認証と 2 営業日の審査が要ります。独自ドメインがあり、審査を待てて、少量を長く無料で送りたい人とは相性がよさそうです。

**立地や条件が合わない**

Scaleway は利用地域、Elastic Email は到達率に関する評価、Loops は SMTP 非対応、Plunk は今回求めていないマーケティング機能まで含む点から4社に入れませんでした。いずれも用途が合えば選択肢になると思います。

**[Scaleway Transactional Email](https://www.scaleway.com/en/transactional-email-tem/)**(Scaleway・仏)は、欧州クラウドのトランザクションメールです。300 通が無料で以降 0.25 ユーロ/1,000 通ですが、支払い方法の登録とドメイン設定が必要です。EU 内にデータを置きたい人であれば、候補の一つになりそうです。

**[Elastic Email](https://elasticemail.com/)**(Elastic Email Inc.)は、API と SMTP リレーの両方を提供します。無料枠は 3,000 通/月・100 通/日でカード不要、有料は $19/月からです。無料枠は今回の用途に十分ですが、到達率について評価が分かれており、4社へ絞る段階で外しました。

**[Loops](https://loops.so/)**(Astrodon・米)は、SaaS 向けのマーケティング + トランザクションメールで、送信は API のみで SMTP はありません。無料は直近 30 日で 4,000 通まででカード不要です。ニュースレターとトランザクションを 1 つの管理画面でまとめたい SaaS とは相性がよさそうです。

**[Plunk](https://www.useplunk.com/)**(EU ホスト。AGPL-3.0 でセルフホスト可)は、トランザクション・キャンペーン・自動化の一体型で、REST API と SMTP リレーの両方があります。無料は 1,000 通/月でカード不要、有料は $0.001/通で基本料なしです。自前サーバーにセルフホストしたい人、基本料を払いたくない人とは相性がよさそうです。

## 4. API

### 今回比べた 4 つ

ここは候補の入れ替えが一番多かった層です。条件は「Docker イメージをそのまま動かせること」でした。

当初の案には **[Zeabur](https://zeabur.com/)**(東京・日本語 UI)と **[Koyeb](https://www.koyeb.com/)**(東京で DB と同居できる唯一の無料 PaaS)が入っていました。ところが Zeabur は有料だと分かり、Koyeb は利用登録ができませんでした。Fly.io と Railway も無料では始められません。AWS と Azure は、個人がひとりで持つには設計が重すぎます。

そうやって残ったのがこの 4 つです。

- **Render** は手数が最少でカード不要、フロントとも同居できるので、当初の第一候補でした
- **Cloud Run** は無料枠が最大で東京に置けて、メモリも自由に設定できます。ただしカード必須で、超えると課金されます
- **Northflank** はカード不要の無料枠で、スリープせずに使えます
- **Back4App** はカード不要の定額制で、「請求リスクゼロ」の代表として入れました

途中の案では Cloud Run を 2 つの構成で測るつもりでしたが、別のサービスを 4 つ見たほうが記事として価値があるので、Back4App に差し替えました。

### 4 社の顔ぶれ

**Cloud Run**(Google・米)は、コンテナをフルマネージドで動かす基盤です。無料枠は 200 万リクエスト/月、vCPU 18 万秒、メモリ 36 万 GiB 秒ですが、**課金アカウント(カード)が必須です**。超えると従量課金で、vCPU $0.000024/秒、メモリ $0.0000025/GiB 秒です。要求がない間は 0 に縮んで処理中だけ課金されます。予算アラートは通知するだけなので、支払いを止めるには自分で自動化する必要があります。

**Render**(米)は、Git 連携中心の PaaS です。無料枠は 750 時間/月、512MB で、15 分無通信でスリープします。カードは要りません。有料は $7/月(0.5 CPU・512MB)からです。公式が「無料枠は本番に使わないこと」と明記しています。

**Back4App**(米・ブラジル拠点)は、Docker アプリを GitHub から配備する PaaS です。無料枠は 0.25 CPU、256MB、転送 100GB/月で、リージョンは US のみ、カードは要りません。有料はコンテナ単位の定額で $5/月(0.5 CPU・512MB)からです。従量ではないので請求が読めます。

**Northflank**(英)は、複数クラウドにまたがって配備できる開発基盤です。無料枠はサービス 2 つ・DB 1 つ・cron 2 つで、スリープせず、カードも要りません。有料は従量で、最安 $5.40/月(0.2 vCPU・512MB)です。自前クラウドへの配備(BYOC)にも対応しています。

### 実測

同じ本番用イメージ(distroless、31MB)を 4 社に置き、DB・写真・メールはすべて同じものを向けました。

| 候補 | 立地 | 往復 | DB あり | 写真 24MP | SMTP |
|---|---|---|---|---|---|
| **Cloud Run** | 東京 | **46ms** | 287ms | **3.5 秒で通る** | **通る** |
| Render | オレゴン | 147ms | 322ms | 502 | **塞がれている** |
| Back4App | 米国 | 193ms | 421ms | 502 | 通る |
| Northflank | US | 479ms | 864ms | 503 | 通る |

**今回の構成では Cloud Run が最もバランスよく動きました。**

東京リージョンからの応答が速く、SMTP にも接続できました。また、無料枠で使えるメモリ量が多く、ほかの候補より余裕を持たせられます。今回の利用量であれば無料枠に収まりそうだったことも含めて、Cloud Run を選びました。

### 公開時のセキュリティ制限

API をインターネットへ公開するなら、動くか、速いか、安いかだけでは決められません。HTTPS、未認証アクセスの遮断、接続元やパスの制限、レート制限をどこまで簡単に設定できるかも比べました。

このアプリは React の SPA から API を直接呼びます。利用者の IP アドレスは固定できず、ブラウザへ共通の秘密鍵を置くこともできません。そのため、**一般利用者向けの API はアプリの JWT 認証と認可で守る**のが前提です。CORS も、ブラウザが別オリジンの応答を読み取れるかを制御する仕組みで、curl などからの直接アクセスは防ぎません。基盤の制限は、管理用パスを追加で守る、短時間の大量アクセスを抑える、API を通らない経路を閉じる、といった多層防御として評価しました。

| 候補 | 基盤だけで設定できる主な制限 | 設定しやすさ | 今回の SPA で残る対応 |
|---|---|---|---|
| **Cloud Run** | IAM による呼び出し制御、内部通信だけにする ingress、ロードバランサー経由だけにする ingress | **機能は最も多い**。ただし WAF やレート制限にはロードバランサーと Cloud Armor の追加構成が要る | 一般利用者向け API の JWT 認証。公開 URL の迂回を防ぐ設定と、必要なら Cloud Armor のルール |
| **Northflank** | IP の許可・拒否、Basic 認証、SSO、特定ヘッダー、パス単位のポリシー、project 内だけの private port | **4 社で最も画面から追加制限を付けやすい** | 一般利用者向け API の JWT 認証。IP を固定できない利用者向けパスはアプリ側でレート制限 |
| **Render** | 自動 TLS、自動 DDoS 対策、インターネットから到達できない Private Service | **最低限は自動**。公開 Web Service のパス・IP・回数の制限はアプリ側が中心 | JWT 認証、ログインや重い API のレート制限、必要なら `X-Forwarded-For` を使った遮断 |
| **Back4App** | カスタムドメインの SSL、環境変数。Containers の公式資料ではパス・IP・回数を制限する機能を確認できなかった | **アプリ側の実装が最も多い** | JWT 認証、レート制限、アクセスログ。必要なら Cloudflare などを前段に置く |

この軸だけなら、組み込みの制限をすぐ足せる Northflank が扱いやすく、細かく構成できる Cloud Run が最も強力です。Render は TLS と DDoS 対策を意識せず始められますが、アプリらしいアクセスに見える攻撃は Go 側で抑える必要があります。Back4App は今回使った Containers では基盤側の選択肢を確認できず、アプリ側の責任が大きくなります。

ここは負荷をかける実測ではなく、2026 年 9 月時点の公式資料で比較しました。Cloud Run は [security overview](https://docs.cloud.google.com/run/docs/securing/security) と [ingress の制限](https://docs.cloud.google.com/run/docs/securing/ingress)、Northflank は [network security](https://northflank.com/docs/v1/application/network/networking-on-northflank) と [path-based security policies](https://northflank.com/docs/v1/application/network/create-path-based-security-policies)、Render は [Web Services](https://render.com/docs/web-services) と [DDoS protection](https://render.com/docs/ddos-protection)、Back4App は [Containers の custom domain](https://www.back4app.com/docs-containers/custom-domain) を参照しています。

### 実際に組み込んで気づいた癖

API の 4 社は、同じ Docker イメージを置けば同じように動くと思っていました。実際には、リポジトリの見方やスリープ時の扱いにそれぞれ癖があります。

Render では、monorepo のどこを起点にするかを Root Directory で指定しました。リージョンはあとから変更できず、今回の環境では SMTP にも接続できませんでした。この 2 点は作り始める前に確認したほうがよさそうです。

Northflank の無料枠で選べたリージョンは US だけでした。また、画像処理のようにメモリを使う処理では、すぐに失敗するのではなく、先に応答がかなり遅くなりました。

Back4App では Dockerfile の名前を指定できず、`Dockerfile` という名前のファイルが使われました。本番用を `Dockerfile.prod` に分けている場合は、ファイルの配置を変える必要があると思います。

同じコンテナを使う場合でも、ファイルの置き方やプロセスの動かし方までは共通にならないと考えておいたほうがよいと思います。

事前調査では「SMTP を塞ぐのは Cloud Run」と考えていましたが、今回の実測では Render から接続できませんでした。**少なくとも今回確認した資料だけでは判別できず、実際に接続して確かめる必要がありました。**

## 5. フロントエンド

### 今回比べた 4 つ

フロントは `/api` を同一オリジンで叩く前提なので、「`/api/*` を外部の URL へリライトできること」が条件です。これでかなり落ちました。残った中から、**設定の書き方が違う 4 社**を選んでいます。

- **Cloudflare Workers** は、設定ではなくコードでリライトを書く唯一の方式です。帯域無制限・商用可も 4 社で唯一でした
- **Render Static** は YAML で宣言する方式で、API と同居できる当初の第一候補でした
- **Netlify** は記述量の少なさの代表です。「1 行で書ける」という評判が性能とどう関係するかを見たかった
- **Vercel** は最も普及しているので、避ける理由があるなら示す価値があると考えました

### 4 社の顔ぶれ

**Cloudflare Workers**(米・上場)は、Workers に静的ファイルを同梱して CDN 配信する仕組みです。Worker 呼び出しは 10 万回/日までですが、**静的アセットへの要求と帯域は無料・無制限**で、商用利用もできます。有料は Paid $5/月(1,000 万リクエスト込み)です。Worker を通す分(`/api/*` の転送)だけが日次上限に掛かります。

**Render Static**(米)は、Git からビルドして CDN 配信するサービスです。静的サイト自体は無料で、帯域とビルド分数がワークスペースの枠に計上されます(検証時の記録では帯域 100GB/月でした)。課金は超過分だけです。API と同じ基盤に同居できますが、CLI はなく Git 連携だけです。

**Netlify**(米)は、静的サイト・フロントエンドのホスティングです。無料枠は 300 クレジット/月で、帯域に換算すると約 15GB 相当です。使い切ると全サイトが止まります。商用利用はできます。有料は Personal $9/月(1,000 クレジット)です。2025 年 9 月にクレジット制に変わり、無料枠の帯域が大きく縮みました。

**Vercel**(米)は、フロントエンド向けのホスティングとサーバーレスです。無料枠は転送 100GB/月、100 デプロイ/日と最大級ですが、**個人・非商用のみ**で、広告や決済を含む商用は規約で禁止されています。有料は Pro $20/月です。

### 実測

同じビルド成果物(496KB)を 4 社に置き、`/api/*` を Cloud Run へ転送する設定を入れました。

| 候補 | HTML | API 転送 | 設定 | デプロイ所要 |
|---|---|---|---|---|
| **Cloudflare Workers** | 54ms | **285ms** | JS 11 行 | **約 8 秒** |
| Render Static | **40ms** | 505ms | YAML 7 行 | push 後 約 1 分 |
| Netlify | 287ms | **827ms** | TOML 9 行 | 8〜71 秒 |
| Vercel | 44ms | **148ms** | JSON 10 行 | 約 25 秒 |

参考として、API 直叩きは 288ms でした。

**HTML の速さと転送の速さは連動しません。** Render は HTML が最速なのに転送は 3 位です。静的配信の速さだけで選ぶと、API 経由で損をします。

Cloudflare だけがコードを書く方式なので減点していましたが、行数の差は 4 行でした。しかも転送は最速です。**「コードを書く手間」は減点になりませんでした。**

### 実際に組み込んで気づいた癖

フロントエンドは静的ファイルを置くだけなので、いちばん素直に進むと思っていました。ところが、API 転送や OAuth まで含めると、各社のルーティングの考え方が効いてきます。

Cloudflare Workers では、静的アセットの配信が Worker より先に処理されました。API や OAuth callback を Worker に通す場合は、`run_worker_first` が必要になると思います。また、OAuth の 302 をそのままブラウザへ返すため、Worker 側の `fetch` には `redirect: "manual"` を指定しました。

Render Static Site では、API の転送に Redirect ではなく Rewrite を使いました。Redirect にするとブラウザから見える接続先も変わるため、CORS の影響を受けると考えられます。

Vercel は、デプロイの仕方によって URL が非公開になったり、デプロイのたびに変わったりしました。OAuth callback の登録先には、固定された Production URL を使うのがよさそうです。

静的サイトを公開するだけであれば大きな違いはありませんが、API や OAuth まで含める場合はルーティングの設定も比較したほうがよいと思います。


### ほかの選択肢

以下は今回の条件では比較対象に入れなかったものです。構成や重視する点が違えば、こちらのほうが候補になる場合もあると思います。

| 区分 | サービス |
|---|---|
| `/api` のリライトができない | GitHub Pages、Surge、GitLab / Codeberg Pages、Azure Static Web Apps |
| 条件付きで今回の構成が成立する | Firebase Hosting(転送先が Cloud Run の場合) |
| 無料枠がない、期限付き、または構成が重い | S3 + CloudFront、Amplify、Bunny、DigitalOcean App Platform(帯域 1GB/月) |
| 静的配信にコンテナは過剰 | Fly.io / Railway に nginx、Koyeb / Zeabur |
| 目的が違う | Coolify / Dokploy(セルフホスト)、IPFS |

選ばなかったものの概要です。リライトができないものでも、API を CORS で別ドメインから直接叩く構成なら使えます。

**外部 URL へのリライトができない**

今回のフロントエンドは `/api/*` を別の API 基盤へ転送する構成です。静的ファイルは配信できても外部 URL へリライトできないサービスは、同じ構成のまま比較できないため外しました。

**[GitHub Pages](https://pages.github.com/)**(GitHub・米)は、リポジトリから静的サイトを公開するホスティングです。リライト機能はなく、静的配信だけです。無料でサイト 1GB、帯域 100GB/月のソフト上限があり、EC や SaaS の商用ホスティングは禁止されています。OSS のドキュメントやポートフォリオで使いやすそうです。

**条件付きで今回の構成が成立する**

**[Firebase Hosting](https://firebase.google.com/docs/hosting)**(Google・米)は、CDN 付きの静的 / SPA ホスティングです。rewrites の宛先はローカルファイル・Cloud Functions・Cloud Run に限られます。Spark は保存 10GB、転送 360MB/日でカード不要です。最終的に API は Cloud Run を選んだため、`/api/**` を同一オリジンで rewrite でき、今回の構成でも成立します。任意の外部 API へ転送できる4社を先に選んだため検証対象から外れていましたが、最終構成を基準にするなら候補へ入れるべきでした。

**外部 URL へのリライトができない（続き）**

**[Surge.sh](https://surge.sh/)**(Chloi Inc.)は、CLI 1 コマンドで公開する静的ホスティングです。外部へのプロキシはドキュメントに記載がなく確認できませんでした。無料プランは公開無制限・カスタムドメイン可で、Professional は $30/月です。とにかく速く試作を公開したい人であれば、候補の一つになりそうです。

**[GitLab Pages](https://docs.gitlab.com/user/project/pages/)**(GitLab・米)は、GitLab の CI/CD から静的サイトを公開する機能です。`_redirects` で内部パスへの 200 リライトはできますが、外部ドメインは 301/302 だけです。Free はカード不要でコンピュート 400 分/月です。すでに GitLab で CI を回しているチームなら候補に入りそうです。

**[Codeberg Pages](https://codeberg.page/)**(Codeberg e.V.・独・非営利)は、FLOSS 向けの無料 Git ホスティングに付属する静的サイト公開です。外部 URL への 200 は「no external URLs」と明記されています。寄付で運営され完全無料ですが、掲載できるのは FLOSS ライセンスのプロジェクトだけです。OSS で EU 拠点の非営利インフラを使いたい人とは相性がよさそうです。

**[Azure Static Web Apps](https://azure.microsoft.com/products/app-service/static)**(Microsoft・米)は、GitHub 連携の静的ホスティング + Functions 連携です。rewrite の宛先はアプリ内の相対パスに限られます。Free は帯域 100GB/月でアプリ 10 個までですが、「個人・趣味向け」とされています。API を Azure Functions や Container Apps に置ける人であれば、候補の一つになりそうです。

**[DigitalOcean App Platform(Static Sites)](https://docs.digitalocean.com/products/app-platform/how-to/manage-static-sites/)**(DigitalOcean・米)は、Git 連携 PaaS の静的サイト部品です。ルーティングは同じアプリ内のコンポーネントか redirect だけです。静的サイトだけのアプリを 3 個まで無料で、各 1GiB/月の転送です。API も同じ App Platform に置き、同一アプリ内でルーティングしたい人とは相性がよさそうです。

**リライトはできるが、無料枠がないか期限付き**

機能上は今回の構成を実現できます。Amplify と Bunny は一定期間後に有料になり、DigitalOcean は無料転送量が小さいため外しました。S3 + CloudFront は無料枠でも成立しますが、S3、CloudFront、ルーティングを別々に設定する必要があり、今回選んだ Cloudflare Workers より構成が重くなるため4社には入れませんでした。

**[Amazon S3 + CloudFront](https://aws.amazon.com/cloudfront/)**(AWS・米)は、S3 の静的ファイルを CloudFront で配信する構成です。CloudFront は任意の HTTP(S) サーバーをオリジンにでき、パス別に振り分けられるので、`/api/*` のプロキシはできます。CloudFront の Free プランは転送 100GB・S3 5GB で超過課金なしですが、AWS アカウント自体に決済手段の登録が要ります。AWS に慣れていて、IaC で CDN・WAF まで自分で組みたい人であれば、候補の一つになりそうです。

**[AWS Amplify Hosting](https://aws.amazon.com/amplify/hosting/)**(AWS・米)は、Git 連携のフルマネージド静的 / SSR ホスティングです。「Reverse proxy rewrite」で外部 URL への 200 リライトができます。無料枠は 12 か月限定で、以降は配信 $0.15/GB です。12 か月後の従量課金を許容できれば、今回の条件も満たします。

**[bunny.net](https://bunny.net/)**(BunnyWay・欧州)は、低価格 CDN とオブジェクトストレージです。Edge Rules の「Change Origin URL」でパス単位に別オリジンへ流せます。恒久の無料枠はなく 14 日の試用で、以降は月最低 $1、アジア向け $0.03/GB です。月数ドルの実費でよく、CDN の設定を自分で握りたい人とは相性がよさそうです。

**セルフホスト・目的が違う**

Coolify と Dokploy はホスティング先ではなく、自分のサーバーを管理するための基盤です。静的サイトの配信先を比較する今回の範囲から外れ、VPS の運用費と管理も増えるため選びませんでした。

**[Coolify](https://coolify.io/)**(coolLabs・ハンガリー。Apache-2.0)は、自分のサーバーに置く Vercel / Heroku 代替の PaaS です。静的ビルドは Nginx で配信し、プロキシは Traefik なので、外部 URL へのリライトは自前設定で可能です。セルフホストは全機能無料、Cloud は $5/月です。VPS を 1 台持っていて、フロントもプロキシも自分で管理したい人であれば、候補の一つになりそうです。

**[Dokploy](https://dokploy.com/)**(Dokploy Technology。Apache-2.0)は、Traefik を統合したセルフホスト PaaS です。Static ビルドと Traefik の直接編集ができ、外部 URL へのルーティングは自前設定で可能です。セルフホストは無料、Cloud は $4.50/月からです。Coolify と同様に VPS 運用派で、Traefik を直接触るのに抵抗がない人とは相性がよさそうです。

**[Fleek](https://fleek.xyz/)**(運営は確認できず)は、IPFS 系の分散ホスティングでしたが、現在は公式サイトが新製品の予告ページのみで、料金もドキュメントも見られません。現時点では選択肢として評価できません。

## 選んだ構成

速度、必要な機能、無料枠のバランスを見て選びました。

| 層 | 採用 | 選ばなかった最有力と、その理由 |
|---|---|---|
| API | Cloud Run(東京、1GB) | 応答が速く、SMTP が通り、無料枠でもメモリに余裕を持たせられました |
| DB | Neon | Supabase は東京で作り直せば速いはずですが、1 週間で停止します |
| 写真 | Cloudflare R2 | Tigris は 3 倍速いのですが、転送量が従量です |
| メール | Resend | Mailjet は関門がなさすぎて、鍵の漏洩と設定ミスに弱いです |
| フロント | Cloudflare Workers | Vercel は転送最速ですが、非商用限定・既定で非公開・Bot 対策の 3 つが重いです |

この構成で公開しているアプリは、[BurgerStack](https://burger-stack.com/)から確認できます。

カード登録なしで完結する構成は組めませんでした。Cloud Run と R2 はカードが要ります。予算アラートは支払いを止めないので、上限を超えたときに自分で止める覚悟は要ります。

## まとめ

**今回の比較では、料金表だけでは判断しにくい点がいくつもありました。**

| 候補 | 料金表に書いてあること | 今回の構成で確認した点 |
|---|---|---|
| Render(API) | 750 時間/月、カード不要 | SMTP が塞がれている。リージョンを変更できない |
| Northflank | サービス 2 つ、常時起動 | 無料枠は US のみ |
| Back4App | 600 時間/月 | 一時 URL が期限切れになる |
| Cloud Run | 200 万リクエスト/月 | 予算アラートは支払いを止めない |
| SMTP2GO | 1,000 通/月 | フリーメールで登録できない |
| Brevo | 300 通/日 | 送信元 IP の登録が要る |
| Vercel | 帯域 100GB/月 | 非商用限定、既定で非公開、Bot 対策で遮断される |
| Supabase(DB) | 500MB、東京あり | Direct connection が IPv6 専用 |
| Backblaze B2 | 10GB、カード不要 | マスターキーが S3 API で使えない |

机上の予想は何度も外れました。SMTP を塞ぐのは Cloud Run だと思っていたら Render でしたし、コードを書く手間があると減点した Cloudflare が転送最速でした。

**今回のようにアプリ固有の要件がある場合は、小さくても実際にデプロイして確かめると、料金表だけでは見えない違いを判断できます。**
