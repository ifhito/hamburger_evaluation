## はじめに

個人開発のハンバーガーレビューアプリ(Go + React)を無料枠で動かすために、DB・写真ストレージ・メール・API・フロントの 5 層で 4 候補ずつ、計 20 サービスを実際にデプロイして比べました。

結論はこうです。

| 層 | 採用 | 決め手 |
|---|---|---|
| API | Cloud Run(東京) | 写真処理・SMTP・常駐ワーカーが全部動いた唯一の候補 |
| DB | Neon | 最も近く、マイグレーションが無改変で通った |
| 写真 | Cloudflare R2 | 転送量が無料・無制限 |
| メール | Resend | 送信元の検証がちょうどよい厳しさ |
| フロント | Cloudflare Workers | API への転送が速く、帯域が無制限 |

一番の学びは、**無料枠の落とし穴は料金表に書いていない**ことでした。20 候補すべてで、実際に使うまで分からない制約に当たっています。

この記事は、各サービスの「スペック」「実測」「設定のしやすさとハマり」を層ごとに 1 枚の表で見られるようにした短縮版です。細かい数字と計測手順は省いています。

## 比べ方

ミニマムなサンプルではなく、本物のアプリをそのまま置いて測りました。サンプルでは写真処理のメモリや SMTP のポートのような、実際に効く制約が見えないからです。

- **アプリ**: Go 1.27(標準 `net/http` + sqlc + pgx)と React 19 の SPA。DB は PostgreSQL で主キーは UUID。レビューの写真はサーバー側で長辺 1600px に縮小。サインアップの確認メールを SMTP で送る
- **候補の条件**: 無料で始められて、個人が一人で登録から運用までたどり着けること。営業への問い合わせ、自前サーバーの運用、IAM の設計が要るものは外した
- **計測**: 日本の自宅回線から。数字は p50(中央値)。レイテンシは接続確立を含む
- **順序**: DB → 写真 → メール → API → フロント。後ろの層は、前の層で選んだものに向けて測った

候補は各層で 10〜15 を見て 4 つに絞りました。絞り方は「同じ軸を代表するものを 2 つ入れない」です。例えば DB なら「休む DB」「東京がある」「API と同居」「ニッチ」の 4 軸で 1 社ずつ。外した理由はだいたい 4 種類で、技術的に使えない、別の道具に乗り換えることになる、無料で始められない、個人には運用が重い、のどれかです。層ごとの経緯は「なぜこの 4 つか」に書いています。

各層の表は「無料枠のスペック」「実測」「設定のしやすさとハマり」の 3 列です。採用したものを太字にしています。

### なぜこの 4 つか

アプリが pgx + sqlc で UUID 主キー・外部キー 6 本・`FOR UPDATE SKIP LOCKED` を使うので、まず「Postgres のワイヤプロトコルで、これらがそのまま動く」が条件です。その上で、違う軸を代表する 4 社を選びました。

- **Neon**: 「休む DB」の代表。コンピュート時間で課金する方式が、個人アプリで現実的に無料で収まるか
- **Supabase**: 4 社で唯一、東京リージョンを選べる。「1 週間で停止」という特異な挙動も測る価値があった
- **Render Postgres**: API の当初の第一候補が Render だったので、「API と同じ事業者に置く」構成を測るため
- **Xata**: ニッチ枠。日本語の情報が少なく、実測に一次情報としての価値がある

外したものは、技術的に使えない(Aurora DSQL は外部キー非対応、Cloudflare D1 は Workers 内専用)、別の道具に乗り換えることになる(PlanetScale・TiDB は MySQL、Turso は SQLite)、要件に対して過剰(CockroachDB・Yugabyte の分散 SQL)、他と差がつかない(Aiven・Prisma Postgres・Nile)、無料で始められない(Fly Postgres)、運用が重い(Oracle Cloud の VM に自前構築)のどれかです。Koyeb Postgres は当初入れていましたが、利用登録ができず Render に差し替えました。

| 候補 | 無料枠のスペック | 実測(往復 / 書き込みトランザクション) | 設定のしやすさとハマり |
|---|---|---|---|
| **Neon** | 0.5GB、コンピュート 190 時間/月、カード不要。自動休止して 1 秒未満で復帰 | シンガポール。**86ms / 348ms** | 接続 URL を入れるだけ。pooler 経由だとマイグレーションが「unnamed prepared statement」で落ちることがある。直結の URL を使う |
| Supabase | 500MB、カード不要。**1 週間触らないと停止** | ムンバイ(新規なら東京も選べる)。131ms / 527ms | Direct connection が **IPv6 専用**で、Docker から名前解決できない。psql では繋がるので気づきにくい。Session pooler を使う |
| Render Postgres | 1GB、カード不要。**30 日で失効** | オレゴン。146ms / 588ms | ハマりなし。ただし無料枠はオレゴン固定 |
| Xata | あり(条件は変わりやすい)、カード不要 | 米国東部。177ms / 714ms | ハマりなし。遠い |

主キーでの 1 件取得も、3 テーブルを結合した 20 件も、`SELECT 1` と区別がつきませんでした。この規模では DB の処理時間がネットワークの往復に埋もれます。

書き込みトランザクションだけが 4 倍遅いのは、BEGIN から COMMIT までで 4 往復しているからです。4 社とも倍率が 4.02〜4.04 で一致したので、時間を決めているのは DB の性能ではなく往復回数です。CTE で 1 文にまとめれば 1 往復になります。

### なぜこの 4 つか

アダプタが使うのは S3 互換の `PutObject` と `DeleteObject` だけで、公開 URL からそのまま配信します。だから「S3 互換で、公開配信ができる」が条件です。写真は書き 1 回・読み多数なので、転送量の課金を一番重く見ました。

- **Cloudflare R2**: 費用の軸。転送量無料という一点で第一候補
- **Supabase Storage**: 統合の軸。DB を Supabase にする場合の一体構成を測るため
- **Tigris**: 配置戦略の軸。グローバル分散が速さにどう出るか、R2 の対抗馬として
- **Backblaze B2**: 実績の軸。R2 登場前の定番で、4 社で唯一カード登録が不要

外したものは、S3 互換でなくコードを書き足すことになる(Vercel Blob・Cloudflare Images・Bunny)、変換特化で用途が違う(ImageKit・Cloudinary。このアプリは保存時に縮小済み)、無料枠がないか期限付き(AWS S3・GCS・Azure・Wasabi・DigitalOcean Spaces)、運用が重い(MinIO のセルフホスト・Storj・Render Disk)のどれかです。

| 候補 | 無料枠のスペック | 実測(PUT / GET / GET のばらつき) | 設定のしやすさとハマり |
|---|---|---|---|
| **Cloudflare R2** | 10GB、1,000 万 read/月。**転送量が無料・無制限**。カード要 | 160ms / 81ms / 中 | バケット名の指定違いで `NoSuchBucket`。公開 URL の `*.r2.dev` は開発用で、本番は独自ドメインが要る |
| Tigris | 5GB。Fly.io の外への転送は従量 | **89ms / 26ms / 小**。全項目で最速 | ハマりなし。アクセスされた地域にデータを寄せる仕組みが効いている |
| Supabase Storage | 1GB、転送 5GB/月 | 433ms / 39ms / **大**(最大 780ms) | ハマりなし。書き込みが読み取りの 11 倍遅いが、写真は書き 1 回・読み多数なので実用上は問題ない |

Tigris の GET 26ms は R2 の 3 分の 1 でした。それでも R2 を選んだのは、写真は何度も読まれるので転送量の課金が長期的に効くからです。

B2 は遅いけれど最も安定していて、Supabase は中央値が速いのに 2 割ほどの閲覧で目に見えて待たされます。平均だけ見ると誤ります。

### なぜこの 4 つか

実装は SMTP だけで、送るのは 1 日数通です。だから「SMTP で送れて、個人が登録できる」が条件で、通数は見ませんでした。

- **Mailjet**: 制約の少なさの軸。ドメインなしで任意の宛先に送れる、当初の第一候補
- **Resend**: 設定の軽さの軸。API キー 1 つで送れる最短経路がどこまで短いか
- **Brevo**: 一度は「代表する軸がない」として外しましたが、代わりに入れた SMTP2GO がフリーメールで登録できず、繰り上げで戻しました
- **MailerSend**: 配信事業者の出自の軸。Resend と同じ「ドメイン前提」の方式が別の事業者でどう違うか

外したものは、登録の障壁で失格(SMTP2GO はフリーメール不可、SendGrid は審査で止まる報告が多い、Amazon SES はサンドボックス解除の申請が要る)、規約上本番で使えない(Gmail・Outlook の SMTP)、無料枠がないか試用のみ(Mailgun・Postmark・ZeptoMail)、立地が合わない(Scaleway は EU のみ)のどれかです。

| 候補 | 無料枠のスペック | 実測(ドメインなし / ドメイン認証後) | 設定のしやすさとハマり |
|---|---|---|---|
| **Resend** | 3,000 通/月 | 自分宛てにしか送れない(`+` エイリアスも拒否) / **送れた**。4 秒で受信箱へ | DKIM を 1 つ登録するだけ。SPF はなくても通った |
| Mailjet | 6,000 通/月、200 通/日 | **送れた** / 送れた。4 秒 | 関門なし。ただし**未認証のドメインのアドレスからでも送れてしまう**。鍵が漏れたときに任意の差出人で送られる |
| Brevo | 300 通/日 | `525 Unauthorized IP` / 送れた。2 秒 | **ドメイン認証では解決しない**。送信元 IP の登録が要り、IP が固定されない Cloud Run と相性が悪い。登録に企業名も必要 |
| MailerSend | 500 通/月 | `450 domain must be verified` / 送れた。6 秒 | SPF と DKIM の両方が要る。4 社で最も厳しい。設定不備に 450(一時的エラー)を返すので、アプリが再試行を続けてしまう |

独自ドメインを持たない段階で送れたのは Mailjet だけでした。ドメインを取って認証したら 4 社とも送れ、迷惑メールには振り分けられませんでした。

最初は関門がない Mailjet を選んだのですが、「通ってしまう」のは弱点だと評価し直して Resend に変えました。他社なら弾かれる状態でも送れるので、設定の不備に気づけないからです。

なお SMTP2GO はフリーメールでの登録を拒否します(`Please use an email at your own domain to sign up`)。料金表では見えない、入口で失格する例です。

- **Cloud Run**: 無料枠が最大で東京に置け、メモリを自由に設定できる。ただしカード必須で超過すると課金
- **Northflank**: 無料枠でも常時起動。常駐ワーカーが動くかを見るため
- **Back4App**: カード不要の定額制。「請求リスクゼロ」の代表として

当初の案には Zeabur(東京・日本語 UI)と Koyeb(東京で DB と同居できる唯一の無料 PaaS)が入っていましたが、Zeabur は有料だと分かり、Koyeb は利用登録ができませんでした。Fly.io は新規向けの無料枠が廃止され、Railway は初回トライアルのみでした。AWS App Runner・ECS・Azure Container Apps は権限とネットワークの設計が要るので、Azure の代わりに Northflank を入れました。途中の案では Cloud Run を 2 つの構成で測るつもりでしたが、別のサービスを 4 つ見たほうが記事として価値があるので Back4App に差し替えました。

| 候補 | 無料枠のスペック | 実測(往復 / DB あり / 写真 24MP / SMTP) | 設定のしやすさとハマり |
|---|---|---|---|
| **Cloud Run** | 200 万リクエスト/月、メモリ 1GB。**超過で課金、カード必須** | 東京。**46ms / 287ms / 3.5 秒で通る / 通る** | リージョンを東京にできた唯一の候補。予算アラートは通知するだけで支払いを止めない。要求がない間はインスタンスが 0 になり、常駐ワーカーも止まる |
| Render | 750 時間/月、512MB、カード不要。上限で止まるだけ | オレゴン。147ms / 322ms / **502** / **塞がれている** | `render.yaml` にシンガポールと書いてもオレゴンになり、後から変えられない。Root Directory を `backend-go` にしないと `go.sum not found`。SMTP が塞がれているのでサインアップが完結しない |
| Back4App | 600 時間/月、256MB、カード不要 | 米国。193ms / 421ms / 502 / 通る | Dockerfile の名前を選べない(既定の `Dockerfile` だけ)。**一時 URL が期限切れになり**、継続運用できない |
| Northflank | Sandbox でサービス 2 つ、256MB、常時起動 | US。479ms / 864ms / 503 / 通る | **無料枠は US しか選べない**(Asia は有料)。384 万画素で 33 秒かかり、落ちる前に極端に遅くなる |

写真の行は、API を直接叩いて原寸(2,400 万画素)を送った結果です。ブラウザ経由なら送信前に 1600px に縮小されるので、無料プランでも通ります。ただし縮小に失敗すると原寸が飛ぶので、守りとしては弱いです。

個人開発で一番怖いのは事故で請求が来ることなので、最初は「上限で止まるだけの無料プラン」を高く評価していました。ところがその基準で選んだ 3 社はどれもアプリを動かせず、動いたのはカード必須で超過時に課金される Cloud Run だけでした。「請求リスクなし」と「機能が動く」は両立しませんでした。

事前調査では「SMTP を塞ぐのは Cloud Run」と書いていましたが、実測すると塞いでいたのは Render でした。ポートの遮断は事業者が明記しないことが多く、実測でしか分かりません。

## 5. フロントエンド: HTML の速さと転送の速さは連動しない

同じビルド成果物(496KB)を 4 社に置き、`/api/*` を Cloud Run へ転送する設定を入れました。静的配信の速さだけで選ぶと、API 経由で損をします。

### 顔ぶれ

| 候補 | 運営 | どんなサービスか | 無料枠 | 超えたときの料金 | 特徴 |
|---|---|---|---|---|---|
| [Cloudflare Workers](https://developers.cloudflare.com/workers/platform/pricing/) | Cloudflare, Inc.(米サンフランシスコ) | Workers に静的ファイルを同梱して CDN 配信する仕組み | Worker 呼び出し 10 万回/日。**静的アセットへの要求と帯域は無料・無制限**。ファイル 2 万個まで | Paid $5/月(1,000 万リクエスト込み、超過 $0.30/100 万) | 帯域の課金がない。Worker を通す分(`/api/*` の転送)だけが日次上限に掛かる |

### なぜこの 4 つか

フロントは `/api` を同一オリジンで叩く前提なので、「`/api/*` を外部の URL へリライトできる」が条件です。これでかなり落ちます。残った中から、設定の書き方が違う 4 社を選びました。

- **Cloudflare Workers**: 設定ではなくコードでリライトを書く唯一の方式。帯域無制限・商用可も 4 社で唯一
- **Render Static**: YAML による宣言。API と同居できる当初の第一候補
- **Netlify**: 記述量の少なさの代表。「1 行で書ける」評判が性能とどう関係するか
- **Vercel**: 最も普及している。避ける理由があるなら示す価値がある

外したものは、`/api` のリライトができない(GitHub Pages・Firebase Hosting は Cloud Functions 先限定・Surge・GitLab Pages・Azure Static Web Apps)、無料枠がないか期限付き(S3 + CloudFront・Amplify・Bunny・DigitalOcean App Platform は帯域 1GB/月)、静的配信にコンテナは過剰(Fly.io・Railway に nginx)、目的が違う(Coolify のセルフホスト・IPFS)のどれかです。

| 候補 | 無料枠のスペック | 実測(HTML / API 転送 / デプロイ所要) | 設定のしやすさとハマり |
|---|---|---|---|
| **Cloudflare Workers** | **帯域無制限・商用可**、カード不要 | 54ms / **285ms** / **約 8 秒** | 設定ではなく JS を 11 行書く。その分、**Google ログインが 2 段構えで壊れた**(ページ遷移だとアセット配信が Worker より先に働く、`fetch` が 302 を勝手に追う)。`run_worker_first` と `redirect: "manual"` の両方が要る。CLI のログインは対話必須 |
| Render Static | 帯域 100GB/月、カード不要 | **40ms** / 505ms / push 後約 1 分 | YAML 7 行。Action を Redirect にするとオリジンが変わって CORS で失敗する。Rewrite が必須。CLI はなく Git 連携のみ |
| Netlify | 300 クレジット/月(帯域は約 15GB 相当)、商用可、カード不要 | 287ms / **827ms** / 8〜71 秒 | TOML 9 行。ハマりなし。ただし転送が突出して遅く、デプロイ時間も大きく振れる |
| Vercel | 帯域 100GB/月。**Hobby は非商用限定** | 44ms / **148ms** / 約 25 秒 | JSON 10 行。**既定で非公開**(SSO に 302)、50 回のリクエストで Bot 対策に遮断、CLI で配ると本番 URL が毎回変わる。GitHub 連携は Root Directory を設定しないと失敗し続ける |

参考として API 直叩きは 288ms です。Vercel と Cloudflare の転送が直叩きより速いのは、エッジと API の間で接続が使い回されるからで、計測条件の差です。

Cloudflare だけがコードを書く方式なので減点していましたが、行数の差は 4 行でした。ただし行数では測れない責任の差があります。宣言的なリライトの 3 社はリダイレクトがそのままブラウザに渡りますが、Cloudflare は正しさを自分で担保する必要があります。

デプロイの所要時間は「コマンドが終わった」と「反映された」が別です。Render は push が 1 秒で戻り、ビルドは向こうで非同期に走ります。反映の確認は、ハッシュではなく変えた値そのものを配信物から探すのが確実でした。Vercel だけバンドルのハッシュが手元と一致しません。

## 選んだ構成

「全機能が動く」を最優先にして、その上で長期の費用と安全側に倒しました。

| 層 | 採用 | 選ばなかった最有力と、その理由 |
|---|---|---|
| API | Cloud Run(東京、1GB) | Render は写真と SMTP が動かず、サインアップが完結しない |
| DB | Neon | Supabase は東京で作り直せば速くなる見込みだが、1 週間で停止する |
| 写真 | Cloudflare R2 | Tigris は 3 倍速いが、転送量が従量 |
| メール | Resend | Mailjet は関門がなさすぎて、鍵の漏洩と設定の不備に弱い |
| フロント | Cloudflare Workers | Vercel は転送が最速だが、非商用限定・既定で非公開・Bot 対策の 3 つが重い |

カード登録なしで完結する構成は組めませんでした。Cloud Run と R2 はカードが要ります。予算アラートは支払いを止めないので、上限を超えたときに自分で止める覚悟は要ります。

残った課題は、統計の再計算ワーカーです。Cloud Run は要求がない間インスタンスが 0 になるので、誰も見ていない間はワーカーも止まります。最小インスタンスを 1 にするか、外部の cron から叩くかのどちらかになります。

## まとめ: 落とし穴は料金表に書いていない

20 候補すべてで、実際に使うまで分からない制約に当たりました。容量や通数の表を並べても、実用上の可否はそこでは決まりません。

| 候補 | 料金表に書いてあること | 実際に当たった制約 |
|---|---|---|
| Render(API) | 750 時間/月、カード不要 | SMTP が塞がれている。リージョン変更不可 |
| Northflank | Sandbox 2 サービス、常時起動 | 無料枠は US のみ |
| Back4App | 600 時間/月 | 一時 URL が期限切れになる |
| Cloud Run | 200 万リクエスト/月 | 予算アラートは支払いを止めない |
| SMTP2GO | 1,000 通/月 | フリーメールで登録できない |
| Brevo | 300 通/日 | 送信元 IP の登録が要る |
| Vercel | 帯域 100GB/月 | 非商用限定、既定で非公開、Bot 対策で遮断 |
| Supabase(DB) | 500MB、東京あり | Direct connection が IPv6 専用 |
| Backblaze B2 | 10GB、カード不要 | マスターキーが S3 API で使えない |

机上の予想は何度も外れました。SMTP を塞ぐのは Cloud Run だと思っていたら Render でしたし、コードを書く手間があると減点した Cloudflare が転送最速でした。デプロイ先は、実際にデプロイしてみないと分かりません。
