## 先に結論

個人開発のハンバーガーレビューアプリ(Go + React)を、できるだけ無料で動かしたい。そう思って調べ始めたら候補が多すぎたので、**DB・写真ストレージ・メール・API・フロントの 5 層で 4 つずつ、計 20 サービスに実際にデプロイして比べました**。

最終的にこうなりました。

| 層 | 採用 | 決め手 |
|---|---|---|
| API | **Cloud Run**(東京) | 写真処理・SMTP・常駐ワーカーが全部動いた唯一の候補 |
| DB | **Neon** | 日本から一番近く、マイグレーションが無改変で通った |
| 写真 | **Cloudflare R2** | 転送量が無料・無制限 |
| メール | **Resend** | 送信元の検証がちょうどよい厳しさ |
| フロント | **Cloudflare Workers** | API への転送が速く、帯域が無制限 |

一番の学びは、**無料枠の落とし穴は料金表に書いていない**ということです。20 サービスすべてで、実際に使ってみるまで分からない制約に当たりました。

## 何をどう比べたか

**本物のアプリをそのまま置いて測りました。** ミニマムなサンプルだと、写真処理で使うメモリや SMTP のポートのような、実際に効いてくる制約が見えないからです。

- **アプリ**: Go 1.27(標準 `net/http` + sqlc + pgx)と React 19 の SPA。DB は PostgreSQL で主キーは UUID。レビューの写真はサーバー側で長辺 1600px に縮小。サインアップの確認メールを SMTP で送る
- **候補の条件**: 無料で始められて、個人が一人で登録から運用までたどり着けること。営業への問い合わせ、自前サーバーの運用、IAM の設計が要るものは外した
- **計測**: 日本の自宅回線から。数字は p50(中央値)
- **順序**: DB → 写真 → メール → API → フロント。後ろの層は、前の層で選んだものに向けて測った

候補は延べ 80 ほど見て、層ごとに 4 つに絞りました。絞り方は**「同じ軸を代表するものを 2 つ入れない」**です。各層の最初に、候補に挙がったもの全部と、なぜその 4 つにしたかを書いています。

## 1. データベース

### 候補に挙がったもの(19)

| 区分 | サービス |
|---|---|
| **選んだ 4 つ** | **Neon、Supabase、Render Postgres、Xata** |
| 技術的に使えない | Aurora DSQL(外部キー非対応)、Cloudflare D1(Workers 内専用)、MongoDB Atlas / DynamoDB(リレーショナルでない) |
| 別の道具に乗り換えることになる | PlanetScale、TiDB Serverless(MySQL)、Turso、SQLite + Litestream |
| 要件に対して過剰 | CockroachDB、YugabyteDB(分散 SQL) |
| 他と差がつかない | Aiven、Prisma Postgres、Nile |
| 無料で始められない | Fly Postgres |
| 個人には運用が重い | Oracle Cloud の VM に自前構築 |
| 登録できなかった | Koyeb Postgres |

### なぜこの 4 つか

このアプリは pgx + sqlc で、UUID 主キー・外部キー 6 本・`FOR UPDATE SKIP LOCKED` を使います。なので「Postgres のワイヤプロトコルで、これらがそのまま動く」が最低条件。ここで MySQL 系と SQLite 系と NoSQL が落ちます。

残った Postgres 勢から、**違う軸を代表する 4 つ**を選びました。

- **Neon** は「休む DB」の代表。使った時間で課金する方式が、個人アプリで本当に無料で収まるのか
- **Supabase** は 4 社で唯一、東京リージョンがある。「1 週間触らないと止まる」という変わった挙動も測りたかった
- **Render Postgres** は「API と同じ事業者に置く」構成のため。API の当初の第一候補が Render でした
- **Xata** はニッチ枠。日本語の情報がほぼなく、測ること自体に価値がある

### 4 社の顔ぶれ

**Neon**(Databricks 傘下・米)
- 無料枠: 保存 0.5GB、コンピュート 100 CU 時間/月、カード不要
- 超えたら: 従量。$0.106/CU 時間、保存 $0.35/GB 月。月額の最低なし
- 特徴: 5 分触らないと自動で休止(無料枠では無効化できない)。DB を Git のようにブランチできる

**Supabase**(シンガポール)
- 無料枠: DB 500MB、プロジェクト 2 つまで、カード不要。**1 週間触らないと一時停止**
- 超えたら: Pro $25/月(DB 8GB 込み)
- 特徴: DB・認証・ストレージを 1 つのプロジェクトで提供する「Firebase 代替」。東京リージョンあり

**Render Postgres**(米)
- 無料枠: 1GB、256MB RAM。**作成から 30 日で失効**
- 超えたら: $6/月(256MB)〜
- 特徴: 同じ Render の Web サービスと私設ネットワークでつながる。常用するなら有料前提

**Xata**(米)
- 無料枠: 現在の料金ページには常設の無料枠がなく、14 日の試用のみ。検証した時点では無料で使えた
- 超えたら: コンピュート $0.012/時〜、保存 $0.28/GB 月
- 特徴: ブランチが中核。差分だけ課金される Copy-on-Write、ゼロダウンタイムのスキーマ変更

### 実測

日本から pgx で直接叩いて、各 200 回。

| 候補 | リージョン | 往復(SELECT 1) | 書き込みトランザクション |
|---|---|---|---|
| **Neon** | シンガポール | **86ms** | **348ms** |
| Supabase | ムンバイ | 131ms | 527ms |
| Render | オレゴン | 146ms | 588ms |
| Xata | 米国東部 | 177ms | 714ms |

**差は距離だけでした。** 4 社ともマイグレーション 12 本が無改変で通り、互換性では差がつきません。

意外だったのは、主キーでの 1 件取得も、3 テーブルを結合した 20 件も、`SELECT 1` と区別がつかなかったこと。この規模だと DB の処理時間はネットワークの往復に完全に埋もれます。

書き込みだけが 4 倍遅いのは、BEGIN から COMMIT まで 4 往復しているからです。4 社とも倍率がぴったり 4.02〜4.04 で揃いました。時間を決めているのは DB の性能ではなく往復回数。CTE で 1 文にまとめれば 1 往復にできます。

### ハマったこと

- **Supabase**: Direct connection が IPv6 専用で、Docker から名前解決できない。psql では繋がるので「マイグレーションが失敗してテーブルがない」という分かりにくい形で出る。Session pooler を使えば通る
- **Neon**: pooler 経由だとマイグレーションが `unnamed prepared statement does not exist` で落ちることがある。直結の URL を使う
- Render と Xata はハマりなし。ただし Supabase は新規なら東京で作れるので、そうすれば順位は変わるはずです

## 2. 写真ストレージ

### 候補に挙がったもの(19)

| 区分 | サービス |
|---|---|
| **選んだ 4 つ** | **Cloudflare R2、Tigris、Supabase Storage、Backblaze B2** |
| S3 互換でない(コードを書き足す) | Vercel Blob、Cloudflare Images、Bunny Storage |
| 用途が違う(画像変換に特化) | ImageKit、Cloudinary、Uploadcare / Uploadthing |
| 無料枠がない、または期限付き | AWS S3、Google Cloud Storage、Azure Blob、Wasabi、DigitalOcean Spaces、Hetzner |
| 運用が重い、条件が読めない | MinIO(セルフホスト)、Storj、Render Disk |

### なぜこの 4 つか

アプリのアダプタが使うのは S3 互換の `PutObject` と `DeleteObject` だけで、公開 URL からそのまま配信します。なので「S3 互換で、公開配信できる」が条件。このアプリは保存時に縮小まで済ませているので、変換特化のサービスは出番がありません。

写真は 1 回書いて何度も読まれるので、**転送量の課金を一番重く見ました**。

- **R2** は費用の軸。転送量無料という一点で第一候補
- **Supabase Storage** は統合の軸。DB を Supabase にするなら一体で使えるか
- **Tigris** は配置の軸。アクセス元に寄せる分散型が、速さにどう出るか
- **B2** は実績の軸。R2 登場前の定番で、4 社で唯一カード不要

### 4 社の顔ぶれ

**Cloudflare R2**(米・上場)
- 無料枠: 保存 10GB、書き 100 万回/月、読み 1,000 万回/月。転送無料。カード要
- 超えたら: 保存 $0.015/GB 月。転送はいくら読まれても $0
- 特徴: 転送量が完全に無料。これだけで選ぶ理由になる

**Tigris**(米)
- 無料枠: 保存 5GB、書き 1 万回/月、読み 10 万回/月。転送無料
- 超えたら: 保存 $0.02/GB 月
- 特徴: データがアクセス元に追従して分散する。リージョン別の課金がない

**Supabase Storage**(シンガポール)
- 無料枠: 1GB、転送 5GB/月。DB と同じく 1 週間で休止
- 超えたら: Pro $25/月(100GB 込み)、転送 $0.09/GB
- 特徴: DB・認証と同じ権限(RLS)で扱える。単価は R2 や Tigris より高い

**Backblaze B2**(米・上場)
- 無料枠: 最初の 10GB が常時無料。転送は保存量の 3 倍/月まで無料。**カード不要**
- 超えたら: 保存 $6.95/TB 月(約 $0.007/GB)
- 特徴: 保存単価が最安級。最短保存期間などの縛りがない

### 実測

300KB の JPEG を各 50 回。

| 候補 | PUT | GET | GET のばらつき |
|---|---|---|---|
| Tigris | **89ms** | **26ms** | 小 |
| Supabase Storage | 433ms | 39ms | **大**(最大 780ms) |
| **Cloudflare R2** | 160ms | 81ms | 中 |
| Backblaze B2 | 233ms | 281ms | **最小**(8.5ms) |

**速さでは Tigris が全項目で最速。** GET 26ms は R2 の 3 分の 1 です。それでも R2 を選んだのは、転送量の課金が長期的に効くから。

Supabase は中央値こそ速いのに、2 割ほどの閲覧で目に見えて待たされます。B2 は遅いけれど最も安定。**平均だけ見ると判断を誤ります。**

Region を `auto` に固定しているコードも、4 社ともそのまま通りました。エンドポイントと鍵を差し替えるだけで動きます。

### ハマったこと

- **B2**: マスターキーが S3 API で使えない。画面上部に大きく出ているアカウント ID を入れてしまい `Malformed Access Key Id`。App Keys から作り直す
- **R2**: バケット名の指定違いで `NoSuchBucket`。公開 URL の `*.r2.dev` は開発用で、本番は独自ドメインが要る
- Tigris と Supabase はハマりなし

## 3. メール送信

### 候補に挙がったもの(15)

| 区分 | サービス |
|---|---|
| **選んだ 4 つ** | **Resend、Mailjet、Brevo、MailerSend** |
| 登録の障壁で失格 | SMTP2GO(フリーメール不可)、SendGrid(審査で止まる報告が多い)、Amazon SES(サンドボックス解除の申請が要る) |
| 規約上、本番で使えない | Gmail SMTP、Outlook SMTP |
| 無料枠がない、または試用のみ | Mailgun、Postmark、ZeptoMail |
| 立地や条件が合わない | Scaleway(EU のみ)、Elastic Email、Loops / Plunk |

### なぜこの 4 つか

実装は SMTP だけで、送るのは 1 日数通です。なので「SMTP で送れて、個人が登録できる」が条件。**無料枠の通数はどこでも余るので、見ませんでした。**

- **Mailjet** は制約の少なさの軸。ドメインなしで任意の宛先に送れる、当初の第一候補
- **Resend** は設定の軽さの軸。API キー 1 つで送れる最短経路がどこまで短いか
- **MailerSend** は配信事業者の出自の軸。Resend と同じ「ドメイン前提」が別の会社でどう違うか
- **Brevo** は繰り上げ。一度は外したものの、代わりに入れた SMTP2GO がフリーメールで登録できず、戻しました

### 4 社の顔ぶれ

**Resend**(米)
- 無料枠: 3,000 通/月、100 通/日、ドメイン 3 つ。送信にはドメインの検証が必須
- 超えたら: Pro $20/月(5 万通)
- 特徴: 開発者向けのトランザクションメール API。無料でも独自ドメインを複数登録できる

**Mailjet**(Sinch 傘下・スウェーデン)
- 無料枠: 6,000 通/月、200 通/日。Mailjet のロゴが付く
- 超えたら: Starter $9/月(8,000 通)
- 特徴: 無料枠の月間通数が 4 社で最大。送信元の検証が最も緩い

**Brevo**(旧 Sendinblue・仏)
- 無料枠: 300 通/日(検証時の記録。公式ページは今回取得できず)
- 超えたら: 未確認
- 特徴: マーケティング中心の配信基盤に SMTP リレーが付く。送信元 IP の登録と、登録時に企業名が要る

**MailerSend**(米・MailerLite と同じチーム)
- 無料枠: 500 通/月、ドメイン 1 つ
- 超えたら: Hobby $5.60/月(5,000 通)
- 特徴: 無料枠は小さいが、最安の有料プランが安い

### 実測

計測は 2 段階になりました。**独自ドメインを持たない状態と、取得して認証したあと**です。

| 候補 | ドメインなし | ドメイン認証後 | 解決に要った作業 |
|---|---|---|---|
| Mailjet | **送れた** | 送れた(4 秒) | なし |
| **Resend** | 自分宛てにしか送れない | 送れた(4 秒) | DKIM の登録 |
| MailerSend | `450 domain must be verified` | 送れた(6 秒) | SPF と DKIM の登録 |
| Brevo | `525 Unauthorized IP` | 送れた(2 秒) | **送信元 IP の登録**(ドメインでは解決しない) |

ドメインなしで送れたのは Mailjet だけ。ドメインを認証したら 4 社とも送れて、迷惑メールには入りませんでした。

最初は関門のない Mailjet を選びました。でも **Mailjet は認証していないドメインのアドレスからでも送れてしまう**。これは利点ではなく弱点だと考え直して、Resend に変えました。鍵が漏れたら任意の差出人で送られるし、他社なら弾かれる設定ミスに気づけないからです。

### ハマったこと

- **Brevo**: ドメイン認証を済ませても `525 Unauthorized IP` が残る。送信元 IP を登録して初めて通る。IP が固定されない Cloud Run とは相性が悪い
- **MailerSend**: 設定不備に 450(一時的エラー)を返すので、アプリが再試行を続けてしまう
- **Resend**: 共有ドメインだと `+` エイリアスすら「自分のアドレス」と認めないほど厳密
- **SMTP2GO**: そもそも登録できない。`Please use an email at your own domain to sign up`

## 4. API

### 候補に挙がったもの(10)

| 区分 | サービス |
|---|---|
| **選んだ 4 つ** | **Cloud Run、Render、Back4App、Northflank** |
| 有料だった | Zeabur、Railway(初回トライアルのみ)、Fly.io(新規向け無料枠が廃止) |
| 登録できなかった | Koyeb |
| 権限とネットワークの設計が要る | AWS App Runner / ECS、Azure Container Apps |

### なぜこの 4 つか

ここは候補の入れ替えが一番多かった層です。条件は「Docker イメージをそのまま動かせること」。

当初の案には **Zeabur**(東京・日本語 UI)と **Koyeb**(東京で DB と同居できる唯一の無料 PaaS)が入っていました。ところが Zeabur は有料だと分かり、Koyeb は利用登録ができませんでした。Fly.io と Railway も無料では始められません。AWS と Azure は個人がひとりで持つには設計が重い。

そうやって残ったのがこの 4 つです。

- **Render** は手数最少・カード不要・フロントと同居できる、当初の第一候補
- **Cloud Run** は無料枠が最大で東京に置けて、メモリを自由に設定できる。ただしカード必須で、超えると課金
- **Northflank** は無料枠でも常時起動。常駐ワーカーが動くか見たかった
- **Back4App** はカード不要の定額制。「請求リスクゼロ」の代表として

途中の案では Cloud Run を 2 つの構成で測るつもりでしたが、別のサービスを 4 つ見たほうが記事として価値があるので Back4App に差し替えました。

### 4 社の顔ぶれ

**Cloud Run**(Google・米)
- 無料枠: 200 万リクエスト/月、vCPU 18 万秒、メモリ 36 万 GiB 秒。**課金アカウント(カード)必須**
- 超えたら: 従量。vCPU $0.000024/秒、メモリ $0.0000025/GiB 秒
- 特徴: 要求がない間は 0 に縮んで、処理中だけ課金。予算アラートは通知するだけで、支払いを止めるには自分で自動化が要る

**Render**(米)
- 無料枠: 750 時間/月、512MB、15 分無通信でスリープ。カード不要
- 超えたら: $7/月(0.5 CPU・512MB)〜
- 特徴: Git 連携中心の PaaS。公式が「無料枠は本番に使わないこと」と明記している

**Back4App**(米・ブラジル拠点)
- 無料枠: 0.25 CPU、256MB、転送 100GB/月。リージョンは US のみ。カード不要
- 超えたら: コンテナ単位の定額。$5/月(0.5 CPU・512MB)〜
- 特徴: 従量ではなくコンテナごとの月額固定。請求が読める

**Northflank**(英)
- 無料枠: サービス 2 つ・DB 1 つ・cron 2 つ。スリープなし。カード不要
- 超えたら: 従量。最安 $5.40/月(0.2 vCPU・512MB)
- 特徴: 無料枠でも常時起動。自前クラウドへの配備(BYOC)にも対応

### 実測

同じ本番用イメージ(distroless、31MB)を 4 社に置き、DB・写真・メールはすべて同じものを向けました。

| 候補 | 立地 | 往復 | DB あり | 写真 24MP | SMTP |
|---|---|---|---|---|---|
| **Cloud Run** | 東京 | **46ms** | 287ms | **3.5 秒で通る** | **通る** |
| Render | オレゴン | 147ms | 322ms | 502 | **塞がれている** |
| Back4App | 米国 | 193ms | 421ms | 502 | 通る |
| Northflank | US | 479ms | 864ms | 503 | 通る |

**全機能が動いたのは Cloud Run だけでした。**

個人開発で一番怖いのは事故で請求が来ることなので、最初は「上限で止まるだけの無料プラン」を高く評価していました。ところがその基準で選んだ 3 社はどれもアプリを動かせず、動いたのはカード必須で超過すると課金される Cloud Run だけ。**「請求リスクなし」と「機能が動く」は両立しませんでした。**

写真の列は、API を直接叩いて原寸(2,400 万画素)を送った結果です。ブラウザ経由なら送信前に 1600px に縮小されるので無料プランでも通ります。ただし縮小に失敗すると原寸が飛ぶので、守りとしては弱い。

### ハマったこと

- **Render**: `render.yaml` にシンガポールと書いてもオレゴンになり、後から変えられない。Root Directory を `backend-go` にしないと `go.sum not found`。SMTP が塞がれているのでサインアップが完結しない
- **Northflank**: 無料枠は US しか選べない(Asia は有料)。384 万画素で 33 秒かかり、落ちる前に極端に遅くなる
- **Back4App**: Dockerfile の名前を選べない(既定の `Dockerfile` だけ)。一時 URL が期限切れになり、継続運用できない
- **Cloud Run**: 要求がない間はインスタンスが 0 になるので、常駐ワーカーも止まる

事前調査では「SMTP を塞ぐのは Cloud Run」と書いていました。実測すると塞いでいたのは Render。**ポートの遮断は事業者が明記しないことが多く、実測でしか分かりません。**

## 5. フロントエンド

### 候補に挙がったもの(17)

| 区分 | サービス |
|---|---|
| **選んだ 4 つ** | **Cloudflare Workers、Render Static、Netlify、Vercel** |
| `/api` のリライトができない | GitHub Pages、Firebase Hosting(Cloud Functions 先限定)、Surge、GitLab / Codeberg Pages、Azure Static Web Apps |
| 無料枠がない、または期限付き | S3 + CloudFront、Amplify、Bunny、DigitalOcean App Platform(帯域 1GB/月) |
| 静的配信にコンテナは過剰 | Fly.io / Railway に nginx、Koyeb / Zeabur |
| 目的が違う | Coolify / Dokploy(セルフホスト)、IPFS |

### なぜこの 4 つか

フロントは `/api` を同一オリジンで叩く前提なので、「`/api/*` を外部の URL へリライトできる」が条件。これでかなり落ちます。残った中から、**設定の書き方が違う 4 社**を選びました。

- **Cloudflare Workers** は設定ではなくコードでリライトを書く唯一の方式。帯域無制限・商用可も 4 社で唯一
- **Render Static** は YAML による宣言。API と同居できる当初の第一候補
- **Netlify** は記述量の少なさの代表。「1 行で書ける」評判が性能とどう関係するか
- **Vercel** は最も普及している。避ける理由があるなら示す価値がある

### 4 社の顔ぶれ

**Cloudflare Workers**(米・上場)
- 無料枠: Worker 呼び出し 10 万回/日。**静的アセットへの要求と帯域は無料・無制限**。商用可
- 超えたら: Paid $5/月(1,000 万リクエスト込み)
- 特徴: 帯域の課金がない。Worker を通す分(`/api/*` の転送)だけが日次上限に掛かる

**Render Static**(米)
- 無料枠: 静的サイト自体は無料。帯域とビルド分数はワークスペースの枠に計上(検証時の記録では帯域 100GB/月)
- 超えたら: 帯域とビルド時間の超過分だけ
- 特徴: API と同じ基盤に同居できる。CLI はなく Git 連携のみ

**Netlify**(米)
- 無料枠: 300 クレジット/月(帯域は約 15GB 相当)。使い切ると全サイト停止。商用可
- 超えたら: Personal $9/月(1,000 クレジット)
- 特徴: 2025 年 9 月にクレジット制に変わり、無料枠の帯域が大きく縮んだ

**Vercel**(米)
- 無料枠: 転送 100GB/月、100 デプロイ/日。**個人・非商用のみ**
- 超えたら: Pro $20/月
- 特徴: 無料枠の帯域は最大級だが、広告や決済を含む商用は規約で禁止

### 実測

同じビルド成果物(496KB)を 4 社に置き、`/api/*` を Cloud Run へ転送する設定を入れました。

| 候補 | HTML | API 転送 | 設定 | デプロイ所要 |
|---|---|---|---|---|
| **Cloudflare Workers** | 54ms | **285ms** | JS 11 行 | **約 8 秒** |
| Render Static | **40ms** | 505ms | YAML 7 行 | push 後 約 1 分 |
| Netlify | 287ms | **827ms** | TOML 9 行 | 8〜71 秒 |
| Vercel | 44ms | **148ms** | JSON 10 行 | 約 25 秒 |

参考として API 直叩きは 288ms。

**HTML の速さと転送の速さは連動しません。** Render は HTML 最速なのに転送は 3 位。静的配信の速さだけで選ぶと、API 経由で損をします。

Cloudflare だけがコードを書く方式なので減点していましたが、行数の差は 4 行でした。転送は最速。**「コードを書く手間」は減点にならなかった**、というのが結論です。

### ハマったこと

- **Cloudflare**: Google ログインが 2 段構えで壊れた。ページ遷移だとアセット配信が Worker より先に働くのと、`fetch` が 302 を勝手に追いかけるのと、原因が 2 つ。`run_worker_first` と `redirect: "manual"` の両方が要る。片方だけ直しても症状が変わらない
- **Render**: Action を Redirect にするとオリジンが変わって CORS で失敗する。Rewrite が必須
- **Vercel**: 既定で非公開(SSO に 302)。50 回のリクエストで Bot 対策に遮断される。CLI で配ると本番 URL が毎回変わる
- **Netlify**: ハマりなし。ただし転送が突出して遅く、デプロイ時間も 8 秒から 71 秒まで振れる

デプロイの所要時間は「コマンドが終わった」と「反映された」が別です。Render は push が 1 秒で戻り、ビルドは向こうで非同期に走ります。反映の確認は、ハッシュではなく変えた値そのものを配信物から探すのが確実でした。

## 選んだ構成

「全機能が動く」を最優先にして、その上で長期の費用と安全側に倒しました。

| 層 | 採用 | 選ばなかった最有力と、その理由 |
|---|---|---|
| API | Cloud Run(東京、1GB) | Render は写真と SMTP が動かず、サインアップが完結しない |
| DB | Neon | Supabase は東京で作り直せば速いはずだが、1 週間で停止する |
| 写真 | Cloudflare R2 | Tigris は 3 倍速いが、転送量が従量 |
| メール | Resend | Mailjet は関門がなさすぎて、鍵の漏洩と設定ミスに弱い |
| フロント | Cloudflare Workers | Vercel は転送最速だが、非商用限定・既定で非公開・Bot 対策の 3 つが重い |

カード登録なしで完結する構成は組めませんでした。Cloud Run と R2 はカードが要ります。予算アラートは支払いを止めないので、上限を超えたときに自分で止める覚悟は要ります。

残った課題は統計の再計算ワーカーです。Cloud Run は要求がない間インスタンスが 0 になるので、誰も見ていない間はワーカーも止まります。最小インスタンスを 1 にするか、外部の cron から叩くかのどちらかになります。

## まとめ

**無料枠の落とし穴は、料金表に書いていない。**

| 候補 | 料金表に書いてあること | 実際に当たった制約 |
|---|---|---|
| Render(API) | 750 時間/月、カード不要 | SMTP が塞がれている。リージョン変更不可 |
| Northflank | サービス 2 つ、常時起動 | 無料枠は US のみ |

机上の予想は何度も外れました。SMTP を塞ぐのは Cloud Run だと思っていたら Render でしたし、コードを書く手間があると減点した Cloudflare が転送最速でした。
