## 先に結論

個人開発のハンバーガーレビューアプリ(Go + React)のデプロイ先を決めるために、DB・画像ストレージ・メール送信・API・フロントの 5 層について、それぞれ 4 候補ずつ実際にデプロイして計測しました。

結論はこうなりました。

| 層 | 採用 | 決め手 |
|---|---|---|
| API | Cloud Run(東京、1GB) | **全機能が動いた唯一の候補** |
| DB | Neon | マイグレーションが無改変で通り、最も近い |
| 画像 | Cloudflare R2 | 転送量が無料・無制限 |
| メール | Resend | 送信元の検証が適切 |
| フロント | Cloudflare Workers | API への転送が最速 |

そして一番の学びはこれです。

> **無料枠の落とし穴は、料金表に書いていない。**

5 層 20 候補すべてで、実際にデプロイして使うまで分からない制約に当たりました。容量や通数の表を並べても、実用上の可否は判断できません。

なお、この検証は Claude Code と一緒に進めました。計測スクリプトや記録の大半は書いてもらっています。

## 検証したアプリ

- バックエンド: Go 1.27、標準 `net/http` + sqlc + pgx。ORM もフレームワークも使わない
- フロント: React 19 + Vite の SPA
- DB: PostgreSQL。主キーは UUID
- 画像: レビューに写真を添付。API がサーバー側でデコードして長辺 1600px に縮小する
- メール: サインアップの確認メールを SMTP で送る
- 認証: 独自実装の JWT。加えて OAuth 2.1 の認可サーバーを持つ

「個人が一人で登録から運用まで到達できること」を候補の条件にしました。営業への問い合わせが要るもの、サーバーの面倒を見るもの、IAM の設計が要るものは外しています。

## 1. DB:差は地理的距離だけだった

Neon・Supabase・Render Postgres・Xata の 4 社を、日本から pgx で直接叩いて 200 回ずつ計測しました。

| 候補 | リージョン | `SELECT 1` | 一覧 20 件 | トランザクション |
|---|---|---|---|---|
| Neon | Singapore | **86.2ms** | 86.3ms | 347.9ms |
| Render Postgres | Oregon | 146.2ms | 146.8ms | 587.6ms |
| Supabase | Mumbai | 131.1ms | 131.5ms | 526.8ms |
| Xata | US East | 177.4ms | 177.9ms | 713.8ms |

### 互換性では差がつかなかった

4 社とも PostgreSQL 17 以上で、マイグレーション 12 本が**無改変で適用できました**。UUID 主キーも外部キー 6 本も `CHECK` 制約もそのまま通り、sqlc の生成コードも無変更で動きました。

つまり **DB の選定で互換性を心配する必要はほぼありません**でした。

### 主キー 1 件も、3 テーブルの結合も、`SELECT 1` と同じ時間

これが一番意外でした。

主キーでの 1 件取得も、3 テーブルを結合した 20 件も、全レビューの集計も、`SELECT 1` と区別がつきません。差は最大でも 3ms です。

この規模のデータでは、**DB の処理時間がネットワークの往復に完全に埋もれます**。ベンチマークのスループット値を見て DB を選ぶのは意味がありませんでした。

### 書き込みは距離のペナルティを 4 倍受ける

トランザクションだけが突出しています。4 社とも**倍率が 4.02〜4.04 で一致**しました。

理由は往復の回数です。レビューの作成はこうなっています。

```
BEGIN
INSERT INTO reviews ...
INSERT INTO burger_stats_recalc_requests ... ON CONFLICT ...
COMMIT
```

4 往復です。事業者も距離も違うのに倍率が同じなのが、**時間を決めているのが DB の性能ではなく往復回数である**証拠になりました。

日本から見ると、レビューの閲覧は 86ms で済むのに、投稿は DB の往復だけで 348ms かかります。

これは CTE で 1 文にまとめれば 1 往復で済みます。

```sql
WITH r AS (
  INSERT INTO reviews (...) VALUES (...) RETURNING burger_id
)
INSERT INTO burger_stats_recalc_requests (burger_id)
SELECT burger_id FROM r
ON CONFLICT (burger_id) DO UPDATE SET ...
```

単一文は暗黙にアトミックなので整合性は保たれます。348ms が 87ms になる見込みです。

### ハマった点:Supabase の Direct connection は IPv6 専用

最初に設定した `db.<ref>.supabase.co` は **A レコードを持たず AAAA だけ**でした。macOS のホストから `psql` では繋がるのに、Docker コンテナからは名前解決できません。

「psql は通ったのにマイグレーションが失敗してテーブルが無い」という分かりにくい形で出ました。Session pooler(`aws-0-<region>.pooler.supabase.com`)に替えると通ります。

## 2. 画像ストレージ:R2 の転送量無料は本当に効く

R2・Supabase Storage・Tigris・Backblaze B2 の 4 社です。

| 候補 | PUT | **GET** | DELETE | GET の標準偏差 |
|---|---|---|---|---|
| **Tigris** | **89.2ms** | **26.0ms** | **22.3ms** | 19.3ms |
| Supabase Storage | 433.2ms | 38.5ms | 199.8ms | 106.1ms |
| Cloudflare R2 | 160.2ms | 80.9ms | 77.8ms | 36.8ms |
| Backblaze B2 | 233.2ms | 280.7ms | 185.6ms | **8.5ms** |

### 書き込みと読み取りの速さは連動しない

Supabase は PUT が GET の **11 倍**遅い一方、GET は 2 番目に速いです。書き込みが API ゲートウェイ、読み取りが CDN を通っていると推測できます。

写真は書き 1 回・読み多数なので、この偏りは実用上むしろ有利です。

### 安定性は B2 が最も高い

B2 は遅いですが GET の標準偏差が 8.5ms で、他社の半分以下です。逆に Supabase は p50 が 38.5ms と速いのに最大 779.9ms で、**2 割ほどの閲覧で目に見えて待たされます**。

平均だけ見ると誤ります。

### 速さでは Tigris、費用では R2

Tigris が全項目で最速でした。GET 26ms は R2 の 3 分の 1 です。それでも R2 を選んだのは、**転送量が無料・無制限**だからです。

写真は 1 回書いて何度も読まれるので、egress 課金の有無が長期的に効きます。

### ハマった点:B2 はマスターキーが使えない

最初に設定した keyID が 12 文字で、これはアカウント ID(マスターキーの keyID)でした。B2 は **S3 互換 API でマスターキーを拒否**します。

```
InvalidAccessKeyId: Malformed Access Key Id
```

App Keys から新規に作ると keyID は 25 文字(`005` で始まる)になります。アカウント ID が画面上部に大きく出ているので間違えやすいです。

## 3. メール送信:通数は選定の基準にならなかった

Mailjet・Resend・Brevo・MailerSend の 4 社です。

計測は 2 段階に分かれました。**独自ドメインを持たない段階と、取得して認証したあと**です。

### 第 1 段階:ドメインなしで送れたのは 1 社だけ

| 候補 | 結果 |
|---|---|
| **Mailjet** | **成功** |
| Brevo | `525 Unauthorized IP address` |
| Resend | `550 You can only send testing emails to your own email address` |
| MailerSend | `450 The from.email domain must be verified` |

Resend の「自分宛にしか送れない」は、**`+` エイリアスすら拒否する**ほど厳密でした。

### 第 2 段階:ドメインを取ったら全社通った

| 候補 | 解決に要した作業 |
|---|---|
| Mailjet | **なし** |
| Resend | DKIM の登録 |
| MailerSend | SPF と DKIM の登録 |
| Brevo | **送信元 IP の許可**(ドメインでは解決しない) |

**Brevo だけドメイン認証では解決しませんでした。** SMTP リレーを使う IP を事前登録する必要があります。ドメイン認証は一度で済みますが、IP の許可は接続元が変わるたびに必要です。Cloud Run のようにインスタンスの IP が固定されない基盤とは相性が悪いです。

### 通数はどれも余った

このアプリが送るのはサインアップ確認と既登録通知の 2 種で、1 日数通です。無料枠は 300 通/日から 6,000 通/月まで幅がありますが、**どれも使い切りません**。

実際に効いたのは「登録できるか」と「送信に到達するまでの関門」だけでした。

### 「通ってしまう」のは利点ではなく弱点

最初は関門が 1 つもない Mailjet を選びました。ところが **Mailjet は自社に認証していないドメインのアドレスからも送信できます**。

これを弱点と評価し直して Resend に変えました。

- SPF / DKIM が揃わないメールは、継続送信で評判が落ちて迷惑メール判定されやすくなる
- API キーが漏れたとき、**任意のアドレスから送れてしまう**
- 他社なら弾かれる状態でも送れるので、**設定の不備に気づけない**

Resend は DKIM 1 つで動きます。MailerSend(SPF + DKIM)ほど厳しくなく、Mailjet ほど緩くありません。

### ハマった点:SMTP2GO は登録すらできない

SMTP2GO はフリーメールでの登録を拒否します。

```
Error code 6 - Please use an email at your own domain to sign up
```

無料枠も機能も悪くないのですが、**ドメインを持たない個人開発者は入口で失格**です。料金表の比較には出てこない情報でした。

## 4. API:無料で「動く」ものが 1 つしかなかった

ここが一番の山場です。Render・Northflank・Back4App・Cloud Run に、同じ本番用イメージ(distroless、30.9MB)をデプロイしました。DB・画像・メールはすべて同じものを向けています。

| ホスト | 種別 | 立地 | メモリ | 写真(24MP) | SMTP |
|---|---|---|---|---|---|
| **Cloud Run** | 無料枠(超過で課金) | **東京** | 1GB | **通る** | **通る** |
| Render | 無料プラン(請求なし) | オレゴン | 512MB | 落ちる | **塞がれている** |
| Back4App | 無料プラン(請求なし) | 米国 | 256MB | 落ちる | 通る |
| Northflank | 無料枠 | US | 256MB | 落ちる | 通る |

### 「請求リスクなし」と「機能が動く」が両立しない

個人開発でいちばん怖いのは、事故で請求が来ることです。だから最初は「無料プラン(上限に達したら止まるだけで請求されない)」を「無料枠(超えたら課金)」より高く評価していました。

ところが**その基準で選んだ 3 社はいずれもアプリを動かせませんでした**。動いたのはカード必須で超過時に課金される Cloud Run だけです。

Cloud Run の予算アラートは通知するだけで、**支払いを止めません**。

### メモリと画素数の関係

同じ画像を小さい順に投げて、どこで落ちるか測りました。

| 画像 | 画素数 | Cloud Run 1GB | Render 512MB | Back4App 256MB | Northflank 256MB |
|---|---|---|---|---|---|
| 1200x800 | 96 万 | 1.3s | 3.3s | 3.8s | 5.3s |
| 2400x1600 | 384 万 | 1.6s | 5.6s | 5.6s | **33.6s** |
| 4000x2666 | 1,067 万 | 4.6s | 7.5s | 7.2s | **503** |
| 6000x4000 | 2,400 万 | **3.5s** | **502** | **502** | **503** |

分かったことが 3 つあります。

1. **公称メモリは実効性能と一致しない。** 256MB の Back4App が 512MB の Render と同じ閾値で、同じ 256MB の Northflank より明らかに強い
2. **落ちる前に「極端に遅くなる」帯がある。** Northflank の 384 万画素は通りますが 33.6 秒かかりました。GC が頻発している兆候です。メモリ不足は二択ではなく、**まず遅くなり、次に失敗します**
3. **落ちてもログに何も残らない。** カーネルが殺すので Go のパニックも出ません。エラーコードも事業者で違います(502 と 503)

### ブラウザ経由なら無料プランでも通る

ただし救いがあります。フロントには送信前に縮小する実装があり、長辺 1600px に縮めてから送ります。

その形(4.6MB・2,400 万画素 → **205KB・170 万画素**)で投げ直すと、Render も Northflank も**同時 3 本すべて成功**しました。

**「無料プランでは写真機能が動かない」は、API を直接叩いた場合に限った話**でした。

とはいえ守りとしては弱いです。実装のコメントにも「縮小に失敗しても元のファイルを送る」とあり、`createImageBitmap` が使えない環境では原寸が飛びます。サーバー側でセマフォによる直列化を入れる価値はあります。

### 無料枠ではリージョンが選べない

| ホスト | 希望 | 実際 |
|---|---|---|
| Render | シンガポール | **オレゴン**(変更不可) |
| Northflank | Asia East | **US**(無料枠は US のみ) |
| Cloud Run | 東京 | **東京** |

`render.yaml` に `region: singapore` と書いたのに反映されず、しかも**後から変更できません**。

**無料枠で東京に置けたのは Cloud Run だけ**でした。レイテンシの順位はほぼこれで決まっています。

### 予測が正反対だった:SMTP を塞いでいたのは Render

事前調査では「Cloud Run が 25/587/465 を塞ぐ」と書いていました。実測すると逆でした。

| ホスト | 587/STARTTLS |
|---|---|
| Cloud Run | **通る** |
| Northflank | 通る |
| Back4App | 通る |
| **Render** | **塞がれている**(`i/o timeout`) |

しかも Render は当初の第一候補でした。写真が動かず、確認メールも送れないので、**サインアップが完了しません**。

ポートの遮断は事業者が明記しないことが多く、**実測でしか分かりません**。

## 5. フロント:HTML の速さと転送の速さは連動しない

Cloudflare Workers・Render Static・Netlify・Vercel の 4 社に、同じビルド成果物(496KB)を置きました。

| ホスト | HTML | `/api` 転送 | 転送設定 |
|---|---|---|---|
| **Cloudflare Workers** | 54ms | **285ms** | JS 11 行 |
| Render Static | **40ms** | 505ms | YAML 7 行 |
| Netlify | 287ms | 827ms | TOML 9 行 |
| Vercel | 44ms | **計測不能** | JSON 10 行 |

参考として API 直叩きは 288ms です。

Render は HTML が最速なのに転送は 3 位、Cloudflare はその逆です。**静的配信の速さだけで選ぶと API 経由で損をします**。

### 「コードを書く手間」は減点にならなかった

Cloudflare だけが設定ではなく JavaScript を書く方式です。手間がかかると思っていましたが、**行数の差は 4 行**でした。しかも転送は最速です。

```js
export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    if (url.pathname.startsWith("/api/")) {
      const target = new URL(url.pathname.replace(/^\/api/, "") || "/", env.API_ORIGIN);
      target.search = url.search;
      return fetch(new Request(target, request));
    }
    return env.ASSETS.fetch(request);
  },
};
```

### ハマった点:Rewrite と Redirect を間違えると壊れる

Render の設定で Action を Redirect にすると、`/api/meta` が `301 Moved Permanently` で API の URL を返します。

ブラウザが直接 API に飛ばされるので**オリジンが変わり、CORS で失敗**します。Rewrite はサーバー側で裏に取りに行き URL が変わりません。同一オリジンを保つには Rewrite が必須です。

### ハマった点:Vercel は制約が 3 つ

1. **Hobby プランは非商用限定**
2. **既定で公開されていない。** デプロイ直後はすべて 302 で SSO にリダイレクトされます
3. **50 回のリクエストで Bot 対策に遮断されました**

```
x-vercel-mitigated: challenge
```

User-Agent をブラウザ相当に変えても解除されず、IP 単位で遮断されているようです。他の 3 社では同じ計測が通りました。

SPA は 1 画面で複数の API を叩くので、**共有 IP(オフィスや学校)からの利用で誤検知される**懸念もあります。

## 料金表に書いていない落とし穴のまとめ

5 層 20 候補すべてで、実際に使うまで分からない制約に当たりました。

| 候補 | 料金表に書いてあること | 実際に当たった制約 |
|---|---|---|
| Render(API) | 750 時間/月、512MB、カード不要 | **SMTP が塞がれている**。リージョン変更不可 |
| Northflank | Sandbox で 2 サービス、常時起動 | **無料枠は US のみ** |
| Back4App | 600 時間/月、5 プロジェクト | **一時 URL が期限切れになる** |
| Cloud Run | 200 万リクエスト/月 | 超過で課金。予算アラートは支払いを止めない |
| SMTP2GO | 1,000 通/月 | **フリーメールで登録できない** |
| Brevo | 300 通/日 | **送信元 IP の登録が要る** |
| Vercel | 帯域 100GB/月 | 非商用限定、既定で非公開、Bot 対策で遮断 |
| Supabase(DB) | 500MB、東京あり | Direct connection が **IPv6 専用** |
| B2 | 10GB 無料 | **マスターキーが S3 API で使えない** |

無料枠の比較記事は容量や通数の表を並べがちですが、**実用上の可否はそこでは決まりませんでした**。

## 計測でやらかしたこと

参考までに、自分たちが踏んだ失敗も書いておきます。

### プレースホルダー画面を測っていた

Cloud Run の最初の計測で `/meta` も `/up` も 44ms という好成績が出ました。よく見ると **DB を使わない `/meta` と DB に ping する `/up` の差が 0ms** でした。

アプリがデプロイされておらず、Cloud Run の既定のプレースホルダー画面を測っていました。決め手は、認証トークンが空なのに写真のアップロードが 200 を返したことです。

**速すぎる結果こそ疑うべき**でした。以後は計測前に `content-type` を確認するようにしています。

### 「転送の上乗せ 0ms」も誤り

Cloudflare 経由の最小値が API 直叩きの最小値より速いという矛盾が出ました。キャッシュかと思って調べると `cf-cache-status: DYNAMIC` で、毎回 API に到達していました。

原因は計測方法です。毎回新しい接続を張るので**直叩きは毎回 TLS の確立を含む**のに対し、Cloudflare 経由では Worker と API の間の接続が使い回されます。条件が揃っていませんでした。

### 共有 DB で常駐ワーカーを測ろうとした

4 ホストに同じ DB を向けたのは公平性のためでしたが、キューのテーブルも共有されるので**どのホストのワーカーが処理しても行が消えます**。

読み取りの比較では共有が公平性を生み、書き込みを伴う常駐処理の検証では干渉を生みます。**目的によって方針が逆になる**と気づきました。

## まとめ

- **互換性は心配しなくてよかった。** DB は 4 社とも無改変で動いた
- **この規模では DB の性能差はネットワークに埋もれる。** 差は地理的距離だけ
- **書き込みは往復回数がすべて。** トランザクションは距離のペナルティを 4 倍受ける
- **通数は選定の基準にならない。** 効くのは「登録できるか」「関門があるか」
- **「通ってしまう」サービスは選ばない。** 関門は制約であると同時に防御でもある
- **無料プランと機能の両立は難しい。** メモリとポートで落ちる
- **無料枠でリージョンは選べない。** 東京に置けたのは 1 社だけ
- **公称メモリは実効性能と一致しない**
- **HTML の速さと転送の速さは連動しない**
- **料金表に書いていない制約が、実用上の可否を決める**

一番の教訓は、**机上の比較で立てた予測が何度も外れた**ことです。SMTP を塞いでいるのは Cloud Run だと思っていたら Render でしたし、コードを書く手間があると減点した Cloudflare が最速でした。

デプロイ先は、実際にデプロイしてみないと分かりません。
