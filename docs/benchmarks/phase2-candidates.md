# Phase 2: 写真ストレージ候補の解説と、選ばなかった理由

- 日付: 2026-09-21
- 計測結果は [phase2-summary.md](phase2-summary.md)、決定は [ADR-0004](../adr/0004-photo-storage.md)

## 前提: このアプリがストレージに求めるもの

実装(`backend-go/internal/adapter/storage/s3.go`)が使う機能は**驚くほど少ない**。

| # | 要件 | 根拠 |
|---|---|---|
| 1 | S3 互換の `PutObject` と `DeleteObject` | アダプタが使うのはこの 2 つだけ |
| 2 | path-style アドレッシング | `UsePathStyle: true`。カスタムエンドポイントはバケットのサブドメインを解決しないため |
| 3 | 公開 URL からの配信 | `URL(key)` が `baseURL + "/" + key` を返すだけ。署名付き URL は使わない |
| 4 | Region `"auto"` を受け付ける | `Region: "auto"` がハードコードされている(検証の結果、4 社とも問題なし) |

使わない機能も明記しておく。**一覧取得、マルチパートアップロード、ライフサイクル規則、
署名付き URL、バージョニングは一切使わない。** 写真は API がデコードして縮小したあと、
単純に 1 つの物体として置くだけである。

つまり**「S3 互換の PUT と DELETE ができて、公開 URL で配れる」以上の機能は要らない**。
選定はほぼ費用と速さだけの勝負になる。

### 評価軸

1. **転送量(egress)の課金**。写真は 1 回書いて何度も読まれるため、ここが最初に無料枠を使い切る
2. 保存容量の無料枠
3. 配信の速さと安定性
4. 公開配信の設定の手間

---

## 選んだ 4 つ

4 社は**それぞれ違う軸の端**を代表するように選んだ。

### 1. Cloudflare R2 — 転送量が無料という一点で選ぶ

Cloudflare が提供する S3 互換のオブジェクトストレージ。最大の特徴は
**転送量(egress)が無料・無制限**であること。他社は保存容量が足りても転送量で先に
無料枠を使い切るため、この一点だけで性質が違う。

- **代表する軸**: 費用。特に転送量
- **無料枠**: 10GB 保存、1000 万 read/月、100 万 write/月。カード要(無料枠内なら請求なし)
- **選んだ理由**: [ADR-0004](../adr/0004-photo-storage.md) の第一候補。転送量無料は
  写真用途で決定的に効く
- **計測結果**: PUT 160.2ms / GET 80.9ms。ただし**開発用の `r2.dev` URL で測っており不利がある**

### 2. Supabase Storage — DB と同居できる

Supabase の一部として提供されるストレージ。S3 互換のエンドポイントを持つ。
Phase 1 で DB として測った Supabase と同じプロジェクトに置けるため、管理が一本化できる。

- **代表する軸**: 統合。DB とストレージを同じ事業者にまとめる
- **無料枠**: 1GB 保存、転送 5GB/月
- **選んだ理由**: DB を Supabase にする場合の一体構成を測るため。東京リージョンも選べる
- **計測結果**: PUT 433.2ms(最も遅い)/ GET 38.5ms(2 番目に速い)。
  **書き込みと読み取りの差が 11 倍**という特異な結果になった

### 3. Tigris — アクセスされた地域へ自動で寄せる

Fly.io と組んで作られた S3 互換ストレージ。アクセスのあった地域にデータを自動的に
複製し、近い場所から配る仕組みを持つ。

- **代表する軸**: 配置戦略。グローバル分散が速さにどう出るか
- **無料枠**: 5GB 保存。Fly.io 内の転送は無料、外部へは従量
- **選んだ理由**: R2 の対抗馬として、配置の違いがレイテンシに現れるかを見るため
- **計測結果**: **全項目で最速**(PUT 89.2ms / GET 26.0ms / DELETE 22.3ms)。
  ADR-0004 の「Fly.io を使う場合のみ」という位置づけを覆した

### 4. Backblaze B2 — 老舗の低価格ストレージ

2015 年から続くクラウドストレージ専業の事業者。R2 が登場する前は「安い S3 互換」の
定番だった。Cloudflare と帯域提携(Bandwidth Alliance)があり、Cloudflare 経由なら
転送量が無料になる。

- **代表する軸**: 実績。R2 登場前の定番が今どうか
- **無料枠**: 10GB 保存、転送は保存量の 3 倍/月まで無料。**カード不要**
- **選んだ理由**: 4 社で唯一カード登録が不要。無料枠の条件も良い
- **計測結果**: GET 280.7ms と最も遅いが、**標準偏差 8.5ms で最も安定**している

## 選ばなかったもの

### A. S3 互換でないため、コードを書き足すことになる

| 候補 | 外した理由 |
|---|---|
| **Vercel Blob** | 独自 API で S3 互換ではない。`aws-sdk-go-v2` が使えず、`adapter/storage/` に新しい実装を足すことになる。無料枠も 1GB 保存・10GB 転送と小さい |
| **Cloudflare Images** | 画像の保存と変換に特化した独自 API。S3 互換ではない。加えて保存時に長辺 1600px へ縮小済みのため、動的変換の必要が薄い |
| **Bunny Storage** | FTP と独自 HTTP API のみ。安さは魅力だが薄いクライアントを書くことになる |

いずれも「安い」「速い」といった利点はあるが、**アダプタを 1 つ書き足す作業が発生する**。
S3 互換で足りているうちは、その作業に見合わない。

### B. 用途が違う(変換特化)

| 候補 | 外した理由 |
|---|---|
| **ImageKit** | 外部の S3 / R2 をオリジンにでき、URL パラメータでリサイズや WebP 変換ができる。ただし**このアプリは保存時に縮小と再エンコードを済ませている**ため、動的変換の出番がない |
| **Cloudinary** | 同上。無料枠(25 クレジット/月)を超えたときの単価も高い |
| **Uploadcare / Uploadthing** | フロントのアップロード UI まで含めたサービス。本アプリは API 経由でアップロードするため、その部分が丸ごと無駄になる |

ADR-0004 の初版では「保存は R2、変換は ImageKit」という折衷案を検討していた。
**実装を読んで、変換がサーバー側で完結していると分かった時点でこの案は不要になった。**

### C. 無料枠がない、または期限付き

| 候補 | 最小コスト | 備考 |
|---|---|---|
| **AWS S3** | 12 か月は 5GB 無料、以後は従量 | 転送量にも課金。バックエンドが AWS でない限り選ぶ理由がない |
| **Google Cloud Storage** | 5GB 無料だが**米国リージョンのみ**、転送は 1GB/月 | 日本から使うと無料枠の外になる |
| **Azure Blob Storage** | 12 か月 | 同上 |
| **Wasabi** | $7/月(1TB 分)〜 | 転送量は無料だが、最低料金が 1TB 分で個人には過剰 |
| **DigitalOcean Spaces** | $5/月(250GB + CDN) | 定額で読みやすいが無料枠がない |
| **Hetzner Object Storage** | €5/月〜 | 欧州のみ。日本から遠い |

### D. 運用が重い、または条件が不透明

| 候補 | 外した理由 |
|---|---|
| **MinIO(セルフホスト)** | S3 互換で開発環境には有用(本検証でもツールの動作確認に使った)。本番で使うには VPS の運用を自分で持つことになる |
| **Storj** | 分散ストレージ。無料枠が縮小傾向で条件が読みにくく、レイテンシも分散の性質上ばらつきやすい |
| **Render Disk** | 永続ボリューム。S3 API がなく、CDN 配信もできず、すべてのアクセスが API を通る。`PHOTO_STORAGE=disk` 用の緊急手段にとどまる |

---

## まとめ

外した理由は 4 つに分かれる。

1. **S3 互換でない**(Vercel Blob、Cloudflare Images、Bunny)— アダプタを書き足すことになる
2. **用途が違う**(ImageKit、Cloudinary、Uploadcare)— 変換はサーバー側で完結済み
3. **無料で始められない**(AWS S3、GCS、Wasabi、DO Spaces 等)
4. **運用が重い / 条件が不透明**(MinIO、Storj、Render Disk)

**2 は実装を読んで判断が変わった例である。** ADR-0004 の初版は「署名付き URL で
ブラウザから直接アップロードし、変換は外部サービスに任せる」設計を前提に
ImageKit を折衷案として挙げていた。実装は API 経由でサーバー側が縮小・再エンコードを
行っており、外部の変換サービスを挟む余地がない。

## 計測が示した軸の対立

選定の軸として「費用」と「速さ」を置いたが、**実測の結果この 2 つが対立した。**

| | 転送量の課金 | GET p50 |
|---|---|---|
| R2 | **無料・無制限** | 80.9ms |
| Tigris | 従量(Fly.io 内は無料) | **26.0ms** |

配信量が少ないうちは Tigris が有利で、増えると R2 が有利になる。
**分岐点がどこかは、実際の閲覧数が分からないと決められない。**

したがって [ADR-0004](../adr/0004-photo-storage.md) の決定は保留とし、次の 2 点を
確かめてから確定する。

1. R2 をカスタムドメインで測り直す(開発用 URL の不利を除く)
2. Tigris の Fly.io 外からの転送量の課金条件を確認する
