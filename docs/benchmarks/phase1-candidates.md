# Phase 1: DB 候補の解説と、選ばなかった理由

- 日付: 2026-09-21
- 計測結果は [phase1-summary.md](phase1-summary.md)、決定は [ADR-0003](../adr/0003-database-hosting.md)

## 前提: このアプリが DB に求めるもの

候補を絞った基準は次の 5 つ。実装(`backend-go`)を読んで決めた。

| # | 要件 | 根拠 |
|---|---|---|
| 1 | PostgreSQL のワイヤプロトコル | ドライバが pgx v5、クエリ生成が sqlc(`engine: postgresql`) |
| 2 | `gen_random_uuid()` が使える | 主キーが UUID。PostgreSQL 13 以上が必要 |
| 3 | 外部キー制約 | スキーマに 6 本ある |
| 4 | `CHECK` 制約 | 文字数の上限を domain と DB の二重で持つ方針 |
| 5 | `FOR UPDATE SKIP LOCKED` | 統計再計算の待ち行列(`burger_stats_recalc_requests`)が使う |

加えて運用の条件として「無料で始められる」「個人が一人で登録から運用まで到達できる」を課した。

---

## 選んだ 4 つ

4 社は**それぞれ違う軸を代表するように**選んだ。同種を 4 つ並べても比較にならないため。

### 1. Neon — サーバーレス Postgres の代表格

計算(コンピュート)とストレージを分離した構成の Postgres。使われていない間はコンピュートを
自動で休止し、アクセスが来ると 1 秒未満で復帰する。Git のようにデータベースを分岐できる
ブランチ機能を持ち、本番のコピーを一瞬で作れる。

- **代表する軸**: 「休む DB」。無料枠でコンピュート時間が課金対象になる方式
- **無料枠**: 0.5GB、コンピュート 190 時間/月、カード不要
- **選んだ理由**: 無料枠で本番運用が現実的な数少ない選択肢で、Render や Cloud Run と
  組み合わせる事例が最も多い。ベースラインとして妥当

### 2. Supabase — Firebase の代替を掲げる統合基盤

Postgres 本体に、認証・ファイルストレージ・リアルタイム通知・自動生成 REST API を
足したもの。本アプリは認証を自前の JWT で実装しているので、**Postgres の部分だけ**を使う。

- **代表する軸**: 「東京リージョンがある」ことと、「1 週間無通信で停止する」という特異な挙動
- **無料枠**: 500MB、カード不要。ただし 1 週間触らないとプロジェクトが一時停止する
- **選んだ理由**: 4 社で唯一、東京リージョンを選べる(新規プロジェクトの場合)。
  一方で放置による停止という無料枠特有のリスクも持つ。利点とリスクの両方を測れる

### 3. Render Postgres — 汎用 PaaS に付属する Postgres

Render は Heroku の後継を狙った PaaS で、Web サービス・静的サイト・Postgres を
同じダッシュボードで扱える。DB 自体に特別な機能はなく、素の Postgres である。

- **代表する軸**: 「API と同じ事業者に置く」こと。内部ネットワークで繋がる速さ
- **無料枠**: **30 日で失効**。以後は $6〜7/月。カード不要
- **選んだ理由**: [ADR-0002](../adr/0002-backend-deploy-target.md) の API 第一候補が Render で、
  同居構成は実際に採用しうる。無料枠は短いが、検証は数日で終わるため支障がない

### 4. Xata — 新興の Postgres プラットフォーム

当初は独自 API と SDK を持つ「データベースプラットフォーム」だったが、素の Postgres の
提供へ方向転換した。ブランチ機能とスキーマ移行の体験を売りにしており、個人開発者向けに
作られている。

- **代表する軸**: ニッチ枠。Neon の対抗馬が実際どう違うか
- **無料枠**: あり(条件は変動しやすい)、カード不要
- **選んだ理由**: 知名度が低く日本語の情報も少ないため、実測に一次情報としての価値がある

## 選ばなかったもの

### A. 技術的に使えない

| 候補 | 種別 | 外した理由 |
|---|---|---|
| **Amazon Aurora DSQL** | 分散 SQL(PG 互換) | **シーケンスと外部キーに非対応。** 本アプリは外部キーを 6 本持つ。名前は「PostgreSQL 互換」だがスキーマの全面見直しが要る |
| **Cloudflare D1** | SQLite(HTTP API) | Cloudflare Workers の中からしか使えない。Go は Workers で動かない(TinyGo → Wasm では pgx が動かない) |
| **MongoDB Atlas / DynamoDB** | ドキュメント / KV | sqlc を捨てて永続化層を全面的に書き直すことになる。店舗・バーガー・レビュー・統計という関係の強いスキーマとも相性が悪い |

Aurora DSQL は注意が要る例である。**「PostgreSQL 互換」という表示は、SQL の方言が
通ることを意味しても、シーケンスや外部キーが使えることを保証しない。**

### B. 動くが、別の言語・別の道具に乗り換えることになる

| 候補 | 種別 | 外した理由 |
|---|---|---|
| **PlanetScale(MySQL)** | MySQL 互換 | ドライバを `go-sql-driver/mysql` に、sqlc のエンジンを `mysql` に変え、クエリの方言を書き直す必要がある。得られるものがない |
| **TiDB Serverless** | MySQL 互換の分散 SQL | 同上。無料枠(5GB)は魅力だが、移行コストに見合わない |
| **Turso / libSQL** | SQLite 系 | 専用ドライバが要り、`gen_random_uuid()` も使えない。統計の待ち行列が前提にする排他制御も Postgres のものとは異なる |
| **SQLite + Litestream** | 組み込み DB | Go との相性は良く(CGO 不要のドライバがある)最も安いが、コンテナ環境では永続ボリュームとレプリケーションの設定が要る。マネージド Postgres の無料枠より手間が増える |

### C. 技術的には動くが、要件に対して過剰

| 候補 | 種別 | 外した理由 |
|---|---|---|
| **CockroachDB Cloud** | 分散 SQL(PG ワイヤ互換) | pgx は公式サポートで、主キーが UUID になったため**当初の懸念(連番 PK の hotspot)は消えた**。それでも売りはマルチリージョンの水平スケールで、単一リージョンの個人アプリでは書き込みレイテンシと運用の複雑さだけを払う。無料枠が従量クレジット制で、いつ尽きるか読みにくい点も不利 |
| **YugabyteDB Aeon** | 分散 SQL(PG フォーク) | Postgres 互換が最も深く、pgx でそのまま動く。Sandbox は無期限無料。理由は Cockroach と同じで、**分散が必要になったときの移行先としては第一候補**だが、今は利点がない |

この 2 つは **ADR-0003 の初版では「連番 PK が分散環境で非推奨」を理由に下げていた**。
実装を読んで主キーが UUID と分かった時点でその理由は消えたので、格上げしたうえで
「利点がない」という別の理由で見送っている。理由の差し替えを記録に残す。

### D. 素の Postgres だが、他と差がつかない

| 候補 | 外した理由 |
|---|---|
| **Aiven for PostgreSQL** | 無料枠 5GB・カード不要と条件は良い。ただし中身は素の Postgres で、Neon や Render と違う軸を代表しない。リージョンの選択肢も限られる |
| **Prisma Postgres** | Node の ORM である Prisma 向けに最適化されている。Go から使う利点がない |
| **Nile** | マルチテナント(1 つの DB を複数の顧客で分ける)に特化。本アプリは単一テナントなので、その機能が丸ごと無駄になる |
| **Koyeb Postgres** | **当初は候補に入れていた**(東京で API と同居できる唯一の無料 PaaS)。2026-09-21 時点で利用登録ができず、検証不能のため Render Postgres に差し替えた |

### E. 無料で始められない

| 候補 | 最小コスト | 備考 |
|---|---|---|
| **Fly.io Managed Postgres** | $5/月前後 | 東京リージョンがあり魅力的だが、新規向けの無料枠が廃止された |
| **PlanetScale Postgres** | $39/月〜 | 性能と運用品質は高いが、この規模では過剰 |
| **AWS RDS / Google Cloud SQL / Azure Database** | $10〜15/月〜 | 加えて VPC や IAM の設定が要る |
| **Render Postgres(31 日目以降)** | $6〜7/月 | 検証には使えるが、無料で運用し続けることはできない |

### F. 無料だが、個人が一人で運用するには重い

| 候補 | 外した理由 |
|---|---|
| **Oracle Cloud Always Free の VM 上に自前構築** | 無期限無料で ARM 4 コア・24GB という破格の枠だが、OS の更新・TLS 証明書・バックアップ・監視をすべて自分で持つ。アカウント停止の報告もある |
| **Kamal / Coolify + VPS 上のコンテナ** | 同上。月額は最安だが、DB の運用責任を負う |

---

## まとめ

外した理由は 6 つに分かれる。

1. **技術的に使えない**(Aurora DSQL、D1、NoSQL)— 外部キーや実行環境が要件と衝突する
2. **道具の乗り換えが要る**(MySQL 系、SQLite 系)— pgx と sqlc の前提を崩す
3. **要件に対して過剰**(Cockroach、Yugabyte)— 分散の利点を使う場面がない
4. **他と差がつかない**(Aiven、Prisma、Nile)— 比較の軸を増やさない
5. **無料で始められない**(Fly、PlanetScale、RDS 等)
6. **運用が重い**(自前構築)

このうち **3 の「過剰」は、実装を読んで判断理由が変わった例**である。当初は「連番の主キーが
分散環境に向かない」という技術的な理由で下げていたが、主キーが UUID だと分かって
その理由は消えた。それでも採用しないのは、分散という機能そのものに使い道がないからである。
