# Phase 6: フロントエンド候補の解説と、選ばなかった理由

- 日付: 2026-09-22
- 計測結果は [phase6-summary.md](phase6-summary.md)、決定は [ADR-0001](../adr/0001-frontend-deploy-target.md)

## 前提: このアプリがフロントのホストに求めるもの

`frontend/` は Vite でビルドする静的な SPA である。出力は `dist/` の 496KB。
SSR も Node ランタイムも要らないため、**要件は驚くほど少ない**。

| # | 要件 | 根拠 |
|---|---|---|
| 1 | 静的ファイルを配信できる | ビルド成果物を置くだけ |
| 2 | **`/api/*` を外部 URL へリライトできる** | `buildApiClient.ts` が `baseURL: "/api"` を既定にする |
| 3 | SPA の deep link に対応できる | `/reviews/<uuid>` への直接アクセスで `index.html` を返す必要がある |
| 4 | HTTPS と独自ドメイン | OAuth の `redirect_uri` は https 必須 |

**2 が選定の核心である。** アプリは API と同一オリジンで通信する前提で書かれており、
ホスト側がリライトを肩代わりする。これができないホストは、`VITE_API_BASE_URL` を
使った直接接続に切り替える必要があり、**Go 側に CORS の実装が要る**(現在は未実装)。

### 評価軸

1. **`/api/*` のリライトができるか、どう書くか**
2. 転送のレイテンシ(直叩きに対する上乗せ)
3. 静的配信のレイテンシ
4. 無料枠の条件(帯域、商用利用の可否、カード要否)
5. deep link の扱い

---

## 選んだ 4 つ

4 社は**リライトの書き方が 4 通りに分かれる**よう選んだ。
同じことを YAML・TOML・JSON・JavaScript で書き比べる形になる。

### 1. Cloudflare Workers(Static Assets)— コードで書く唯一の方式

Cloudflare Pages を統合した後継の形。静的ファイルを配信しつつ、
同じ Worker のコードでリクエストを横取りできる。

- **代表する軸**: 設定ではなく**コード**でリライトを書く
- **無料枠**: **帯域無制限・商用可**。カード不要
- **書き方**: `worker/index.js` で `fetch` を書く(実効 11 行)
- **計測結果**: **転送が最速(285ms)**。HTML は 54ms
- **選んだ理由**: 帯域無制限・商用可という条件は 4 社で唯一

### 2. Render Static Site — 宣言的な YAML

Heroku の後継を狙った PaaS の静的ホスティング。`render.yaml` に宣言を書く。

- **代表する軸**: YAML による宣言。API と同居できる(当初の想定)
- **無料枠**: 帯域 100GB/月、無期限。カード不要
- **書き方**: `render.yaml` の `routes`(実効 7 行。**4 社で最少**)
- **計測結果**: **HTML が最速(40ms)で最も安定**。転送は 505ms
- **選んだ理由**: [ADR-0001](../adr/0001-frontend-deploy-target.md) の当初の第一候補。
  API も Render に置く前提だった

**この前提は Phase 4 で崩れた。** API が Cloud Run になったため、同居の利点は消えた。

### 3. Netlify — 最小記述の代表

JAMstack という言葉を広めた老舗。`_redirects` や `netlify.toml` で宣言する。

- **代表する軸**: 記述量の少なさ
- **無料枠**: 帯域 100GB/月。商用可。カード不要
- **書き方**: `netlify.toml` の `[[redirects]]`(実効 9 行)
- **計測結果**: **転送が最も遅い(827ms)**。HTML も 287ms で最も遅く、ばらつきも大きい
- **選んだ理由**: 「1 行で書ける」という評判が、実際の性能とどう関係するかを見るため

### 4. Vercel — 最も普及している

Next.js の開発元。Git 連携と PR プレビューの体験が洗練されている。

- **代表する軸**: 普及度。JSON による宣言
- **無料枠**: 帯域 100GB/月。**Hobby は非商用限定**
- **書き方**: `vercel.json` の `rewrites`(実効 10 行)
- **計測結果**: HTML は 44ms。**転送は計測できなかった**(Bot 対策で遮断)
- **選んだ理由**: 最も普及しているため、避ける理由があるなら示す価値がある

## 選ばなかったもの

### A. `/api` のリライトができない

**これが最大の足切り条件である。** リライトできないホストを選ぶと、
`VITE_API_BASE_URL` による直接接続に切り替えることになり、
**Go 側に CORS ミドルウェアを実装する作業が発生する**(現在は未実装)。

| 候補 | 状況 |
|---|---|
| **GitHub Pages** | リライト機能がない。SPA の deep link も `404.html` を使う回避策が要る |
| **Firebase Hosting** | リライト先が Cloud Functions / Cloud Run に限られ、任意の外部 URL へは転送できない |
| **Surge.sh** | 静的配信のみ |
| **GitLab Pages / Codeberg Pages** | 同上 |
| **Azure Static Web Apps** | 外部 API へのリンクは Azure 内サービスに限られる |

無料枠の条件だけ見れば悪くないものもあるが、**要件 2 を満たさない時点で比較の土俵に乗らない。**

### B. 無料枠がない、または期限付き

| 候補 | 状況 |
|---|---|
| **AWS S3 + CloudFront** | 12 か月無料の後は従量。設定量も 4 社と比べて格段に多い |
| **AWS Amplify Hosting** | 12 か月無料。外部 URL への 200 リライトは可能 |
| **Bunny.net** | 月 1 ドル程度。東京 PoP は魅力だがデプロイが手動 |
| **DigitalOcean App Platform** | 静的 3 つまで無料だが**帯域が 1GB/月**と実用に足りない |

### C. 静的配信にコンテナは過剰

| 候補 | 状況 |
|---|---|
| **Fly.io / Railway に nginx コンテナ** | `frontend/Dockerfile`(nginx)がそのまま動くが、静的ファイルを配るために常駐プロセスを持つのは無駄。Fly は無料枠もない |
| **Koyeb / Zeabur の静的ホスティング** | Phase 4 で Koyeb は登録不可、Zeabur は有料と判明 |

### D. 目的が違う

| 候補 | 状況 |
|---|---|
| **Coolify / Dokploy(セルフホスト)** | 自前 VPS に PaaS の UI を載せる。運用を自分で持つ |
| **IPFS(Fleek 等)** | 分散配信が目的でなければ選ばない |

---

## まとめ

外した理由は 4 つに分かれる。

1. **`/api` のリライトができない**(GitHub Pages、Firebase、Surge、Azure SWA)
2. **無料で始められない**(AWS 系、Bunny、DO)
3. **静的配信に対して過剰**(コンテナ系)
4. **目的が違う**(セルフホスト、IPFS)

**1 が実質的な足切りだった。** 静的ホスティングは数多くあるが、
「外部の API へリライトできる」という条件で大半が落ちる。
無料枠の帯域や容量の比較に入る前の話である。

## 計測が覆した前提

選定時の想定と実測が食い違った点が 2 つある。

### 「コードを書く手間」は減点にならなかった

[ADR-0001](../adr/0001-frontend-deploy-target.md) では Cloudflare を
「設定でなくコードを書く手間がある」と減点していた。

実際の記述量は次のとおりで、**差は 4 行しかなかった**。

| ホスト | 方式 | 実効行数 |
|---|---|---|
| Render | YAML | 7 |
| Netlify | TOML | 9 |
| Vercel | JSON | 10 |
| Cloudflare | **JavaScript** | 11 |

しかも **Cloudflare の転送が最速だった**。減点の根拠は薄かった。

### 「API と同居できる」利点は消えた

Render を当初の第一候補にした理由は、API も Render に置けることだった。
Phase 4 で API が Cloud Run になったため、**この利点は前提ごと失われた**。

結果として 4 社とも「API は別事業者」という同じ条件になり、比較としては公平になった。
