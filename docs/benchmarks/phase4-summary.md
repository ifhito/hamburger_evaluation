# Phase 4: API デプロイ先 4 候補のまとめ

- 計測日: 2026-09-22
- 計測元: 日本(自宅回線)から、本番用イメージ(`backend-go/Dockerfile`、30.9MB)
- 共通の接続先: DB は Neon(シンガポール)、写真は Cloudflare R2、メールは Mailjet
- 各社の詳細は `phase4-<社名>.md`

## 結論

**このアプリを全機能動かせたのは Cloud Run だけだった。**

| ホスト | 種別 | 立地 | メモリ | 写真(24MP) | SMTP | 総合 |
|---|---|---|---|---|---|---|
| **Cloud Run** | 無料枠(超過で課金) | **東京** | **1GB** | **通る** | **通る** | **○** |
| Render | 無料プラン(請求なし) | オレゴン | 512MB | 落ちる | **塞がれている** | ✕ |
| Back4App | 無料プラン(請求なし) | 米国 | 256MB | 落ちる | 通る | △ |
| Northflank | 無料枠 | US | 256MB | 落ちる | 通る | △ |

**「事故で請求が発生しない」ことと「機能が動く」ことが両立しなかった。**
これが Phase 4 の中心的な発見である。

## レイテンシ

| ホスト | `/meta`(DB なし) | `/up`(DB あり) | DB 往復の差分 |
|---|---|---|---|
| **Cloud Run**(東京) | **46ms** | 287ms | 241ms |
| Render(オレゴン) | 147ms | 322ms | **175ms** |
| Back4App(米国) | 193ms | 421ms | 228ms |
| Northflank(US) | 479ms | 864ms | 385ms |

ローカルの基準値は `/up` 2ms、`/shops` 3ms(`phase0-baseline.md`)。

### 「アプリが近い」ことと「DB が速い」ことは別問題

Cloud Run の `/meta` は 46ms で圧勝だが、DB 往復は 241ms でオレゴンの Render(175ms)より**遅い**。
東京とシンガポールは地理的に近いのに逆転している。

**scale-to-zero で DB 接続が維持されず、毎回 TCP と TLS を張り直している**と考えられる。
Render や Northflank はプロセスが生き続けるため `pgxpool` の接続を再利用できる。

**Neon を東京に置ければ解消する**はずで、再計測の価値がある。

### リージョンは思いどおりにならない

| ホスト | 希望 | 実際 | 理由 |
|---|---|---|---|
| Render | シンガポール(`render.yaml` に明記) | **オレゴン** | 手動作成で既定になった。**後から変更できない** |
| Northflank | Asia East | **US** | **無料枠は US のみ**。Asia は有料プラン |
| Back4App | — | 米国(推定) | 選択肢なし |
| Cloud Run | 東京 | **東京** | 希望どおり |

**無料枠で東京に置けたのは Cloud Run だけだった。** レイテンシの順位はほぼこれで決まっている。

## 写真の処理: メモリと画素数の関係

同じ画像を小さい順に投げて、どこで落ちるかを測った。

| 画像 | 画素数 | Cloud Run 1GB | Render 512MB | Back4App 256MB | Northflank 256MB |
|---|---|---|---|---|---|
| 1200x800 | 96 万 | 1.3s | 3.3s | 3.8s | 5.3s |
| 2400x1600 | 384 万 | 1.6s | 5.6s | 5.6s | **33.6s** |
| 4000x2666 | 1,067 万 | 4.6s | 7.5s | 7.2s | **503** |
| 6000x4000 | 2,400 万 | **3.5s** | **502** | **502** | **503** |

### 分かったこと

1. **公称メモリは実効性能と一致しない。** Back4App(256MB)が Render(512MB)と同じ閾値で、
   同じ 256MB の Northflank より明らかに強い。表示値で判断してはいけない

2. **落ちる前に「極端に遅くなる」帯がある。** Northflank の 384 万画素は通るが 33.6 秒かかった。
   96 万画素の 5.3 秒に対し、画素数 4 倍で時間は 6 倍以上である。GC が頻発している兆候で、
   メモリ不足は「動く / 落ちる」の二択ではない。**利用者から見ると、まず遅くなり、次に失敗する**

3. **無料プランの実用上限は 1,000 万画素あたり。** スマートフォンの写真(2,400 万画素)は通らない

4. **落ちてもログに何も残らない。** カーネルが殺すため Go のパニックも出ない。
   エラーコードも事業者で違う(Render/Back4App は 502、Northflank は 503)

5. **復帰の速さが 3 段階に分かれた。** Render と Back4App は即座、Northflank は 20 秒。
   常時起動を謳う Northflank でも、OOM からの再起動には時間がかかる

### 回避できる可能性がある

フロントには送信前に縮小する実装がある(`frontend/src/lib/photoResize.ts`)。
`GET /meta` の `max_edge`(1600px)を見て縮小するため、**ブラウザから普通に使う分には
無料プランでも動く可能性が高い**。API を直接叩いた場合だけ落ちる。

Phase 6 で実際のブラウザ経由の挙動を確かめる価値がある。

## SMTP: 予測が正反対だった

| ホスト | 587/STARTTLS | 結果 |
|---|---|---|
| Cloud Run | **通る** | `sent` |
| Northflank | 通る | `sent` |
| Back4App | 通る | `sent` |
| **Render** | **塞がれている** | `failed` / `dial tcp ...:587: i/o timeout` |

[ADR-0006](../adr/0006-email-delivery.md) では「**Cloud Run** はポート 25/587/465 を塞ぐ」と
予測していたが、**実際に塞いでいたのは Render** だった。しかも Render は
[ADR-0002](../adr/0002-backend-deploy-target.md) の第一候補だった。

**机上の調査が正反対の結論を導いていた。** 両 ADR の訂正が必要である。

エラーの形は Phase 3 で閉じたポート(47777)に向けたときと同じだった。
あのとき「塞がれていたらこう見える」と書いた予測が、ホストだけ入れ替わって的中している。

### Render にとっては致命的

写真が動かず(512MB)、確認メールも送れない。**サインアップが完了しない**ため、
このアプリを Render で運用することはできない。

## 常駐ワーカー: 構造から決まる

### 計測できなかった理由(方法論)

Phase 4 は公平性のため **4 ホストすべてに同じ Neon を向けている**。
`burger_stats_recalc_requests` は共有され、**どのホストのワーカーが処理しても行は消える**。

実際、Cloud Run にレビューを投稿して放置したところ 30 秒で行が消えたが、
常時起動の Northflank か Back4App が処理した可能性が高く、**Cloud Run の証拠にならない**。

Neon のプーラー経由のため、`pg_stat_activity` の接続元もすべて `pgbouncer` に見え、
DB 側からも切り分けできなかった。

**同じ DB を共有する方針は、読み取りの比較では公平性を生むが、
書き込みを伴う常駐処理の検証では干渉を生む。** 目的によって方針が逆になる。

### 構造から導ける結論

ワーカーはプロセス内の goroutine なので、**プロセスが止まれば動かない**。

| ホスト | ワーカーの状態 | 根拠 |
|---|---|---|
| Northflank / Back4App | **動く** | 実測(リクエストなしで処理された)。常時起動 |
| Render | 起きている間は動く。スリープ中は動かない | 構造上自明 |
| Cloud Run | リクエスト外は動かない | 構造上自明(CPU が絞られる) |

### 実害は小さい

現在の実装には 2 つの保険がある。

1. 依頼を DB に積む(書き込みと同一トランザクション)。プロセスが死んでも依頼は残る
2. **起動直後に 1 サイクル実行する**。次に誰かがアクセスした時点で溜まった依頼を回収する

したがって Cloud Run でも「動かなくなる」のではなく「**次のアクセスまで遅れる**」だけである。
レビューサイトでは投稿者自身が直後に結果を見るため、実際には数秒で追いつく。

[ADR-0005](../adr/0005-async-job-platform.md) の判断は変わらない。

ただし**時間減衰のための日次全件再計算は別問題**で、誰のアクセスとも無関係に走る必要がある。
外部 cron が必須で、これは**どのホストを選んでも同じように必要**である。

常時動かしたい場合の選択肢は 3 つ。

| 案 | 代償 |
|---|---|
| そのまま(次のアクセスで回収) | 統計が一時的に古い |
| Cloud Run に `--no-cpu-throttling` | **無料枠の消費が大幅に増える** |
| 外部 cron で数分おきに `/up` を叩く | cron の設定 1 つ。消費は小さい |

日次の全件再計算のために外部 cron はどのみち要るので、**その間隔を短めにすれば
副次的にワーカーも動く**。追加コストはない。

## 計測でつまずいた点

### Cloud Run の最初の計測は無効だった

アプリがデプロイされておらず、**Cloud Run の既定のプレースホルダー画面**を測っていた。
`/meta` と `/up` がどちらも 44ms で、**DB 往復の差分が 0ms** という不自然さが手がかりになった。
決め手は、認証トークンが空なのに写真のアップロードが 200 を返したことだった。

再発防止として `scripts/bench/latency.sh` に事前確認を入れた。計測前に 1 回叩き、
`content-type` が `text/html` なら警告を出す。

**ステータスコードだけを見て計測してはいけない。速すぎる結果こそ疑う。**

### ビルドが通らなかった(2 社)

`go.sum not found` で失敗した。`Dockerfile` は `COPY go.mod go.sum ./` から始まるため、
**ビルドコンテキストが `backend-go` でないと失敗する**。

加えて **Back4App は Dockerfile 名を指定できない**(既定の `Dockerfile` を見る)ことが分かり、
リポジトリの構成を変えた。

| ファイル | 用途 |
|---|---|
| `Dockerfile` | **本番用**(distroless、30.9MB) |
| `Dockerfile.dev` | 開発用。`docker-compose.yml` が使う |
| `Dockerfile.prod` | 互換のための別名 |

**本番用こそ既定の名前に置くべき**という教訓である。

### ローカルの計測は楽観的に出る

Phase 0 のローカル計測では 512MB で 24MP の単発が通っていたが、Render(512MB)では
**単発でも落ちた**。ローカルの Docker には OS 側の余裕があるが、
ホストの 512MB はランタイム全体の上限だからだと考えられる。

## ADR への反映

### [ADR-0002](../adr/0002-backend-deploy-target.md): 第一候補を変える必要がある

当初の決定は **Render** だった。実測では、

- 写真が動かない(512MB)
- **SMTP が塞がれている**(サインアップが完了しない)
- リージョンが変更できない(オレゴン固定)

**Render では運用できない。** 第一候補を **Cloud Run** に変えるべきである。

ただし Cloud Run は無料枠(超過で課金)でカードが必須であり、
「事故で請求が発生しない」という利点は失われる。

### [ADR-0006](../adr/0006-email-delivery.md): SMTP 遮断の記述が逆

「Cloud Run は 25/587/465 を塞ぐ」は誤りだった。実際に塞いでいたのは Render である。
