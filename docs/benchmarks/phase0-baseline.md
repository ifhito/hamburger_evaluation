- 計測日: 2026-09-21

- 対象: `hamburger-api:prod`(本ドキュメントと同時に作成した `backend-go/Dockerfile.prod`)

## 統計ワーカーの動作確認

一括投入で 200 件の再計算依頼を積んだところ、**約 6 秒で全件処理**され `burger_stats` が 206 行になった。
既定の `STATS_WORKER_INTERVAL=1s`、`STATS_WORKER_BATCH=20` で、1 サイクル 20 件ずつ処理する実装どおり。

## 写真アップロードのメモリ(最重要)

テスト画像: 6000x4000(2,400 万画素)、4.6MB の JPEG。iPhone 15 以降の標準サイズ相当。
生成スクリプトは検証時に使い捨て(`image/jpeg` でノイズ画像を作る 30 行程度)。

### 単発

| 項目 | 結果 |
|---|---|
| 結果 | HTTP 201 成功 |
| 所要時間 | 1.07 秒 |
| ピークメモリ | **260.5 MiB**(待機時 12.75 MiB から約 248 MiB 増) |

512MB でも単発なら十分に通る。

### 同時 2 本

**コンテナの状態で結果が変わる。これが本検証で最も重要な発見。**

| 条件 | 結果 |
|---|---|
| 512MB・**起動直後**(ヒープが冷えている) | 5 回中 **0 回** OOM。成功する |
| 512MB・**1 本処理した後**(ヒープが育っている) | 3 回中 **3 回** OOM |
| 512MB + `GOMEMLIMIT=400MiB`・ヒープが育った後 | 3 回中 **3 回** OOM |
| 768MB・ヒープが育った後 | 3 回中 **0 回** OOM |
| 1GB・ヒープが育った後 | 3 回中 **0 回** OOM |
| 1GB + `GOMEMLIMIT=920MiB`(開発と同じ)・ヒープが育った後 | 3 回中 **0 回** OOM |

OOM は `docker inspect` の `OOMKilled=true`、`ExitCode=137` で確認した。Go のパニックではなく
カーネルによる強制終了で、**ログに何も残らない**。

### 読み取り

- 原因は Go の GC が約 260MiB のヒープを OS へすぐ返さないこと。冷えた状態なら 2 本分が
  512MB に収まるが、一度使ったあとは前回分が残っているため 2 本目の山で超える。
- **実運用は常に「育った状態」である。** 起動直後だけ通るという事実は、本番では通らないことを意味する。
- `GOMEMLIMIT` は効かない。GC を強める設定であり、同時に生きる 2 つの大きな確保は減らせない。
- **必要なのは 768MB 以上。**

## ADR への影響

- [ADR-0002](../adr/0002-backend-deploy-target.md): **512MB の無料枠(Render / Koyeb)では写真つき投稿が
  同時に 2 件来ると落ちる。** 無料枠の選定に直接効く。Cloud Run はメモリを選べるが、
  無料枠は GB 秒で測るため 768MB にすると消費が 1.5 倍になる。
- 緩和の選択肢(いずれも未検証、Phase 4 で判断する):
  1. 768MB 以上のプランにする(有料化)
  2. 同時実行数を制限する(セマフォで写真処理を 1 本ずつに直列化)
  3. 受け付ける画素数の上限を下げる(現在 2,400 万画素。1,200 万画素にすればピークは半減する見込み)
  4. フロントの送信前縮小を必須にする(現在も縮小しているが、backend は上限内なら再処理する)

2 は数行で実装でき、レスポンスは遅くなるがメモリは一定に保てる。無料枠を維持したいなら最も安い。
