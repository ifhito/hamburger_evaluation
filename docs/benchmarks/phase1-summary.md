# Phase 1: データベース 4 候補のまとめ

- 計測日: 2026-09-21
- 計測元: 日本(自宅回線)のローカル Docker から、本番用イメージ `hamburger-api:prod` 経由
- データ量: 全社そろえて shops 54 / burgers 206 / reviews 1,009
- 個別の結果: `phase1-neon.md`、`phase1-supabase.md`、`phase1-render.md`、`phase1-xata.md`

## 結果

| 候補 | リージョン | PostgreSQL | マイグレーション | `GET /up` p50 | `GET /shops` p50 | `DB_MAX_CONNS` |
|---|---|---|---|---|---|---|
| Neon | Singapore(ap-southeast-1) | 18.6 | 12 本 OK(37 秒) | **79ms** | **80ms** | 50 まで OK |
| Render Postgres | Oregon(us-west) | 18.6 | 12 本 OK(23 秒) | 139ms | 139ms | 50 まで OK |
| Supabase | Mumbai(ap-south-1) | 17.6 | 12 本 OK(22 秒) | 142ms | 142ms | 50 まで OK |
| Xata | US East(us-east-1) | 18.6 | 12 本 OK(29 秒) | 186ms | 187ms | 50 まで OK |

参考: ローカルの PostgreSQL 16 コンテナでは `/up` 2ms、`/shops` 2〜3ms(`phase0-baseline.md`)。

## 読み取り

### 1. 互換性はすべて問題なし

4 社とも PostgreSQL 17 以上で、`gen_random_uuid()` が使え、マイグレーション 12 本が
**無改変で適用できた**。UUID 主キー、外部キー 6 本、`CHECK` 制約、`db/migrations_test.go` が
求める制約名も含めてそのまま通る。sqlc の生成コードも 4 社すべてで無改変に動いた。

**互換性は候補選びの判断材料にならない。** 差が出たのはレイテンシだけだった。

### 2. 差はほぼ地理的距離で決まる

| 候補 | 距離 | p50 |
|---|---|---|
| Neon | シンガポール | 79ms |
| Render | オレゴン | 139ms |
| Supabase | ムンバイ | 142ms |
| Xata | 米国東部 | 187ms |

`/up`(DB に ping するだけ)と `/shops`(実クエリ)の p50 がほぼ同じであることに注目する。
**DB の処理時間ではなく往復の時間が支配的**で、この規模のデータでは DB の性能差は測定に現れない。

### 3. リージョンの選択が結果を決めている

今回はアカウント作成時に選べるリージョンをそのまま使った。実際には次の制約があった。

- Neon: 無料枠で ap-southeast-1(シンガポール)が選べた。東京はない
- Supabase: 既存プロジェクトが ap-south-1(ムンバイ)だった。**新規なら東京も選べる**
- Render: 無料枠は us-west(オレゴン)。シンガポールは有料プランのみ
- Xata: us-east-1

**Supabase を東京で作り直せば、この表の順位は変わる可能性が高い。** 東京なら往復は 10〜30ms 程度に
なるはずで、Neon の 79ms を大きく下回る。これは再計測する価値がある。

### 4. 接続数は 4 社とも 50 まで問題なし

`DB_MAX_CONNS` を 5 / 10 / 20 / 50 と変えて、起動と同時リクエストを試した。
どれも失敗しなかった。無料枠でも、この規模なら接続数が制約にならない。

## ハマった点

### Supabase の Direct connection は IPv6 専用で Docker から繋がらない

最初に設定された URL は `db.<ref>.supabase.co`(Direct connection)で、次のエラーが出た。

```text
hostname resolving error: lookup db.<ref>.supabase.co ... : no such host
```

`dig` で確認したところ **A レコードがなく AAAA のみ**だった。macOS のホストからは
`psql` で繋がるが、Docker コンテナの DNS では解決できない。

**Session pooler**(`aws-0-<region>.pooler.supabase.com`)に替えると通った。こちらは
AWS の ELB を指す IPv4 のホスト名である。

同じ理由で、Transaction pooler(6543)も避けている。pgx は既定で prepared statement を
使う(`QueryExecModeCacheStatement`)が、transaction モードのプーラーはコネクションを
トランザクション単位で使い回すため相性が悪い。

### psql とコンテナで到達性が違う

上の件の直接の帰結として、**ホストの `psql` で繋がっても、コンテナから繋がるとは限らない**。
`db-verify.sh` は psql をホストで、マイグレーションと API をコンテナで動かすため、
この差が「psql は通ったがマイグレーションが失敗し、テーブルが無い」という形で現れた。

# 追加計測: DB 単体の読み書き(pgx で直接、200 回ずつ)

- 計測日: 2026-09-21
- 方法: アプリの HTTP 層を挟まず `pgx` で直接叩く(`scripts/bench/db-ops.sh`)
- 各社の詳細は `phase1-<社名>.md` の末尾にある

上の計測はアプリの HTTP エンドポイント経由だったため、アプリの処理時間と DB の往復が
混ざっていた。また読み取りしか測っていなかった。ここでは DB とネットワークの往復だけを、
読み 5 種と書き 4 種について測る。

## 結果の要約

| 候補 | リージョン | 往復のみ p50 | 単発操作 p50 の幅 | トランザクション p50 | 倍率 | 往復のみの標準偏差 |
|---|---|---|---|---|---|---|
| Neon | シンガポール | 86.2ms | 86.3〜87.4ms | **347.9ms** | 4.04 倍 | 2.8ms |
| Supabase | ムンバイ | 131.1ms | 131.3〜132.8ms | **526.8ms** | 4.02 倍 | 14.6ms |
| Render | オレゴン | 146.2ms | 146.4〜147.8ms | **587.6ms** | 4.02 倍 | 7.9ms |
| Xata | 米国東部 | 177.4ms | 177.5〜180.0ms | **713.8ms** | 4.02 倍 | 1.5ms |

「単発操作」は主キー 1 件・一覧 20 件・結合 20 件・集計・INSERT・UPDATE・DELETE の 7 種。
その p50 が収まる幅を示している。

## 分かったこと

### 1. DB の処理時間はネットワークに完全に埋もれている

4 社すべてで、**主キー 1 件の取得も、3 テーブルの結合 20 件も、全レビューの集計も、
`SELECT 1` と区別がつかない**。差は最大でも 3ms である。

| Neon の例 | p50 |
|---|---|
| `SELECT 1`(往復のみ) | 86.2ms |
| 主キー 1 件 | 86.4ms |
| 一覧 20 件 | 86.3ms |
| 結合 20 件(3 テーブル) | 87.2ms |
| 集計(バーガー別の平均評価) | 86.7ms |

**この規模のデータでは、DB の性能指標を比べても意味がない。** インデックスの効きも
実行計画の良し悪しも、往復の 86ms に埋もれる。ベンチマークのスループット値を見て
DB を選ぶのは、この規模では誤りである。

### 2. 書き込みは距離のペナルティを 4 倍受ける

トランザクションだけが突出している。4 社とも**倍率が 4.02〜4.04 で一致**した。

理由は往復回数である。レビューの作成は次の 4 往復からなる。

```text
BEGIN
INSERT INTO reviews ...
INSERT INTO burger_stats_recalc_requests ... ON CONFLICT ...
COMMIT
```

事業者も距離も違うのに倍率が同じであることが、**時間を決めているのが DB の性能ではなく
往復回数であること**の証拠になっている。

実務的な意味は大きい。日本から見て、レビューの閲覧は 86ms で済むのに、**投稿は DB の
往復だけで 348ms かかる**(Neon の場合)。Xata なら 714ms である。

### 3. 平均だけ見ると安定性を見誤る

平均値では Supabase(133ms)と Render(148ms)は近く見えるが、ばらつきが違う。

| 候補 | 往復のみの標準偏差 | p99 | 最大 |
|---|---|---|---|
| Xata | 1.5ms | 181.8ms | 189.8ms |
| Neon | 2.8ms | 96.5ms | 114.2ms |
| Render | 7.9ms | 168.3ms | 247.0ms |
| Supabase | 14.6ms | 159.5ms | 327.7ms |

**Xata と Neon は極めて安定している。** Supabase は往復のみの最大値が 327ms と、
p50 の 2.5 倍に達する外れ値を持つ。プーラー(Supavisor)経由の接続取得が時々遅い
ことを示唆する。

Render も DELETE の最大値が 379ms、Xata は DELETE の標準偏差が 84.9ms・最大 1,739ms と、
書き込み系で大きな外れ値が出た。**p50 だけでなく p99 と最大値を併記する理由がこれである。**

### 4. 順位は距離で決まり、距離はリージョンの選択で決まる

往復のみの p50 を地理的距離と並べると、ほぼ単調に対応する。

| 候補 | リージョン | 往復 p50 |
|---|---|---|
| Neon | シンガポール | 86.2ms |
| Supabase | ムンバイ | 131.1ms |
| Render | オレゴン | 146.2ms |
| Xata | 米国東部 | 177.4ms |

今回の順位は、**無料枠で選べたリージョンがそのまま出たもの**であり、DB の優劣ではない。

- Neon: 無料枠は ap-southeast-1(シンガポール)。東京はない
- Supabase: 既存プロジェクトが ap-south-1(ムンバイ)だった。**新規なら東京を選べる**
- Render: 無料枠は us-west(オレゴン)。シンガポールは有料プランのみ
- Xata: us-east-1

**Supabase を東京で作り直せば、往復は 10〜30ms 程度になり、Neon の 86ms を大きく
下回る見込みである。** 再計測の価値が高い。

## 実装への示唆: トランザクションを 1 往復にできる

現在の書き込み経路は 4 往復だが、CTE を使えば 1 文にまとめられる。

```sql
WITH r AS (
  INSERT INTO reviews (rating, comment, user_id, burger_id)
  VALUES ($1, $2, $3, $4)
  RETURNING id, burger_id
)
INSERT INTO burger_stats_recalc_requests (burger_id)
SELECT burger_id FROM r
ON CONFLICT (burger_id) DO UPDATE
  SET version = nextval('burger_stats_recalc_requests_version_seq'), updated_at = now()
```

単一文は暗黙にアトミックなので、現在の整合性(レビューの作成と再計算依頼の登録が
不可分であること)は保たれる。往復が 4 回から 1 回になるため、**レビュー投稿の DB 時間は
348ms から 87ms へ、およそ 4 分の 1 になる見込み**である。

遠いリージョンほど効果が大きく、リージョンを選べない無料枠に対する直接的な対策になる。
ただしこれは実装の変更であり、本検証の範囲外とする。別途 issue として起票する価値がある。

## ADR への反映

[ADR-0003](../adr/0003-database-hosting.md) の決定(Neon を第一候補)は支持されたが、
**理由は当初の想定と違う**。

| | 当初の理由 | 実測で判明した理由 |
|---|---|---|
| Neon を選ぶ根拠 | 無料枠が無期限で、休止からの復帰が速い | **日本から最も近く、最も安定している**(標準偏差 2.8ms) |
| 互換性の懸念 | 分散 SQL は UUID や制約で詰まりうる | **4 社とも無改変で動いた。判断材料にならない** |
| 性能の比較 | DB ごとの処理性能を比べる | **この規模では往復に埋もれ、比較できない** |
