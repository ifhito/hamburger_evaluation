# Phase 4: Google Cloud Run

- 計測日: 2026-09-22
- URL: `https://burger-stack-421794940461.asia-northeast1.run.app`
- 種別: **無料枠**(超過で課金。カード必須)
- リージョン: asia-northeast1(東京)
- メモリ: **1GB**(最初からこの設定)

## レイテンシ

| エンドポイント | n | p50 | p95 | 最小 | 最大 |
|---|---|---|---|---|---|
| `GET /meta`(DB なし) | 60 | **46ms** | 55ms | 40ms | 65ms |
| `GET /up`(DB あり) | 60 | 287ms | 370ms | 279ms | 406ms |
| `GET /shops` | 60 | 289ms | 336ms | 281ms | 521ms |

DB 往復の差分は **241ms**。

### 「アプリが近い」ことと「DB が速い」ことは別問題

`/meta` の 46ms は 4 ホストで最速で、東京リージョンの効果がそのまま出ている。
日本からの往復に TLS を足した値としてほぼ理論値である。

ところが `/up` では逆転が起きる。

| ホスト | アプリの位置 | `/meta` | DB 往復 |
|---|---|---|---|
| Cloud Run | 東京 | **46ms** | 241ms |
| Render | オレゴン | 147ms | **175ms** |

東京とシンガポールは地理的に近いのに、オレゴンからより遅い。
**scale-to-zero で DB 接続が維持されず、毎回 TCP と TLS を張り直している**と考えられる。
Render や Northflank はプロセスが生き続けるため `pgxpool` の接続を再利用できる。

読み取りだけなら Cloud Run が圧勝だが、DB を触る経路では優位が消える。
**Neon を東京に置ければ解決する**はずで、再計測の価値がある。

## 写真のアップロード: 唯一すべて成功

| 画像 | 結果 | 時間 |
|---|---|---|
| 154KB | 201 | 3.2 秒 |
| **24MP(4.6MB)単発** | **201** | 5.5 秒 |
| **24MP 同時 2 本** | **201 × 2** | 6.2 / 7.3 秒 |
| 直後の `/up` | 200(落ちない) | — |

**4 ホストで唯一、24MP の写真が通った。** Phase 0 のローカル計測
(「768MB 以上が必要、1GB なら同時 2 本も通る」)が本番で再現した。

## SMTP: 予測が外れて通った

[ADR-0006](../adr/0006-email-delivery.md) では「Cloud Run はポート 25/587/465 を
塞ぐため SMTP が使えない」と予測していた。

**実際には通った。** Mailjet の 587 番(STARTTLS)でサインアップ確認メールを送信でき、
`mail_deliveries` は `sent` になった。

**ADR-0006 と ADR-0002 の記述を訂正する必要がある。** この予測は
ADR-0002 で Cloud Run の順位を下げた根拠の 1 つだった。

## 常駐ワーカー: 計測できなかった(方法論の問題)

「リクエスト外で統計ワーカーが動くか」を測ろうとしたが、**この検証は現在の構成では
成立しない**ことが分かった。

### 原因

Phase 4 は公平性のため **4 ホストすべてに同じ Neon の DB を向けている**。
`burger_stats_recalc_requests` は共有されており、**どのホストのワーカーが処理しても
行は消える**。

| ホスト | 起動モデル | 無通信時のワーカー |
|---|---|---|
| Cloud Run | scale-to-zero | 止まるはず(検証したい対象) |
| Render | 15 分でスリープ | 15 分間は動き続ける |
| Northflank | **常時起動** | **ずっと動く** |
| Back4App | **常時起動** | **ずっと動く** |

実際、Cloud Run にレビューを投稿して放置したところ **30 秒で行が消えた**。
常時起動の Northflank か Back4App が処理したと考えられ、
**Cloud Run のワーカーが動いた証拠にはならない。**

### 教訓

同じ DB を共有する方針は、**読み取りの比較では公平性を生むが、
書き込みを伴う常駐処理の検証では干渉を生む**。目的によって方針が逆になる。

### 測り直す方法

1 ホストずつ、他を止めて測る必要がある。

- Northflank と Back4App を一時停止する、または
- 他のホストの `STATS_WORKER_INTERVAL` を `24h` などにして実質止める(再デプロイが要る)

## 評価

**機能面では 4 ホストで唯一の合格。** 東京リージョン、写真が動く、SMTP も通る。

一方で **無料枠(超過で課金)であり、カードが必須**である。無料プラン 3 社
(Render・Northflank・Back4App)はいずれも写真機能が動かなかった。

**「事故で請求が発生しない」ことと「機能が動く」ことが両立しない**、というのが
Phase 4 の中心的な発見である。
