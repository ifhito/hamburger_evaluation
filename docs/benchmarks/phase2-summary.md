# Phase 2: 写真ストレージ 4 候補のまとめ

- 計測日: 2026-09-21
- 計測元: 日本(自宅回線)から、`adapter/storage/s3.go` と同じ組み立ての S3 client
- 物体の大きさ: 300KiB(長辺 1600px に縮小したあとの JPEG 相当)
- 各操作 50 回。個別の結果は `phase2-<社名>.md`

## 結果

| 候補 | 公開配信 | PUT p50 | **GET p50** | DELETE p50 | GET の標準偏差 |
|---|---|---|---|---|---|
| **Tigris** | `*.tigrisfiles.io` | **89.2ms** | **26.0ms** | **22.3ms** | 19.3ms |
| Supabase Storage | `*.supabase.co/storage/v1/...` | 433.2ms | 38.5ms | 199.8ms | 106.1ms |
| Cloudflare R2 | `*.r2.dev`(開発用) | 160.2ms | 80.9ms | 77.8ms | 36.8ms |
| Backblaze B2 | `f005.backblazeb2.com` | 233.2ms | 280.7ms | 185.6ms | **8.5ms** |

## 分かったこと

### 1. Region のハードコードは問題にならなかった(予想が外れた)

`adapter/storage/s3.go` は次のように Region を固定している。

```go
client := s3.New(s3.Options{
    BaseEndpoint: aws.String(endpoint),
    Region:       "auto", // R2 のプレースホルダのリージョン
    Credentials:  credentials.NewStaticCredentialsProvider(accessKeyID, secretAccessKey, ""),
    UsePathStyle: true,
})
```

AWS の署名 v4 は署名鍵にリージョンを含むため、実リージョンを要求する事業者では
署名エラーになると予想していた。**4 社ともそのまま通った。** B2 のように
エンドポイントにリージョン名(`s3.us-east-005.backblazeb2.com`)を持つ事業者でも、
署名側の Region は `auto` のままで受け付けられた。

**[ADR-0004](../adr/0004-photo-storage.md) の「エンドポイントを差し替えるだけで載る」
という前提は支持された。** コード変更は要らない。

### 2. Tigris が全項目で最速だった

GET 26.0ms は R2 の 80.9ms の 3 分の 1、B2 の 280.7ms の 10 分の 1 である。
PUT と DELETE も最速だった。アクセスされた地域へデータを自動的に寄せる仕組みが
効いていると考えられる。

ADR-0004 では「Fly.io を使う場合のみ R2 と並ぶ」と位置づけていたが、
**単体で R2 を明確に上回っている。**

### 3. 書き込みと読み取りの速さは連動しない

| 候補 | PUT | GET | 比(PUT / GET) |
|---|---|---|---|
| Supabase | 433.2ms | 38.5ms | **11.2 倍** |
| R2 | 160.2ms | 80.9ms | 2.0 倍 |
| Tigris | 89.2ms | 26.0ms | 3.4 倍 |
| B2 | 233.2ms | 280.7ms | 0.8 倍 |

Supabase は書き込みが際立って遅い一方、読み取りは 2 番目に速い。書き込みが API
ゲートウェイを通り、読み取りが CDN から出ていると推測できる。

**写真は 1 回書いて何度も読まれるので、この偏りは実用上むしろ有利である。**
逆に B2 は読み書きがほぼ同じ速さで、読み取りに最適化されていない。

### 4. 安定性は B2 が最も高い

| 候補 | GET の標準偏差 | GET の最大 |
|---|---|---|
| B2 | 8.5ms | 315.5ms |
| Tigris | 19.3ms | 115.5ms |
| R2 | 36.8ms | 307.4ms |
| Supabase | 106.1ms | 779.9ms |

B2 は遅いが**極めて安定している**。Supabase は p50 が 38.5ms と速いのに標準偏差が
106.1ms、最大が 779.9ms と大きく揺れる。**平均だけ見ると Supabase が優秀に見えるが、
2 割ほどの閲覧で目に見えて待たされる。**

Tigris は速さと安定性を両立している。

## 注意すべき点

### R2 は開発用 URL で測っている

R2 の公開配信は `pub-xxx.r2.dev` を使った。これは**開発用でレート制限があり、
本番では非推奨**である。本番はカスタムドメインを繋ぐ想定なので、
**独自ドメインで測り直せば GET が改善する可能性がある。** 公平な比較のためには再計測が要る。

他の 3 社は既定の公開 URL をそのまま使っており、この不利はない。

### 今回測っていないもの

- **転送量の課金**: 50 回の PUT と GET で約 29.3 MiB を消費した。無料枠の残量は
  各社のダッシュボードで確認する必要がある。R2 は転送量が無料・無制限なので、
  この軸では依然として唯一である
- **大量配信時の挙動**: 50 回では CDN のキャッシュが十分に温まらない可能性がある

## ハマった点

### Backblaze B2 はマスターキーが S3 API で使えない

最初に設定された `keyID` は 12 文字で、これは**アカウント ID**(マスターキーの keyID)だった。
B2 は S3 互換 API でマスターキーを拒否し、`InvalidAccessKeyId: Malformed Access Key Id`
を返す。

App Keys から新規のアプリケーションキーを作ると、`keyID` は 25 文字(`005` で始まる)、
`applicationKey` は 31 文字(`K005` で始まる)になる。これで通った。

紛らわしいのは、**アカウント ID が画面上部に大きく表示されている**点である。
`applicationKey` は作成直後の一度しか表示されない。

### Cloudflare R2 のバケット名

最初の実行は `NoSuchBucket` で失敗した。バケット名の指定違いだった。
エンドポイント(アカウント ID)が正しくてもバケット名が違えば 404 になる。

## ADR への反映

[ADR-0004](../adr/0004-photo-storage.md) の決定は **R2** だった。実測を踏まえると、
判断が変わりうる。

| 観点 | R2 | Tigris |
|---|---|---|
| 転送量の課金 | **無料・無制限** | 従量(Fly.io 内なら無料) |
| 保存の無料枠 | 10GB | 5GB |
| GET の速さ | 80.9ms(開発用 URL) | **26.0ms** |
| PUT の速さ | 160.2ms | **89.2ms** |

**速さでは Tigris、費用では R2 である。** どちらを採るかは配信量の見込みによる。
写真が増えて転送量が効いてくるなら R2、体感の速さを優先するなら Tigris になる。

次の 2 つを確かめてから決めるのが妥当である。

1. R2 をカスタムドメインで測り直す(開発用 URL の不利を除く)
2. Tigris の転送量の課金条件を確認する(Fly.io 外からの配信がいくらか)
