- 日付: 2026-09-21(2026-09-20 初版を、Rails 退役と実装の確認を受けて改訂)
- 目的: [ADR-0001〜0006](adr/) の決定案を実測で裏付け、ブログ記事のシリーズにする
- 手順: [検証手順書](deploy-verification-runbook.md)

## 初版からの変更点

実装(`backend-go`)を読んだ結果、前提が変わった。

| 項目 | 初版 | 改訂後 |
|---|---|---|
| 検証に使うアプリ | 最小構成を新規に作る | **本物をそのまま使う**。`backend-go` は完成している |
| 層の数 | 5 層 20 候補 | **6 層 24 候補**(メール送信を追加) |
| Phase 0 の作業 | 最小 API を実装する | **本番用 Dockerfile を作る** |
| 画像の検証 | 署名付き URL のコード量を比較 | **API のメモリ**を測る(アップロードが API を通るため) |
| 非同期の検証 | どの基盤を採用するか | 現行実装を前提に、**Cloud Run で常駐ワーカーが動くか**を測る |
| DB の検証 | bigint 連番 PK の移行 | **UUID 主キー**と PostgreSQL 13 以上 |

## 選定基準

「無料で始められる」に加えて、**個人が一人で最後まで到達できること**を条件にする。

1. セルフサービスで完結する(営業への問い合わせや審査がない)
2. サーバーの面倒を見なくてよい(OS 更新・TLS・バックアップ・監視を持たない)
3. 権限設計が要らない(IAM やネットワークの設計なしに動く)
4. ダッシュボードか CLI だけで完結する
5. 個人向けのドキュメントがある

この基準で Oracle Cloud(VM 運用)と分散 SQL(CockroachDB / YugabyteDB)は検証対象から外した。
分散 SQL は主キーが UUID になったことで技術的な障害は減ったが([ADR-0003](adr/0003-database-hosting.md))、
単一リージョンの個人アプリに利点がない。

## 候補の選び方

層ごとに**対比の軸**を先に決め、その軸の端に来るものを選ぶ。

| 層 | 対比の軸 | 記事タイトル案 |
|---|---|---|
| API | メモリと CPU をいつもらえるか | Go API を無料で動かす 4 つの形 |
| DB | 休む DB は使えるか | 無料 Postgres 4 つを pgx から叩く |
| 写真 | 転送量が無料なのはどこか | 画像ストレージ 4 つ、転送量で殴り合う |
| メール | SMTP が通るのはどこか | 無料のメール送信 4 つと、塞がれたポート |
| 非同期 | 誰がジョブを起こすか | 寝ているサーバーで日次バッチを回す 4 手 |
| フロント | `/api` をどう転送するか | 静的 SPA の API プロキシを 4 方式で書き比べる |

## 1. API(ADR-0002)

軸: メモリと CPU をいつもらえるか。画像処理と常駐ワーカーがあるため、単純なレイテンシ比較では足りない。

Phase 0 で「512MB では 24MP の同時 2 本が OOM する」と判明したため、
**ホスト 3 つ × メモリ 2 段階**の 4 通りを測る構成に変えた(当初の Koyeb は利用できず)。

| # | 候補 | 起動モデル | メモリ | 立地 | 選んだ理由 |
|---|---|---|---|---|---|
| 1 | Render(無料 512MB) | 15 分でスリープ | 512MB | シンガポール | 手数最少・カード不要。ベースライン |
| 2 | Zeabur | スリープあり | 要確認 | 東京 | 東京かつ日本語 UI。個人開発者向け |
| 3 | Cloud Run(512MB) | scale-to-zero | 512MB | 東京 | 無料枠は最大。常駐ワーカーと SMTP が焦点 |
| 4 | Cloud Run(1GB) | scale-to-zero | 1GB | 東京 | **写真の OOM を避ける最も安い方法**になりうるかを測る |

3 と 4 を分けたのは、Cloud Run が従量課金で、メモリを上げても低トラフィックなら
ほぼ無料のままでありうるためである。「いくら払えば落ちなくなるか」が記事の問いになる。

測る指標:

- **写真の同時アップロードで OOM するか**(Phase 0 の再現。ヒープが育った状態で同時 2 本)。最重要
- OOM を避けるのに必要なメモリと、その月額
- 30 分放置後の初回応答(`GET /up` を 5 回、中央値)
- 定常時の p50 / p95(`GET /shops` を 100 回)
- **リクエスト外で統計ワーカーが動くか**(4 の Cloud Run が焦点)
- **外向き SMTP の疎通**(4 は塞がれている想定)
- デプロイ成功までの手数と所要時間、カード要否

## 2. DB(ADR-0003)

軸: 無料枠の Postgres が「休む」ことにどう対処するか。

| # | 候補 | 休止の挙動 | 立地 |
|---|---|---|---|
| 1 | Neon | 無通信で自動休止、復帰 1 秒未満 | シンガポール |
| 2 | Supabase | 1 週間無通信で停止、手動復帰 | 東京 |
| 3 | Render Postgres | 休止しない(無料枠は 30 日で失効) | シンガポール |
| 4 | Xata | 自動休止 | 要確認 |

測る指標:

- マイグレーション 12 本が無改変で通るか(UUID・外部キー・`CHECK` 制約)
- 休止からの復帰時間
- `DB_MAX_CONNS` をいくつまで上げられるか
- `GET /shops` と `GET /up` の差(DB 往復のコスト)
- `STATS_WORKER_INTERVAL` を 1 秒のままにしたときの、無料枠のコンピュート消費

## 3. 写真ストレージ(ADR-0004)

軸: 転送量の無料枠。保存は API が行うので、比較対象は配信側になる。

| # | 候補 | 転送量 | 立地 |
|---|---|---|---|
| 1 | Cloudflare R2 | 無料・無制限 | 自動配置 |
| 2 | Supabase Storage | 5GB/月 | 東京 |
| 3 | Tigris | 従量 | グローバル |
| 4 | Backblaze B2 | 保存量の 3 倍/月 | 米・欧 |

測る指標:

- `PHOTO_S3_ENDPOINT` の差し替えだけで `adapter/storage/s3.go` が動くか(4 社すべて)
- 同じ画像を 1000 回配信したときの転送量の消費と、無料枠の残り
- 日本からの画像配信レイテンシ
- `PHOTO_PUBLIC_BASE_URL` によるカスタムドメイン配信の設定手数

## 4. メール送信(ADR-0006)

軸: SMTP が通るか。ホストとサービスの組み合わせで決まるため、API 編と連動して測る。

**4 つとも本番で使えることを条件に選んだ。** 当初は Gmail SMTP(規約上グレー)と
SendGrid(新規アカウントの審査で止まる事例が多い)を含めていたが、採用しえないものを
測る意味がないため差し替えた。

| # | 候補 | 無料枠 | 代表する軸 |
|---|---|---|---|
| 1 | Resend | 3,000 通/月、100 通/日 | 開発者向けの新興。設定の軽さ |
| 2 | Mailjet | **6,000 通/月、200 通/日** | 無料枠の最大値。EU 系の大手 |
| 3 | SMTP2GO | 1,000 通/月 | SMTP 専業。到達率重視 |
| 4 | MailerSend | 3,000 通/月 | メール配信会社の transactional 部門 |

測る指標:

- **4 つの API ホスト × SMTP の疎通可否**(この表が記事の核になる)
- 独自ドメインなしで送れるか(Mailjet と SMTP2GO は送信者アドレスの認証だけで可)
- 送信から受信までの所要時間
- 迷惑メール判定されるか(独自ドメイン設定の前と後)
- SPF / DKIM の設定手数

## 5. 非同期処理(ADR-0005)

軸: 定期実行を誰が起こすか。統計ワーカー自体は現行実装を維持するので、検証対象は定期ジョブの担い手。

| # | 候補 | 起こす主体 | 選んだ理由 |
|---|---|---|---|
| 1 | cron-job.org | 外部 cron | 最も手軽。ベースライン |
| 2 | GitHub Actions | CI | 設定がリポジトリに残る。遅延の実測が焦点 |
| 3 | Upstash QStash | 外部キュー | 再試行と DLQ つき |
| 4 | Cloud Scheduler | GCP | API が Cloud Run のときの純正手段 |

測る指標:

- 指定時刻からの発火遅延(2 は数分〜十数分ずれる想定)
- 寝ているホストを起こせるか
- 全件再計算が `burger_stats_recalc_requests` を正しく積み、ワーカーが処理しきるか
- 失敗時の再試行(3 と 4)

## 6. フロントエンド(ADR-0001)

軸: `/api/*` をどう転送するか。

| # | 候補 | 転送の書き方 |
|---|---|---|
| 1 | Render Static Site | `render.yaml` の rewrites |
| 2 | Cloudflare Workers | Worker のコードで `fetch` 転送 |
| 3 | Netlify | `_redirects` に 1 行 |
| 4 | Vercel | `vercel.json` の rewrites |

測る指標:

- 転送設定の記述量と、疎通までの時間
- 転送経由と API 直叩きのレイテンシ差
- deep link(`/reviews/<uuid>`)が設定なしで動くか
- **OAuth の `redirect_uri` 登録が必要な URL の数**(プレビュー環境が使えないことの実証)

## 検証しないもの(理由は各記事で触れる)

- **Oracle Cloud Always Free / Kamal / Coolify + VPS**: サーバー運用を自分で持つ
- **CockroachDB / YugabyteDB**: 単一リージョンの個人アプリに利点がない
- **Fly.io**: 新規向け無料枠が廃止
- **AWS S3 / RDS**: 無料枠が 12 か月で終わる
- **AWS ECS / Azure Container Apps**: 権限とネットワークの設計が要る
- **Cloudflare Workers 本体 / Fermyon**: Go は TinyGo → Wasm になり pgx が動かない
- **ImageKit / Cloudinary**: 保存時に 1600px へ縮小済みで、動的変換の必要が薄い
